# 自动化与 AI 判断条件

自动化由 backend 在当前家庭内运行，配置和执行记录保存到 PostgreSQL。Web 的 `/automations` 在规则树内配置设备属性、时间和 AI 判断条件；Agent 可以生成规则草稿、选择获准动作或复核设备证据。确定性规则不依赖 Agent 在线，不向米家云端创建自动化。运行按本机低并发设计，允许丢掉单次触发、动作或日志；失败结束本次工作，后续正常触发和周期继续。

本页说明当前实现。持续调查、主动问询、完整家庭情景及后续验收见[协作计划](plans/household-automation.md)；设备值的来源资格见[设备事实](contracts/device-facts.md)，控制协议与未验证范围见[米家来源契约](contracts/mijia.md#设备控制入口)。

## 使用与运行前提

1. 配置数据库并运行仓库根目录的 `bun run db:migrate`。backend 迁移命令同时初始化 Graphile Worker 的数据库结构。Graphile Worker 是保存和派发后台任务的 PostgreSQL 调度库，用一个执行位置串行处理模型任务和AI 条件扫描。规则求值和设备动作调度在 backend 内存中完成，设备动作并发上限为 4；固定动作不等待数据库登记或任务领取即可发送。设备请求和模型等待不阻塞后续规则求值，关闭时停止接纳、取消未发送动作并等待执行器及日志队列结束。
2. 绑定家庭并确认设备清单与规格可用。规则树可用已读取的云端缓存、初始值或已接纳上报判断条件，无需预先配置 `rule_eligible`；设备离线、缺值、过期、规格不明或值无效时仍按未知处理。
3. 在规则树页手动编辑，或输入一句话生成草稿。查看行为说明、节点求值和动作后保存并启用；保存未启用草稿不会执行。新增条件时选择「AI 判断」，填写目标、参考属性和间隔；预算和判断有效期在高级设置中。

每条规则的「触发与条件日志」展示最近 50 次已保存的执行，打开后每秒刷新。固定动作通过条件和冷却检查后进入内存执行流程，全部动作结束后异步保存记录；Agent 决策在请求登记时创建记录，所选动作结束后异步补充结果。记录可能延迟出现；数据库故障、日志队列满或进程中断可能造成缺失或状态未更新，不阻止设备控制，也不会触发重发。成功保存的失败、取消或决策跳过记录保留原因。基线、条件未满足和重复状态更新不产生运行日志。展开记录可查看触发来源与时间、输入时使用的设备值、条件节点结果和规则版本。页面不展示耗时指标、执行时间线或逐项动作轨迹。

轨迹分别记录输入捕获、内存规则计算起止、执行记录开始保存与提交完成、动作进入内存队列与领取、发送准备、控制请求发出及返回。规则计算耗时由单调计时器独立测量；时间戳相减只表示对应阶段间隔，不以数据库记录的事务时间冒充计算耗时。没有采集到的阶段不补造时间；记录的提交时间在事务提交后补记，日志写入失败会告警，不重新发送动作。固定动作的记录保存发生在控制之后，不能把规则结束至日志写入的间隔算成发送延迟。

属性写入还会关联同一家庭运行期、同一设备和属性最近一次已记录发送的命令，在发送后 30 秒内收到与目标值匹配的实时上报时保存反馈时间及证据身份。请求返回前已到达的反馈通过返回后读取当前观测补充，执行日志提交后再读取一次当前观测；反馈记录有并发容量限制，服务重启、来源中断、日志尚未保存、快速连续覆盖或超出窗口都可能导致缺失。缓存读取不作为反馈；没有反馈不等于设备未执行，有匹配反馈也不证明由本次命令导致。页面的「触发上报至状态反馈」使用后端接收时间，不表示人在现场出现到设备物理动作的精确耗时。

缓存只参与条件判断和建立基线，本身不触发设备属性规则。新启用、修改和重启先记录当前状态；之后该属性被接纳的新实时上报使条件从不满足变为满足，才产生进入触发，退出方式同理。同值上报不产生进入或退出触发；属性持续条件从新上报确认满足时开始计时，缓存不会自行启动持续计时。时间窗口与独立事件沿用各自的触发来源。上报被识别为重放、基线或未接纳时不能当作实时触发。

属性上报通过索引定位相关规则，读取各规则引用的当前值，随即在内存中计算并更新条件状态、持续计时和冷却。同值上报不会重复产生进入或退出触发；持续条件在首次实时上报确认后开始计时，后续重复上报不重置期限。离线、恢复和有效性变化同样更新状态。未命中的输入不保存到数据库；命中后完整冻结规则引用的已有设备证据、条件结果和规则版本，不按属性数量截断，固定动作直接进入内存队列，Agent 决策则登记数据库任务。

例如已有缓存为“卧室无人、床头灯开启”，启用时不执行；此后人在传感器上报“有人”，即可结合床头灯缓存判断并打开大灯，无需先等床头灯也上报。缓存的真实采样时间可能未知，规则使用期间可能暂时与设备实际状态不一致，后续上报会更新条件。

属性采集策略位于本机 `config/collection.json`，结构及 `verified_push`、`rule_eligible` 用法见[设备事实配置](contracts/device-facts.md#本机策略)。这些标记仍描述经过配置验证的设备证据，供情景复核等消费者使用；规则树使用缓存不会把它们改为真。已配置的过期规则、已知离线和明确数据缺口仍使对应事实失效。自动化不会自行扩大采集或控制授权。

自然语言生成、Agent 动作选择和情景复核另需可用的 Agent 数据库及模型配置。默认运行边界为可信本机、单 backend 与单 Agent 进程；没有跨实例执行保证。

## 规则树与条件角色

一份规则定义保存 AND、OR、NOT 分组、条件节点、动作、冷却期和动作启动期限。Web 使用 `react-querybuilder` 处理嵌套编辑，在页面边界转换为项目共享契约；规则语义归 `packages/api`，组件格式不进入执行领域。

每个条件标注「触发」或「状态」。触发节点同时参与判断，并声明开始满足、退出满足、持续满足或独立事件发生；状态节点只检查当前条件，变化后不会单独执行，也不补发曾被阻止的触发。条件支持设备属性、带时区和星期的时间窗口，以及已注册的家庭事件。手动新增时间窗口时采用浏览器本地时区；编辑已有窗口保留其保存的时区。页面只显示时区说明，不提供切换控件。

例如「有人且光线暗就开灯」可把两者均标为触发，任一条件最后成立都能发起执行；「有人进入时，如果光线暗就开灯」则把有人条件的进入标为触发，把光线暗标为状态。生成器按语义选择角色和方式，返回简短解释。设备范围优先采用需求明确的房间，保留其中的传感器等条件来源；房间内已有同名设备时，不因名称匹配引入其他房间的设备。明确提到的其他房间、范围外独有名称的设备及当前草稿引用仍会保留。模型上下文按设备分组，合并重复字段，不删减能力约束；实际请求或上下文超出上限时，提示缩小房间范围，或先手动填写规则再描述调整要求。缺少重要阈值或动作时机有歧义时返回澄清问题，不擅自补成可执行规则。页面分别显示生成中、草稿已填入和仍需补充信息；补充后仍需澄清时显示已提交的内容。

规则求值保留真、假、未知。缺值、离线、过期和无效值保持未知；NOT 不把未知变成真。AND 不要求多个触发同时出现，OR 的触发必须来自证明本次结果成立的分支。退出方式在条件离开原满足状态时生效；持续方式遇假或未知清除计时，后续由新上报重新开始。同值上报不产生新的进入或退出触发，冷却到期本身也不产生触发。

backend 按设备、属性维护相关规则索引，条件列表按定义缓存，输入只读取规则引用的属性；状态变化更新资格，时间窗口边界和持续期限由原生内存定时器唤醒；每条规则只保留最近一个待到期时间。动作发送前重新检查当前条件和触发所处的连续阶段：中途转为假或未知后再次恢复，不继承旧触发的执行资格。独立事件保留自己的身份，不因相同属性值或较旧的属性序号被合并丢弃。

每次内存求值同步完成后更新该规则状态，下一次输入直接使用更新后的状态；求值过程中不等待数据库、设备或模型。Agent 决策登记与定义修改共用一个串行写入队列，待保存操作合计最多接纳 256 项，超限或保存失败时丢弃本次决策。内存动作执行器最多接纳 256 项尚未完成整次执行的动作，整次接纳或拒绝，不只发送其中一部分；超限取消本次动作。执行结果由独立日志队列串行保存，最多接纳 256 次执行记录，超限或保存失败只丢记录。冷却从本次命中开始计算，接纳或保存失败均不恢复旧条件、不重新触发。

动作和模型任务只尝试一次，失败后结束，不退避、不重新入队。内存动作队列有可用执行位置时立即派发，无数据库通知或轮询等待；模型和AI 判断任务提交后由数据库通知唤醒，每秒检查一次待执行任务，这些检查不重试失败任务。启动、家庭切换、修改或重新启用规则时重建当前基线；持续计时和冷却不跨运行期恢复。停用、删除、切换家庭及关闭服务均清除对应内存定时器。

属性类型从设备规格派生，Web、Agent 和 backend 共用约束：

| 类型 | 运算符与输入                             |
| ---- | ---------------------------------------- |
| 布尔 | 是、不是；开／关选择                     |
| 枚举 | 等于、不等于、属于、不属于；规格选项     |
| 数值 | 等于、不等于、大小比较、区间；数字及单位 |
| 文本 | 等于、不等于、包含、不包含；文本输入     |

`value_list` 优先作为枚举，即使底层编码是整数也不提供大小比较；人数等整数数量仍按数值处理。写入设备属性和调用动作还校验格式、整数范围、枚举、范围、步长及参数顺序。未知格式不会推测为可用条件。每棵树最多 128 个节点、12 层，每组最多 32 个子节点、每条规则最多 16 项动作。

## 动作与 Agent 决策

动作支持写入米家属性、调用设备动作和网页通知。当前网页通知的成功表示内容已保存到自动化执行记录，可在该页面查看；没有系统推送、音箱播放或实际已读保证。设备控制的 `accepted` 只表示供应商接纳，实际效果仍未确认；拒绝、未知、取消与成功分别展示，设备结果不会直接写成新的当前事实。

规则默认执行配置好的动作，也可配置 Agent 决策目标。此时 backend 冻结本次触发和事实，可靠登记请求；Agent 只能返回已配置动作 ID 的子集，可选择不执行，不能修改设备、参数、通知内容或扩大动作范围。执行快照保留规则引用的全部已有设备事实；决策请求超过 256 KiB 时在占用家庭模型额度前跳过，Agent 模型上下文超过 `AGENT_CONTEXT_BYTES` 时也跳过，并保存原因，不截断事实或调用模型。模型完成、backend 接纳结果和设备动作完成分别记录。AI 条件可以直接搭配固定动作，不必再调用一次模型选择动作。

动作从内存队列领取及实际发送前核对家庭、规则版本、启停、当前条件、触发连续性、启动期限及设备资格；这些检查不读取数据库。修改、停用、删除和家庭切换撤销旧资格；已发出的请求不重发，结果尽力保存。控制请求不自动重试、不跟随 HTTP 重定向；发送后超时或进程中断不能证明设备未执行。取得未知结果时尽力保存，进程中断可能没有记录，均停止重发。

自动化动作共用一个并发上限为四的内存队列，通知也计入此上限。逐设备串行由米家控制模块统一负责；同设备等待会占用执行位置，繁忙时其他动作可能等到过期后丢弃。同一条规则中发往不同设备的动作可并行，动作列表不表达跨设备的先后依赖。全部动作结束后在内存汇总结果，再异步批量保存；后续控制不等待日志写入。模型决策结果仍先完成接纳事务，所选动作随后使用同一个内存执行入口，不再登记设备动作数据库任务。

Agent 请求使用稳定 `request_id`，每次执行只提交一次。忙碌或明确拒绝记为失败；超时、断连或响应无效记为未知，本次执行结束，不重投、不轮询回执。Agent 以现有 PostgreSQL checkpointer（执行状态存储）保存开始与结果，防止相同请求重复调用模型。当前自动化决策与情景复核共用家庭每小时最多 20 次模型请求登记、Agent 一个在途执行；自然语言草稿生成和聊天有各自限制，这不是所有 Agent 调用的统一费用账本。具体模型接口与上下文上限见 [Agent README](../apps/agent/README.md#自动化复核与动作选择)。

聊天工具按设备或关键词分页查询能力，按名称分页查询规则摘要，再按 ID 获取完整定义；单页最多 20 项且不超过 8 KiB。执行记录返回简要状态，生成草稿和保存结果也受本轮剩余上下文限制；完整定义无法读取时须在网页编辑，不能根据摘要覆盖规则。聊天可生成草稿，并按用户明确要求保存或删除。聊天保存仅允许 `enabled=false`；修改已有规则也会保存为停用草稿，须在网页核对启用。生成本身不保存、不启用，工具不能绕过 backend 校验。

## AI 判断条件

AI 判断是规则树中的 `kind=ai` 条件，可作为触发或状态节点，与设备属性、时间条件一起参与 AND、OR、NOT。新增条件时填写目标、选择 1—50 个参考设备属性并设置至少 5 分钟的检查间隔；高级设置包含判断有效期、过去 24 小时调用上限（最多 48 次）和是否在证据不变时重新判断。默认间隔 15 分钟、有效期 30 分钟、每天最多 12 次。共享家庭每小时模型调用额度继续生效。

配置只保存在所属规则的节点中；规则保存时在同一事务里更新节点的调度状态，修改、停用或删除规则会撤销旧判断及在途请求。删除条件会删除它的调度与历史；规则编辑会保留仍存在节点的历史，但当前判断重新从未知开始。没有独立维护配置或跨规则共享判断。

Graphile Worker 每分钟扫描到期条件，繁忙时等待当前模型任务结束。每轮先推进下次检查时间，再冻结选定属性、检查有效原始证据、证据变化和额度。默认相同证据不重复调用模型；结果过期后保持未知，直到新证据产生有效判断。需要定期重新判断相同证据时，启用「证据不变也重新判断」。每项最多一个在途执行，遇忙跳过本轮；失败直接结束，后续周期继续，不重试、不补跑。重启清空当前判断，已登记的相同证据仍受去重限制。请求与结果接纳期限为两分钟，单次网络等待最多一分钟。

模型返回成立、不成立或未知，以及说明和支持证据身份。明确判断必须引用至少一项具备资格的实时设备证据；backend 核对引用、事实含义、连续性、来源资格和期限。结果有效期从本轮采集证据时起计算；证据变化、结果过期或一次实际调用失败会使当前判断变为未知，不沿用旧结论。设备属性上报不会直接调用模型，但会使不再适用的旧判断失效。当前 AI 条件只读取选定属性，没有媒体、身份或完整活动历史。

「开始满足」在未知或不成立变为明确成立时触发；持续成立不会重复触发。「不再满足」只在明确成立变为明确不成立时触发，过期与失败不算不成立。「持续满足」要求判断在有效期内连续成立；状态节点只参与条件判断，不单独发起动作。重启及修改规则本身不执行动作，之后新取得的明确成立判断可以触发。AI 条件直接更新规则树，不生成中转的家庭事件；它自身不控制设备，动作仍由规则树整体判断决定。

规则的「触发与条件日志」包含 AI 条件判断历史，包括跳过原因、成立／不成立／未知及判断说明。编辑器的节点预览不会调用模型，未保存草稿中的 AI 条件显示未知。

## 保存、恢复与接口

定义使用稳定 ID 和预期版本，重复的相同保存返回已有结果，内容冲突要求刷新。规则的保存、删除操作先撤销内存执行资格；写入失败或提交结果不明时保持暂停，不做事务补偿。刷新页面核对数据库中的配置后，再次明确保存才能恢复当前进程中的执行资格；已发出的设备请求不能撤回。当前家庭约束贯穿读写和执行。设备能力消失后编辑器保留原条件引用和值，仍可保存停用定义；启用时重新校验。家庭切换清理旧家庭的自动化、AI 条件、事件、模型请求及动作记录，旧任务不能取得新家庭资格。

独立事件按事件 ID 及生产者的来源 ID 去重，同一身份内容不同拒绝。首次事件接纳提交成功后，只向当前内存规则引擎通知一次；事件提交后进程停止可能丢失这次触发，不从数据库重放。固定动作的设备证据、执行记录和动作结果在控制结束后一起尽力保存；Agent 决策请求仍与触发证据在同一事务中登记。重启丢弃内存中的动作，不补跑；取消未完成的决策，已接纳决策但缺少动作结果的执行标为未知。固定动作在中断前未保存的记录无法恢复。随后重建当前基线，只处理新输入。规则初始化或家庭恢复读取失败时保持暂停，每分钟重新读取配置；成功后建立新基线，故障期间的输入直接丢弃。事件记录仍可查询，但不会据此补跑旧触发。属性求值、队列接纳或任务执行失败可能丢失本次工作，结果保存失败可能只丢失记录；不保证零漏报、完整日志或设备恰好执行一次。

HTTP 均为本机 JSON POST，携带当前 `scope_epoch`：

| 前缀与操作                                                   | 用途                             |
| ------------------------------------------------------------ | -------------------------------- |
| `/api/household/automations/{list,capabilities,save,delete}` | 规则定义与当前能力               |
| `/api/household/automations/{query,read,capabilities/query}` | 聊天分页查询和单条完整定义       |
| `/api/household/automations/{evaluate,runs,generate}`        | 节点求值、执行记录、自然语言草稿 |
| `/api/household/automations/reviews/runs`                    | 按所属规则查询 AI 判断历史       |

事件写入仅供可信 backend 生产者调用，没有任意 HTTP 写入入口。当前没有已接入的家庭事件生产者，米家独立设备事件 `siid/eiid` 尚未接入；规格中列出事件不能当作可用触发来源。

共享定义位于 `packages/api/src/contracts/{automations,automation-reviews,household-events}.ts`，纯规则语义位于 `packages/api/src/domain/automations.ts`，设备值类型与校验由 `packages/api/src/domain/devices.ts` 统一提供。backend 的 `household/automations/` 拥有定义、求值、决策和调度，`automations/reviews/` 拥有 AI 条件调度、判断结果和历史，`household/events/` 拥有事件身份与接纳，`household/automations/actions.ts` 拥有内存动作队列、发送与异步结果保存，`execution.ts` 组织执行快照与结果汇总，`mijia/control/` 适配设备控制；它们不拥有 Agent 的持续工作和问询状态。

条件状态只保存在内存中，执行证据直接保存在 `automation_runs`，没有单独的输入队列或状态表。执行历史每分钟独立清理一次，启动期限已过的记录按每条规则最近 1,000 条且不超过七天的限制清理，包括日志写入失败或队列满后遗留的待完成记录；仍在启动期限内的记录保留。日志失败直接丢弃，不补写、不重试，也不为清理补造执行结果；清理不占用属性求值路径。事件保存上限为每家庭 50,000 条，满后拒绝新事件；AI 判断终态历史保留七天，过期的未完成复核在下个正常周期终结。模型请求另有有界清理，当前页面用于查询运行结果，不作为永久审计或完整设备历史。

## 验证范围与限制

类型和构建检查不能代替真实来源与输出验收。模型生成效果、动作决策与复核效果、真实设备写入、供应商结果确认，以及内存定时、失败丢弃和重启基线行为仍需按场景验收。音箱输出、回答关联、语音身份、设备独立事件、语义事件纠正与撤回、跨来源情景生命周期和 Agent 持续调查／主动问询尚未交付，不能从现有规则树或周期复核推导这些能力。
