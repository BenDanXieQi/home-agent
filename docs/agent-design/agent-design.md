Agent体系应该会有一个不间断运行的Loop，这个Loop会不停接收比较全量的、压缩后的家庭情景上下文。自主决策后，如果觉得某个方向、某个地方需要做出Action，或者说完成某个任务，就会发起一个独立会话。

或者通过一些固定的事件触发类型工具，也有可能触发这类会话。事件触发类型的工具应该在Backend里面得到确定性定义，比如摄像头捕获到一些家庭成员的画面，或者是门窗传感器之类检测到了开关状态的变化。
这些固定事件触发器，是用户在Web界面上通过预制的排版工具编排得到的，或者可以由Agent根据固定的Workflow通过用户描述的自然语言生成。

这个会话会有比较独立、更小的上下文，包含这个会话目的所需要的家庭设备、感知和执行；其他内容就从完整的家庭情景上下文里过滤出去。
在最早期的实现里，这个会话涉及的设备和成员决定下来之后，就会由预制的裁切utils把所需的上下文裁切出来，包括感知和执行。
后面可以把这个裁切工具通用化，然后封装成一个Agenct层面用的Tools，让模型自己决定裁切哪些东西。但是，这个效果需要完整的评估流程去验证。

数字世界中工作的Agent，它的决策通过Tools影响所处环境之后，往往能很快地进行自我验证，能够在reAct循环里，通过逐步验证和思考的过程，比较精确、可靠地达成任务的目的。
工作在物理世界的Agent，它的Tools能造成的影响极为有限（具身智能真正出现之前），从决策发出，到Tools执行，再到物理世界的环境真正受到影响，这个过程可能会很漫长。还有很多情况，它需要寻求人类的帮助，或者说人类的反馈，才能真正影响到物理世界。

举个例子，比如检测到室内二氧化碳浓度、温度或者异常气味过高，再执行对应设备，打开空调也好，打开空气净化器也好，它得到的反馈往往是持续性的、渐进式地逼近目标，而不是一次性获得结果。环境传感器里的这些数据会每秒钟不停变更，再趋近目标，也未必能达到想要的目标。

第二个例子：如果它监测到某个危险的物理开关，比如一个门没有关，大多数情况下，物理世界里并没有能够执行设备完成关门这个动作。它需要找到人类在的地方，如果人不在家里，它甚至得通过一些通信方式和人类取得联系并且得到明确的反馈，等待人类完成关门动作，或者反馈需要进一步等待人类完成，或者采用其他处理方式。

这并不意味着物理世界中工作的Agent需要不同于reAct的全新执行方式，但可能意味着，每一个工作会话都需要在异步等待、需要在 Human in Loop 流程里、需要在任务目标完成定义、需要在持续追踪所需环境上下文、需要在多Agent沟通反馈方式 等等方面，做出有别与数字世界工作的Agent的处理。
