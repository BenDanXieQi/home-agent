# 设备事实与房间快照

家庭运行时进入 `running` 后，`household/collection.ts` 观察当前家庭全部可订阅设备。采集不依赖页面、Agent 或诊断录制；设备加入、移除与规格变化会调整观察范围。米家适配器复用账号已有 MQTT 连接，协议重连、续期和订阅重试仍由米家模块管理。

`household/observations.ts` 使用普通领域函数校验、计算和接纳观测，家庭 XState 实例是当前值的唯一维护者。每次输入原子提交后，页面接收 SSE。`subscribeFacts` 在有事实处理结果或状态变化时交付同次提交的 `state_version`、`changes` 和 `result`，包括同值报告的处理及过期、断连等状态变化；这些字段来自内存，不另行写入数据库。`history` 报告数组交付已接纳属性上报、读取、在线通知及设备清单在线值，没有报告时为 null：普通上报含一条报告，设备清单一次交付全部在线报告，由独立消费者保存设备状态历史。设备清单的状态变化先随状态机提交通知，后续历史报告通知的 `changes` 为空、`result` 为 null，避免重复交付状态变化或混入其他报告的处理结果。回调应立即返回，不建立持久事件队列。

## 当前值、来源与时间

`latest` 使用账号、设备、`siid/piid` 作为键；名称、单位和可读能力来自已加载 MIoT 规格。规格声明的属性先建立缺值条目，额外合法上报也可在预算内保留，不能通过页面筛选缩减接收范围。

| 字段                                         | 含义                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| `has_value/value`                            | 缺值与设备报告的 false、0、null 分开                                        |
| `evidence`                                   | 观测 ID、处理序号、来源与连接代次、接收／来源时间、交付性质、规格和策略版本 |
| `reason`                                     | 缺值、缓存、断连、过期、规格等具体原因；`current` 表示符合本机使用策略      |
| `applied_at/expires_at`                      | 采纳时间和配置的有效期；计时实际使用进程单调时钟                            |
| `last_report_at/last_change_at/last_read_at` | 最后上报、可信变化与成功读取时间，首次值不算变化                            |
| `read_candidate`                             | 最多一份无法证明比当前值更新的云缓存，不覆盖当前值或延长有效期              |

设备报告保留值、来源、时间、规格及 `reason`，不另设质量等级。`reason=current` 只表示符合本机配置的使用条件，不证明物理状态真实正确；缓存、断连、过期等原因分别表达。原观测的来源与时间保存在 `evidence`，不随当前状态变化改写。

首次上报、恢复基线和缓存不作为可信变化。前值仍符合使用策略且未到期，新的可信实时报告在同一连续连接中出现不同值时，才更新 `last_change_at`。同值更新接收时间与适用有效期，不能按值去重。已被识别为重放、交付性质未知、已有值后的基线或更早观测的报告不改变当前事实，即使其值不符合规格，也只记录拒收。可影响当前事实的实时上报与规格冲突时，不裁剪成合法值，并使原条件失效；读取返回非法值只报告失败，不影响已有推送值。未知规格可以显示原值，不满足有效当前值条件。

断连、订阅失效、明确离线和观测缺口更新相关属性的具体原因，使旧报告不再符合当前使用条件。连接恢复或 SUBACK 不刷新旧值，后续报告重新建立比较起点。到期检查排在此前已收到的观测之后；积压中已经超过有效期的报告不能重新成为有效当前值。UTC 用于展示，处理序号与单调计时不依赖系统时间先后；检测到系统时间跳变会标记缺口。

设备在线状态统一使用 `online`：当轮完整设备清单建立初值，当前来源的合法实时上线／离线通知直接更新，不按型号验证名单过滤。清单准备提交后收到的合法实时通知优先于该轮清单，等待数据库保存不能使在线状态回退；相同值通知和多次上下线往返也按接纳顺序处理。清单刷新确认离线或收到离线通知时，旧推送属性不再符合当前使用条件；上线只恢复在线标志，属性仍须等待新报告。MQTT 断连与订阅失败由 `source_health` 和 `device_coverage` 表达，不改写最近获知的设备在线标志；断连仍使旧推送属性不再符合当前使用条件。MQTT 每次连接成功后，现有设备清单通知通路在最后一次通知或连接事件的五秒后触发完整刷新，修正断连期间遗漏的在线变化。属性读值和摄像头连接不推导设备在线。独立 `siid/eiid` 事件没有接入。

## 本机策略

可选文件为仓库根下 `config/collection.json`，最多 256 KiB，启动时严格校验并计算内容版本；修改后重启 backend。文件缺失时仍接收全部合法上报，并默认补读原生规格声明为可读的属性；不推断有效期，收到值后保持待确认。文件非法则启动失败，不静默忽略。

```json
{
  "properties": [
    {
      "model": "cgllc.airm.cgd1st",
      "spec_id": null,
      "siid": 3,
      "piid": 7,
      "read": true,
      "verified_push": true,
      "freshness": { "mode": "ttl", "max_age_ms": 60000 }
    }
  ]
}
```

示例表达“温度最多沿用接收后的 60 秒”，不是已经核实该设备每分钟上报的证明。配置前应核对实际型号、属性和来源契约；精确 `spec_id` 优先，null 表示按型号匹配。规格中的类型、单位和读写能力不重复配置。最多 2,000 条策略，不允许相同目标重复定义。

`freshness.mode` 可为 `unknown`、`ttl` 或 `change`。`ttl` 的期限为 1 秒至 24 小时；`change` 只适用于已验证初值、变化通知及恢复语义的来源，维持到明确缺口。后两者都要求 `verified_push=true`，该声明是部署配置依据，不是系统自动认证的结论。`read` 仅控制自动补读：默认启用，可用 `read=false` 排除特定属性，用户仍可显式请求原生可读属性。

初始化先建立订阅，确认后自动分批读取缺值／待确认的可读属性；规格较晚就绪也会补上，不依赖页面打开或手动点击。每批最多 50 项，上一批完成后继续余下属性，预算满时等待空位，不因全家庭属性超过 100 项而放弃剩余项。单项失败保留缺值及诊断原因，不阻塞其余批次。

恢复连接或手动重试采集也可触发一轮补读。清单刷新和实时通知确认设备由离线恢复在线时，均重新建立补读轮次；同一连接内短暂的离线／上线不会因调度合并而遗漏。同属性在途请求合并，同轮订阅不会反复补读；没有周期属性轮询。当前米家读取属于时间未知的云缓存：无值时建立待确认初值，已有值时只更新候选。设备报告离线时暂缓读取；失败不自动重发。读取不会执行设备动作，缓存缺失时供应商可能转为设备 RPC，仍不保证每个可读属性都能成功返回。

## 接口与页面

所有接口沿用米家本机访问限制；运行命令核验 `scope_epoch`，退出或访问撤销后旧任务不能回写。

| 接口                               | 输入与结果                                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/mijia/state`、`/events`  | 公共状态新增 `latest`、`device_coverage`、`source_health` 和 `collection`                                                                             |
| `POST /api/mijia/facts/query`      | 只读；`room_id`（null 为未分配房间）、可选 `device_ids`、`properties: [{ did, siid, piid }]`、`limit`、`offset`；返回同一提交版本的房间资料与覆盖信息 |
| `POST /api/mijia/properties/read`  | `{ scope_epoch, properties: [{ did, siid, piid }] }`，最多 100 项；逐项返回 applied／candidate／unchanged／failed、具体原因和最终状态版本             |
| `POST /api/mijia/collection/retry` | `{ scope_epoch }`，恢复采集暂停、重试可恢复订阅失败并重新补读，不绕过供应商永久拒绝                                                                   |
| `GET /api/mijia/diagnostics`       | 包含观测队列、活动观察、在途读取和有界异常摘要                                                                                                        |

房间查询不触发云读取，默认 500 项、最多 2,000 项，设备或指定属性筛选各最多 100 项；明确返回缺值、请求中不存在或不在所选房间的属性、未确认订阅、规格不足、裁减及下一页位置。它不保存第二份设备值，也不输出人物身份、睡眠或动作许可。

设备页 `/devices` 从 SSE 快照派生设备最近报告，按房间切换范围，支持搜索、分类、能力与在线状态筛选。默认显示全部设备，未收到属性值的设备仍保留。列表以“最近报告”展示属性，过期值明确标记；完整来源与具体原因在悬停提示和展开详情中展示，云端缓存不冒充实时状态。展开设备详情可查看全部属性、缺值项、缓存候选、上报／读取／变化时间与一次性读取入口。家庭采集诊断集中在设备页底部。

读取按钮只发一次请求，结果不回填页面事实，以后台订阅为准。更换房间或退出页面取消等待，旧响应不显示到新房间。

## 资源与验证边界

当前值连同候选最多 20,000 项或 2 MiB；单值 16 KiB，MQTT 消息 256 KiB。观测队列最多 2,048 条或 4 MiB，每轮最多处理 128 条后让出执行。持续过载在一分钟内发生三次即暂停，需要手动恢复；丢弃前积压并标明缺口，旧报告不能重新建立错误连续性。

读取最多 100 个待处理属性、4 个应用在途批次，每批最多 50 项，供应商请求仍经过已有串行预算。自动补读只推进一批，余下属性在设备清单中等待；单项进入读取队列后最多 35 秒。共用批次中的某个调用者取消不会取消其他仍需要的属性，全部取消才终止该来源请求。异常摘要最多 100 条或 256 KiB，不保存完整非法载荷。容量不足、失败和缺口通过公共状态或诊断报告，不阻塞其他正常来源或使诊断录制成为采集前置条件。

断线、到期、过载、换房、移除和撤销分支尚未完成实机故障验收；不能据正常上报推定这些边界已经验证。未覆盖范围包括：订阅失败与恢复不延长旧值期限；读取期间的新推送不被迟到缓存覆盖，单项失败保留可信值，共用批次取消不影响其他调用者；同值续报、可信变化、首次值与恢复基线语义分开，已收到积压先于到期判断处理；设备与访问变化回收资源并拒绝旧回调；持续过载暂停、丢失范围及手动恢复可见，慢页面不造成无限积压。条数、字节和处理预算仍须按实际消息量校准。独立设备事件及更多型号的在线语义仍受[米家来源契约](mijia.md)约束。

设备采集接纳的属性、读取候选与在线报告另由独立历史通路比较，只把首次值及值或属性说明变化保存到数据库；合法设备清单读到的在线值遵循同一规则，连续同值不新增历史记录；其说明固定、保留、查询和验证限制见[设备状态历史](../household-runtime.md#设备状态历史)。历史保存不改变上述当前值及其使用条件。
