# 家庭记录与 Agent 工作存储设计

**状态：待实施设计。** 本文唯一维护家庭记录、工作恢复和动作所需的数据结构、约束、事务及清理。字段按[主交付顺序](household-automation.md#实施顺序与改动位置)随实际消费者增加，不一次建立所有表；首批只读查询可直接复用现有结构。

语义见[信息边界与状态归属](household-model.md)，运行流程、接口用途与能力验收见[协作设计](household-automation.md)。下列新增结构不是当前数据库。业务表继续使用 PostgreSQL；backend 由 Drizzle 管理，Agent 使用现有 `pg` 和 `agent_state`。官方检查点表及队列表由相应库管理，不通过其内部字段推导领域状态。

## 现有数据与复用

[当前 schema](../../apps/backend/src/db/schema.ts)已有 `household_subjects`、`context_records`、`context_entities`、`identity_members`、`identity_samples`，以及凭据、米家家庭选择与设备清单表。

`context_records` 已有 `id/kind/topic/summary/data/certainty/occurred_at/created_at/expires_at/evidence/scope_epoch`，`kind` 为 `observation/assessment`；实体关联由 `context_entities` 保存。当前主要生产者是[成员出现写入者](../../apps/backend/src/household/identity/activity-repository.ts)：按 `data.attribution.revision` 拒绝旧修订、原地更新记录，并在同一事务替换当前主体关联。`occurred_at` 固定为首次观察，最后观察在 `data.lastObservedAt`；归因变更不得改写原始身份。

A 批次只为实际查询增加必要索引和业务投影，不创建工作或模型账本。成员最近出现按经过 schema 校验的 `data.lastObservedAt` 排序；可用主题限定的表达式索引，不另维护当前位置表。已有设备状态在内存，窗口文字和媒体也不能因新增查询而变成持久记录。

以下字段中的时间统一为 UTC 时间戳；用户时区另存。UUID 由首次请求生成并在重试中复用；HTTP 中的数据库大整数使用十进制字符串。JSON 内容按具体主题或命令的共享 schema 校验，不能让调用者提交任意可执行对象。类型从 schema 和实现推导，不另复制类型定义。

## 本地家庭与来源绑定

B 批次新增单例 `home_config`，由 backend 家庭配置唯一写入。保存 `home_id`、`status(active/resetting)`、`revision`、显示时区，以及可空的 `reset_request_id/reset_phase`。配置命令核对预期修订，重置请求身份唯一；Agent 接纳与查询响应必须核对稳定 `home_id`。C 批次再增加 `change_seq/replay_floor`，供记录提交与清理维护。

Agent 同批增加单例 `agent_state.home_scope`，由本应用生命周期入口写入，保存 `home_id/status(active/closed)/last_reset_request_id/last_closed_home_id`，供输入接纳、调度与重置回执查询。它只保存 backend 已确认的归属与本应用关闭结果，不创建家庭或拥有来源绑定。关闭回执与本应用清理同事务提交；新家庭须经 backend 激活交接后才能接纳工作，保留最近重置身份使丢失回执可重查，过时家庭请求始终拒绝。

现有 `mijia_home_selections` 扩展 `local_home_id` 和 `binding_id`。米家账号、米家家庭编号继续表示外部来源，新的明确绑定生成新的 `binding_id`；普通重启不更换。来源资料由现有模块拥有，不新增一份可独立修改的设备清单。历史记录保存原绑定标识，不以级联删除使来源退出顺带删除家庭历史。

本地成员继续使用现有资料和身份表，迁移时赋予所属 `home_id`；识别样本、参考资格及本地纠正沿用现有所有者。历史主体引用不要求物理外键指向始终存在的成员行；删除成员后保留历史的原名称与依据，不能自动关联到以后同名成员。

来源解绑撤销新读取和新动作；本地报告与工作继续存在，来源记录按其授权范围查询。家庭重置将 `status` 置为 `resetting` 后拒绝新工作与派发，使用同一个重置请求与 Agent 交接。Agent 在本地事务记录旧家庭已关闭、取消本应用待办并清理所属数据，再返回回执；backend 重试查询／交付同一请求，确认后清理自己的记录与媒体、生成新家庭身份。旧家庭关闭回执保留至 backend 确认完成，不能先删除恢复所需身份。

切换来源与明确重置的界面、访问门禁、会话归属及历史查询必须一起迁移。单独加 `home_id` 字段不构成生命周期交付。

## 家庭记录与实体关联

B 批次扩展 `context_records`，继续使用同一逻辑记录 ID；成员出现的领域规则保持不变，新增用户确认报告生产者。公共投影只表达真实已接纳的信息。

| 新增字段                                   | 约束、写入者与消费者                                                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `home_id`                                  | 所属本地家庭；由 backend 接纳入口确定，不接受模型选择其他家庭                                                                                                   |
| `source_kind/source_key/source_binding_id` | 来源种类及输入身份，绑定可空；唯一键 `(home_id,source_kind,source_key)`，用户报告用稳定请求身份，成员出现复用现有记录身份                                       |
| `revision`                                 | 非负内容修订；未撤回记录同身份同修订同内容返回已有结果，冲突拒绝；成员出现与 `data.attribution.revision` 同事务保持一致。撤回不增加内容修订，按下述终态规则接纳 |
| `updated_at/withdrawn_at`                  | 保存修订时间及可空的撤回时间；撤回是不可重新启用的终态，保留 ID、来源唯一键与最后内容修订供查询和拒绝重交                                                       |

`summary/data/evidence/certainty` 沿用现有字段；修订、实体关联和本主题的时间字段一起提交。成员归因变为 unknown 不删除来源观察，也不等于整条记录被撤回；当前主体关联由身份领域更新。`context_entities` 继续区分来源与主体；查询必须取当前关联，历史解释通过实际输入快照保留。

用户报告使用新主题 `user_report`，由报告接纳入口写入 `kind=observation`。`data` 保存原文、报告者或未知、会话输入身份、用户确认的 `observed_from/observed_to`、时间解释依据及显示时区；本批次只接纳时间已明确的报告，歧义留在待澄清工作输入中。`occurred_at` 取确认的开始时间，不能用请求到达时间代替。用户更正原报告时须指向原 ID 和预期修订；不同来源报告可能涉及同一活动，不自动合并或计数。

记录撤回由 backend 记录领域接纳并锁定原记录，核对预期内容修订后设置 `withdrawn_at`，保存撤回原因；不修改身份领域的归因版本。此后所有生产者先按记录 ID 与来源唯一键核对撤回状态，再解析正文或接纳修订：旧输入重交只返回已撤回的原身份，更高归因版本或更换记录 ID 也不能恢复同一来源输入。新的实际观察使用新的来源身份，不能借新编号重放旧材料。普通查询排除已撤回记录，按编号查询返回撤回状态与最后内容修订；派发核验同时检查修订和未撤回资格。

查询索引包括 `(home_id,topic,occurred_at,id)`、来源唯一键、现有实体反查索引及成员出现的最后观察索引。游标绑定家庭、筛选和排序；普通列表不冻结跨页数据库快照，响应明确期间可能有修订，不能当作连续变更消费。摘要只返回任务所需字段，详情仍受响应上限；记录过大返回限制及可读取部分的明确说明，不把截断数据称为完整证据。

## 记录变更与提交一致性

C 批次新增 `record_changes`，唯一生产者是各记录写入事务的共同提交边界，消费者是 Agent 变更读取器。不是所有遥测都写入此表。

| 字段                       | 用途与约束                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `home_id/seq`              | 联合主键，家庭内已提交变化顺序                                                                                       |
| `record_id/revision/op`    | 内容修订及 `created/revised/withdrawn`，唯一 `(home_id,record_id,revision,op)`；同一内容修订允许一条原变更和一条撤回 |
| `before_scope/after_scope` | 变更前后的主题、主体、来源与观察时间，足以匹配移入／移出范围的消费者                                                 |
| `summary/committed_at`     | 有界变化说明与登记时间，不充当完整旧版本记录                                                                         |

写入者先锁定 `home_config` 的变更序号行，再校验和更新记录、当前关联、直接依赖它的未派发动作及新的变化行，最后一起提交。序号在锁内递增；不直接用可能先分配后提交的独立 sequence 最大值作为安全消费位置。事务失败则记录与变化一起回滚；相同内容修订和操作重交不产生第二条变化。内容重交复用原操作，不允许换用 `created/revised` 在同一内容修订下再登记一次变化。撤回使用最后已接纳的内容修订与 `op=withdrawn`，独立取得新的 `seq`；例如修订 7 的 `revised` 与随后修订 7 的 `withdrawn` 分别提交。重复撤回返回原撤回结果，不另登记变化；记录已经撤回后不再允许 `created/revised`。

补读响应给出 `scanned_through`、当前已提交上界及 `replay_floor`。按完整提交区间扫描后再过滤；即使没有命中也能推进扫描位置，不漏过稍后提交的低序号。变化行只保证发生过该修订，需要该时刻全部内容的工作必须已保存输入快照；补查发现记录已更新时返回当前修订及差异，不伪造旧版详情。

清理只移除连续前缀，在同一锁下推进 `replay_floor`；不在可补读区间内部掏洞。请求低于下界或属于其他家庭明确失败。长期保留单条记录不扩展变化流的连续保留范围。

## Agent 工作与输入

B 批次新增 `agent_state.works` 和 `work_inputs`，分别保存职责与可靠接纳的输入；唯一写入者为 Agent 工作应用层，页面和调度处理器读取。工作是持续责任，输入是促成某次推进的材料，两者都不是聊天检查点。

| 表            | 必要字段与约束                                                                                                                                                                                                                                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `works`       | `id/home_id/kind/revision/status/instruction/subject_refs/policy/state/next_wake_at/deadline/created_at/updated_at`；`kind` 首批仅 `reminder`，之后按实际交付增加 `investigation`；状态为设置中、待澄清、启用、等待、修改中、暂停、完成、取消或失败 |
| `work_inputs` | `home_id/input_id/work_id/kind/payload_hash/payload/accepted_at/run_id/processed_at`；唯一 `(home_id,input_id)`，同身份不同内容拒绝；已接纳内容不可覆盖，处理状态可推进，`run_id` 在分配执行前为空                                                  |

工作 `policy` 保存认可的来源、通知目标、频率、期限及本职责每小时／每日模型调用与 token 上限；模型不能自行增权。`state` 按 `kind` 校验：提醒保存报告 ID／修订、确认时间锚点、间隔、时区、稳定 `reminder_slot_id` 及执行许可；调查保存问题、等待条件、已处理输入及未决问题的有限集合。调查没有全局活动、人数或通行状态。初次职责仅触发一次提醒，新一轮须有明确用户操作或另行交付的重复策略。

先持久接纳用户输入并安排恢复 job，再调用 backend 保存报告；使用输入 ID 作为报告接纳身份。拿到报告和许可后，在 Agent 事务核对工作修订、保存配置并登记到期 job，才启用工作。跨服务失败停留在设置中，恢复继续同一输入；不能只因聊天说“好的”就认定任务已生效。

提醒修订不改变已有 `reminder_slot_id`。改期先持久登记修改意图和交接 job，撤销旧执行许可并等待 backend 回执，再提交新状态和新许可；交接未完成显示修改中。暂停、取消先走相同撤销边界，已派发结果仍保留。过期 job 醒来核对工作修订，不能覆盖新期限或再次执行旧提醒。

索引包括 `(home_id,status,next_wake_at)`、待处理输入索引和 JSON 中实际使用的报告引用索引。事务锁工作行，接纳输入、更新进度、安排下一次唤醒一起提交。网络调用不持数据库锁，跨服务用稳定身份和预期修订恢复。同一输入接纳成功不表示工作已完成。

### 变更消费

C 批次新增 `agent_state.record_change_cursor`，每个家庭固定消费者一行，保存 `scanned_through`、缺口状态、注册交接身份及期限。它由变更消费者唯一推进，不由工作自行跳到最新位置。

正常接纳在一个 Agent 事务内锁游标、读取当前工作过滤条件、插入唯一输入、标记直接引用记录的笔记待复核、登记推进 job，再更新游标。输入身份由家庭、变更序号和目标工作确定；记录从原成员移出时仍按 `before_scope` 命中原工作。再次交付同页不新建运行。

首次启用“从现在开始”的调查时，先在该游标行登记有期限的注册屏障，消费者暂停推进但不持跨网络锁；向 backend 取得已提交上界 `W` 和服务端时间。在 Agent 事务保存工作 `start_seq=W/effective_at`、过滤条件和唤醒，再释放屏障；消费者不跳过原积压，只向新工作交付 `seq>W`。交接超时则取消本次启用，旧响应不能激活。最初不支持热修改活跃调查的过滤范围，须暂停后以新注册边界恢复；这项限制须在界面说明。

注册后到达但观察时间早于 `effective_at` 的材料属于历史补充。消费越界时，先在 Agent 本地事务记录缺口，将依赖完整消费的工作置为修改中、递增工作修订并阻止新的动作请求，标记相关笔记待复核，同时保存受影响工作已登记及登记中的许可请求键和撤销交接 job。许可请求键在外发前已保存，因此尚未取得登记回执的许可也须撤销；不能只检查已返回的动作列表。

交接使用原请求身份向 backend 撤销这些许可。backend 在许可与动作的共同锁边界内登记撤销、阻止其待派发动作并递增动作修订，返回可重查的撤销回执及已有动作结果。Agent 取得全部撤销回执后才确认自动派发已停止；交接未完成保持修改中，并显示仍可能产生效果。派发先提交的动作保留已派发或未知结果，不能宣称撤回。重启继续同一次交接，不能以本地暂停或推进消费位置代替 backend 回执。

完成撤销后，再查询当前依赖、记录无法恢复的部分并重新登记消费边界。只有职责不再要求不可恢复的历史完整性、当前依据及授权重新核验通过时，才可按新工作修订取得新许可并恢复；旧许可不重新激活。不能把新边界写回后声称已消费缺失历史；不依赖完整变更消费的有限提醒仍须在派发时核对当前报告。

## 材料与执行输入

A 的即时查询不增加持久媒体义务。C 的文字调查与 D 的可恢复媒体调查共用 `agent_state.work_runs` 和下节的 `work_model_calls`，由先交付的调查消费者引入；两者均依赖 B 的家庭身份、工作、输入及持久唤醒基础。D 另行新增 backend `evidence_materials`，不要求先启用 C 的记录变更消费者。两种保存分别承担“执行实际看过什么”和“承诺还能读取哪些字节”，不可互相替代。

| 表与所有者                                 | 必要字段与用途                                                                                                                                                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `work_runs`，Agent 执行应用层              | `id/home_id/work_id/work_revision/input_ids/status/started_at/finished_at/deadline/input_snapshots/result/error`；运行 ID 与选定输入同事务登记，重试复用原 ID；快照保存实际记录 ID、修订、正文摘要、查询时间、缺口和材料回执 |
| `evidence_materials`，backend 材料接纳模块 | `id/home_id/request_key/source_refs/description/representation/state/content_hash/storage_key/bytes/readable_until/submit_until/error`；请求键唯一，状态 `preparing/ready/missing/expired/revoked`；引用读取不能延长期限     |

创建运行时锁定工作行，选取尚未分配的输入，一起写入 `work_runs`、这些输入的 `run_id` 和恢复 job；恢复只按原运行 ID 读取，不能重新选择一批输入。运行状态为 `ready/running/completed/failed/cancelled`。等待用户或下一批材料时结束本轮执行并把等待条件交回工作，下次唤醒建立新一轮；已提交模型调用的未知结果单独留在调用记录中，迟到结果可存档但不能越过工作的新修订或原截止请求动作。

记录快照和已就绪材料描述不可改写。补查追加独立编号的快照，旧输入不变；每次模型调用保存它实际使用的快照编号。纯转写、帧事实、裁切图像、音频和视频分别声明表示及覆盖，不能把某个 URL 当成已交付字节。

材料接纳先预留有界容量、登记 `preparing` 和恢复 job，再从仍有资格的源读取、写临时文件，校验字节数和哈希后以原子文件替换完成落盘，最后更新数据库为 `ready`。数据库失败可按同一请求及哈希核对已落盘文件；无法恢复原输入则转 `missing`，不能使用新画面替换。启动时按登记核对自有文件，缺失 ready 文件标为 missing，未登记孤立文件回收。数据库提交不证明文件已经存在。

读媒体和向模型外发前分别检查家庭、来源资格和读取期限；撤权立即拒绝后续读取与提交，已交给外部模型的字节不能声称已收回。来源正常结束不把历史输入重新标为实时，也不延长原期限。提交截止与媒体读取截止分开，保存的文字输入可在媒体到期后解释历史，但不能重跑依赖已丢失字节的分析。

D 的初始工程边界为每次材料接纳最多 8 MiB、准备等待最多 60 秒、保留最多 30 分钟且不超过来源授权；全局另设 256 MiB 已接纳材料容量，不能挤占当前 P4 的短期缓存预算。这些是待验收的新增容量，不表示已有窗口可以跨重启恢复。接纳前必须确保工作可在读取期限内开始；排队不能保证时拒绝接纳媒体义务或明确降为文字任务。清理区分尚在期限内的承诺与可淘汰缓存，容量满拒绝新接纳。

## 可恢复模型调用与笔记

C/D 中先交付的有限调查增加 `agent_state.work_model_calls`，后续调查复用，唯一写入者为调查执行器；不为当前聊天、房间分析和语音判断预建迁移账本。

字段为 `call_id/run_id/ordinal/input_snapshot_ids/status/submitted_at/finished_at/result/usage/reserved_budget/error`，唯一 `(run_id,ordinal)`。每次调用输入固定后登记，状态区分 `prepared/submitted/completed/failed/uncertain`。提交前在同一 Agent 事务核对工作资格、原截止与额度、预留预算并写 submitted；网络在事务外执行。明确未发送的失败可按原身份重试，已经或可能发送但没有持久结果则转 uncertain，不自动再调用。SDK 自动重试关闭，应用重试计入原限额。

初始有限调查每次运行最多两次模型调用、总计 60 秒，补查和重试不刷新截止；输入快照总计最多 256 KiB 文字，媒体另受材料容量约束。每项工作每小时和每日自动调用额度保存在 `works.policy`，由用户或部署者启用时明确给出。小时按最近 60 分钟、日按该工作预算时区计算；预留锁工作行，汇总该工作窗口内的实际用量与未结算预留后核验，写入调用记录。配置修改须核对已有用量，结果未知保留预留额。调用数与 token 统计覆盖实际接入此路径的调用，不能显示为全服务总预算。调用提交还须取得[调查并发准入](household-automation.md#调查并发准入)的执行名额；预算合格不等于可以立即调用。运行创建时固化 `deadline`，包含排队时间，重新领取 job 不延长期限。底层在途请求未结束不释放并发名额，重启后的不确定调用不永久占据不存在的本机连接。

只有出现笔记复用消费者时才新增 `agent_state.notes`：`id/home_id/subject_refs/content/origin/record_refs/revision/status/updated_at/review_after`，状态为可参考、待复核、撤回。Agent 记忆模块唯一写入，调查查询读取；`record_refs` 保留实际记录与修订，按被引用记录建索引。修改带预期修订；直接依据被纠正或补读缺口无法核对时置待复核，使用前仍查当前材料。不保存完整统计支持集合、不承诺全部相关历史变化都能使经验自动重算；笔记不是动作授权或有效事实投影。

## 执行许可与动作

B 的通知闭环新增 backend `action_grants` 与 `action_executions`，由动作领域唯一写入，Agent 与页面只请求和查询。设备动作字段随具体设备适配交付，不预建通用规则表。

| 表                  | 必要字段与约束                                                                                                                                                                                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `action_grants`     | `id/home_id/work_id/work_revision/request_key/authorization_ref/allowed_effect/target/valid_from/valid_until/revoked_at`；最小执行许可，只保存派发核验信息；每个授权请求身份唯一                                                                                        |
| `action_executions` | `id/home_id/effect_key/grant_id/work_revision/kind/target/payload_hash/payload/basis_refs/input_snapshot/status/not_before/start_before/dispatched_at/result/created_at`；唯一 `(home_id,effect_key)`；状态含待派发、已派发、渠道接纳、确认、失败、阻止、取消、结果未知 |

许可身份在 Agent 保存交接意图时固定，重试沿用原 `request_key`，同键内容冲突拒绝。撤销先于登记到达时，backend 仍保存该请求键的撤销记录；迟到登记返回已撤销，不得创建可用许可。已经撤销的许可不能重新激活，恢复或改期使用经当前工作修订确认的新许可，原提醒效果身份保持不变。

`authorization_ref` 对应实际用户操作或已启用策略，不能仅是模型的一段解释。许可的 `valid_from/valid_until` 限定允许派发的时间区间，提醒的最早时间来自用户确认的到期时间。动作保存 `not_before/start_before`，接纳时核对 `valid_from <= not_before < start_before <= valid_until`；backend 派发事务独立核对当前时间已到 `not_before` 且未到 `start_before`，不能仅凭队列任务被领取或许可尚未过期发送。尚未到时按原身份重新安排唤醒，已过期则阻止派发。

提醒的效果键来自稳定提醒槽、通知用途、渠道及目标；同一槽改期不生成第二个键。动作记录另保存递增 `revision` 与有界的派发前变更摘要。普通动作接纳仍拒绝同键内容冲突；改期使用独立的修订命令，携带预期动作修订、新工作修订、新许可及新的时间、载荷和依据。backend 核对旧许可已撤销且该效果从未登记派发后，才允许将待派发或因旧许可撤销而阻止／取消的动作更新为待派发；在同一事务保存新许可引用、工作修订、派发时间及依据，递增动作修订并登记新派发 job。已派发、渠道接纳、确认或结果未知的效果不能通过改期重新启用，也不能覆写已派发载荷。修订命令重交返回原修订回执，同一预期修订的不同修改冲突拒绝；达到变更摘要上限须结束旧编辑并明确处理，不能丢掉未决效果。

每个派发 job 携带动作 ID 与预期动作修订，领取后在派发事务核对当前修订；旧 job 即使尚未从队列删除也只结束，不发送或替新版本安排任务。撤销许可时一起阻止关联的待派发动作并递增其修订。改期后的新 job 遵守新的最早派发时间，例如十六点改至十七点后，旧十六点 job 不能提前发送新载荷。库的任务取消只用于回收，不代替业务修订与时间核验。

撤销许可、核对派发与动作状态更新使用同一许可锁。涉及多种状态的事务按家庭门禁、记录 ID、许可 ID、动作 ID 的固定顺序取锁，同类按 ID 排序，防止纠正与派发互相反向等待。派发核对 job 的动作修订、许可与工作修订、最早及最晚派发时间和实际依据记录修订后写入已派发，再发网络请求；如撤销先提交，旧请求被阻止，如派发先提交，取消结果须说明可能已经产生效果。记录纠正事务阻止直接依赖旧修订的待派发动作；已有网络副作用保留真实结果。

动作接纳与派发 job 同事务提交。请求超时后调用方查询同一效果键，不用新 ID 重建；已派发但回执未保存按未知处理。队列恢复负责核对和保存结果，不能等同于再次发送。渠道支持查询时按原回执查询；无法确认则保留未知，需用户决定后续，不以模型重判替代执行核对。

通知去重与物理设备冲突分开。通知的索引为效果键及待派发期限，未知通知不锁住整个接收人。物理动作须按实际设备能力定义冲突范围、确认方式与授权，未接入时不允许 UI 或 Agent 用任意动作载荷绕过。

| ---------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ |

| 消费缺口停用动作 | Agent 保存缺口、工作新修订及许可撤销交接；backend 分别提交撤销和待派发动作阻止 | 全部回执确认前保持修改中；已派发效果保留结果，恢复使用新许可 |
| Agent 调用完成   | 实际结果、用量结算和下一步恢复 job                                             | 重复回执读取已保存结果，不重新调用模型                       |
| backend 动作接纳 | 效果身份、许可与依据引用、派发 job                                             | 回执丢失按身份查询；未知效果不重发                           |
| 家庭重置         | 各应用分别提交关闭／清理及稳定回执                                             | 按持久阶段恢复，完成前不激活新家庭                           |

使用 pg-boss 的事务适配与所属应用相同连接入队，执行设施选择见[协作设计](household-automation.md#执行设施与选型)。库管理的 job、租约、重试表不复制进本 schema。网络、模型及文件操作均不长时间持有业务事务。

## 保留与清理

以下为待实施的初始工程口径，配置和响应须公开实际生效范围。扩容或缩短期限不能静默违背已接纳责任。

| 数据                       | 初始保留与容量                                                         | 清理条件与缺失语义                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 家庭资料与用户确认报告     | 本地家庭生命周期内保留；报告单条最多 32 KiB、每家庭最多 10,000 条      | 达限拒绝新接纳并提示管理；明确撤回保留稳定身份与撤回状态；除家庭重置外，报告按家庭生命周期保留，不依赖 Agent 上报活跃引用                  |
| 成员出现记录               | 初始 30 天、每家庭最多 100,000 条，单条沿用现有生产者上限              | 达到期限或容量上限后按下述清理边界撤回并清除正文；Agent 引用不延长保留期，执行保存实际输入快照；查询报告真实覆盖，不承诺当前实现已有此清理 |
| 已清理记录的撤回摘要       | 每家庭最多 100,000 条；保留至明确家庭重置                              | 仅保留原记录 ID、家庭、主题、来源唯一键、最后内容修订、撤回时间与原因；达到上限暂停新记录接纳并提示管理，不删除仍用于拒绝重交的身份        |
| `record_changes`           | 7 天或 100,000 条，先到为准                                            | 只清理连续前缀并推进下界；消费者落后显示缺口，不阻止来源无限保存                                                                           |
| 活跃工作与输入             | 每家庭最多 100 项活跃工作；每工作最多 100 条待处理输入或 1 MiB         | 持久接纳前检查容量；已承诺输入不能静默丢弃，满额保留待处理和背压状态，越过来源保留期则记录缺口                                             |
| 已结束工作、运行和调用详情 | 完成后 30 天，单次执行文字快照最多 256 KiB                             | 有在途交接或未知动作时保留必要恢复内容；清理后只保留身份、终态及必要去重信息，不声称可重放全部输入                                         |
| 接纳媒体                   | 按材料表的固定期限和总容量                                             | 期限内保留已承诺材料；过期／撤权回收字节并保留缺失描述至相关运行结束后的审计期                                                             |
| 动作与输入去重摘要         | 详细结果 30 天；工作允许重交期间保留效果键、载荷摘要、终态和原接纳时间 | 未知效果必须保留；关闭工作或过接纳期限的旧请求永久拒绝，不能因删除详情重新产生副作用                                                       |
| 笔记                       | 每家庭最多 1,000 条、单条最多 16 KiB，按需修订或撤回                   | 依据过期则待复核，不永久锁住全部原始媒体；超限拒绝新增或由用户整理                                                                         |

backend 记录领域独占原记录清理，读取本地保留规则及动作依据，不跨库查询 Agent 工作，也不承诺按未登记的工作引用延长保留。C/D 调查在使用材料前保存实际输入快照；补查时原记录已过期、被撤回或不可读，则保存缺失结果。只需解释历史的执行可使用已保存快照并说明无法复核；依赖当前依据的等待或动作须重新取证，不能用快照恢复事实资格。需要保证日后仍可核对原记录的职责，在没有相应保留能力时拒绝启用。

启用记录清理须同时接入 C 的记录变更提交边界：清理事务按上述终态规则登记撤回（原因注明保留期或容量清理），并阻止 backend 中直接依赖它的待派发动作，再清除正文和实体关联，保留用于拒绝重交的撤回摘要。

摘要留在原 `context_records` 行，保留身份字段及来源唯一约束；`summary/evidence` 清空，`data` 改为共享 schema 定义的撤回描述，不再作为成员出现正文解析。查询、写入者和数据库浏览须同步支持该终态表示。撤回摘要容量在同一事务内预留；没有容量则不删除身份、不声称已完成清理，停止新增记录并显示清理受阻。

Agent 经变更消费或后续按编号查询发现缺失，不要求它先在线确认才能清理；变更已过保留期时按消费缺口处理。删除不代表现实中未发生；未找到原记录同样不能通过派发核验。长期摘要也有总量上限，达限暂停新职责接纳并提示清理，不能为腾空间删除未知效果身份。

家庭重置是显式破坏性生命周期操作，清理旧家庭数据后依靠已关闭家庭身份拒绝重交，不要求永久保存其内容。媒体自有临时文件、库 job 及其他应用数据分别按所属机制清理，不能靠删除数据库行假定外部副作用已撤回。

## 迁移与具体实例

迁移按批次执行一次明确变更，不引入长期双写、历史版本分支或协议别名。B 为当前单家庭数据赋予本地家庭身份和绑定身份；成员出现的 `revision` 从实际归因修订回填，记录 ID 与证据不变。无法验证来源的记录标明限制，不猜测缺失时间或身份。同步更新共享 schema、生产者、数据库浏览、Agent 和页面，再启用新能力。

C 启用变更流时从迁移完成后的共同写入边界开始，公开初始水位；已有历史仍可查询，但不能声称迁移前修订可以回放。增加表或索引不恢复此前已丢弃的媒体。C/D 的公共运行与调用结构由先交付的消费者迁移一次；D 另行迁移材料结构，未启用媒体消费者不创建永久缓存。

用户在十点说“八点遛过，八小时后提醒”：

1. Agent 接纳唯一输入，backend 保存 `user_report`，发生时间为八点；Agent 保存报告引用、十六点期限和稳定提醒槽。
2. 通知许可就绪后，工作启用与到期 job 在同一 Agent 事务提交；崩溃恢复仍读取这条工作。
3. 十六点核对报告与授权，backend 以提醒槽效果键接纳通知，派发后保存回执；结果丢失保持未知。
4. 用户更正九点时，旧许可先撤销；未派发动作被阻止，原槽通过动作修订命令绑定新许可与依据，最早派发时间改为十七点；旧十六点派发 job 因动作修订不符结束。若原通知已发或未知，则保留结果，不能把改期当成自动重发许可。

此实例不创建遛狗活动实体或全局当前位置。另一个实际来源的记录可以作为补充材料，只有用户确认其对锚点的影响后才改变提醒。
