# 家庭语义基础：设备状态与集采实施计划

**状态：Step 1 任务 1.1 已交付实现，实机验收受阻；后续任务待执行。** 具体缺口及报告见 [任务 1.1](household-steps/01-device-access/01-account-and-read.md)。一次只推进一个 Step，完成该步验收后再进入下一步。第一轮完成 Step 1—5，Agent 接入另做。

终极目标是建立可解释、可维护的家庭语义：理解成员与空间、观察与活动判断、发生过的事件及当前有效要求，供 Agent 消费，并接纳 Agent 基于证据生成的语义候选。本组六步负责其设备数据底座与 Agent 基础接入。backend 是目录、当前状态、有效性与观测顺序的唯一权威；前端和 Agent 订阅同一已提交状态，Agent 另行消费带触发证据的语义事件；历史保存能够解释当时的值、归属、质量和数据缺口。

本组文件是实施规范，不表示功能已经实现。六个 Step 的交付能力均保留；Step 6 的共享契约必须在前五步设计时遵守，运行代码仍在 Step 6 交付。不可把 Agent 的完整状态副本、独立事件通路或历史能力替换成演示页面、定时查询或无来源的文本摘要。

## 家庭模型与本组交付边界

先阅读 [家庭语义目标与领域模型](household-model.md)。该文定义成员与宠物、空间及覆盖、来源观察、当前判断、领域事件和生效要求；Agent 的长期记忆属于独立层，不由家庭状态机 或设备历史库承担。

本组六步交付设备感知基础，尚不覆盖完整的身份／布局自动建模、视觉融合、房间综合状态、要求仲裁和情境设备控制。逐步适配结论与后续交付拆分见该文的“六步架构适配检查”。不能将本文中的“完整公共状态”理解成已包含这些尚未交付的语义。

设备状态采用独立 Agent、完整只读设备副本与独立规则事件流。后续语义计算复用 Agent 服务，候选通过受控命令提交 backend；backend 负责接纳、版本、失效与发布。新增语义上下文按任务读取，不自动扩充设备投影，也不替换已定设备同步通路。

全程顺序为 **Step 1—5 设备基础 → Step 6 设备级 Agent → 无摄像头卧室语义闭环 → 受控情境动作 → 按场景扩展**。家庭语义是最终验收目标，六步完成只是基础阶段完成。卧室与卫生间不部署摄像头；首个语义场景使用经验证的手机亮屏／息屏、灯光和实际可用传感器，允许身份、位置与睡眠状态未知。

具体家庭语义 schema 在六步之后按首个场景落地，当前只保留身份、证据、时间、质量与依赖版本的衔接。不提前创建语义空表、接口或通用引擎，不以手机接入、自动身份识别、视觉或长期记忆未完成阻塞设备六步。

## 实施决策与外部验证边界

本文规定的所有者、身份、提交顺序、错误处理和交付边界是实施决定，不由各步骤另选一套。参数分三类：能力业务策略按 Step 3 的配置文件与持久版本管理；超时、并发、队列、缓存及调度预算集中为 backend 的类型化运行配置，采用本文给定值，不逐项创建环境变量、数据库设置或 UI；协议字段、顺序和原子性是固定契约，不提供开关。Web／Agent 从共享契约引用传输限制，不各自复制默认值。调整预算须同步其唯一配置、文档及验收，不允许隐式启用新采集方式。

每次重构直接替换受影响实现，并在同一改动中更新所有实际消费者、共享类型与文档，删除被替代路径。不存在需要兼容的旧版本；不添加别名、旧 DTO 转换器、双写、功能切换开关或备用请求路径。保留账号／媒体的职责所有权不要求保留其现有类、签名或响应形状。未受本步影响的功能继续使用其唯一实现，不为后续步骤预建第二套实现。

Step 1 的属性读取复用现有 MiCloud 扫码会话，不增加独立 OAuth、uid 映射或额外授权页面。MiLoCo 提供属性语义、MQTT topic 和恢复行为参考；MQTT 的同账号鉴权与供应商准入仍须核实，不能把参考实现的 OAuth 当作本项目已具备的前置。实际设备覆盖、订阅和消息是否到达、服务端限流以及恢复表现仍需实机验收；独立设备事件缺少 MiLoCo 实现，保持未接入。它们统一在 Step 1 产出可用性清单；结果只有已验证可用、已验证不支持、未验证三类。未验证等同于不能启用依赖能力，不等同于整个家庭失败。推送基础通路未通过则停止集采实施，不通过增加轮询绕过门槛。缓存只能提供未知时间的值时，恢复结果允许保持待确认，必须按 Step 3 的恢复矩阵展示，不能承诺自动变成可信状态。

首期通常使用一个供应商账号下的一个家庭，也支持在账号内选择和切换家庭，同一时间只运行一个。家庭选择是全局后台配置；切换时停止旧家庭、清空其运行状态，再保存选择并初始化新家庭，期间允许不可用，失败后停留错误状态供重试。页面搜索和房间筛选只影响显示。多家庭同时守护、物理设备写操作、视觉推理及跨重启可靠语义事件消费不属于本组实施交付，不得以空接口或“已预留”替代独立实现与验收。

## 共同约定

- 用完整 XState，不手写通用状态管理框架。Hono 只负责命令、查询和 SSE 传输。
- 单 backend 进程维护账号当前家庭；前端与 Agent 跟随同一选择。Agent 的本地副本只读，不能与 backend 争夺当前状态所有权。
- 保留 MiLoCo 业务字段和规格语义，新增业务字段使用 snake_case；不创建兼容别名。
- 先广泛接收当前家庭的合法推送，再分别决定 latest 更新、历史保存和消费者展示。设备能力没有推送通路时明确标为不支持，不提供属性轮询降级；主动读取仅用于初始化、重连对齐和显式按需读取。
- 前端与 Agent 通过本地 backend 订阅状态；断线后重连订阅，不以定时 HTTP 查询降级。一次性诊断查询和登录材料读取不承担持续状态同步。
- 属性状态、设备事件和在线状态分别验证。逐条输入的状态变更与规则证据按同一提交顺序产生；投影提交后才向消费者发布。状态快照不能还原事件经过，语义事件不能用接收时的最新状态替代触发时证据。规则输入见 Step 3，消费协议见 Step 6。
- SSE 恢复当前状态，不补偿历史事件。历史只对数据库已确认提交的记录提供持久查询；未确认数据遵守 Step 3/4 的有界队列和丢失约定，不能把它描述为可靠消息队列。
- 沿用现有账号授权及媒体资源所有者，不顺带重写扫码、续期和 go2rtc。
- 参数上限和周期需用 Step 3 的真实数据量验证。目录同步、凭据续期、协议心跳及本地计时器沿各自职责运行，不得用它们暗中执行周期属性读取。

## 跨步骤唯一契约

| 概念                                   | 唯一含义与定义位置                                                                                                                                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 稳定身份                               | `account_id/home_id/device_id` 不随登录会话或进程重启变化；账号包含供应商身份与区域约束。持久目录和归属由 Step 2 定义。                                                                               |
| `scope_epoch`                          | backend 每次启动及有效作用域变更生成的 UUID；旧 epoch 的新输入、命令和任务结果不能进入当前家庭。Step 2 定义变更和提交点。                                                                             |
| `source_id` / `collection_generation`  | 前者标识采集来源；后者标识该来源的活动采集实例，断线重建或凭据替换时更新。业务 epoch 相同也必须拒绝失效实例的结果。Step 3 定义观测字段。                                                              |
| `input_sequence`                       | 当前家庭运行内实际接纳输入的顺序，从 1 开始；设备观测排队处理，控制事件直接进入状态机，统一在提交时编号。拒绝输入不占号，没有公共变化的接纳输入也占号；不用于逐条追踪历史写入回执。 |
| `StateVersion`                         | `{ scope_epoch, sequence }`；`sequence` 仅在公共投影变化时连续递增。语义事件通过 `state_version` 引用它，客户端不跨 epoch 比较数值。Step 5 定义状态传输。                                             |
| `observation_id`                       | 一次被接纳观测的内部身份，写入重试不改变；不冒充供应商消息 ID。Step 3 定义去重，Step 4 定义存储唯一键。                                                                                               |
| `semantic_event_id` / `event_sequence` | 语义事件的稳定发送身份与当前 epoch 内独立递增序号；不能与状态 sequence 混用。Step 6 定义事件传输和去重边界。                                                                                          |
| 时间                                   | 对外时间统一为 UTC RFC 3339 毫秒字符串，未知来源时间为 null；数据库使用带时区时间类型。进程内超时和持续条件使用单调时钟，不用系统时钟跳变推导持续时间。                                               |
| 最新值与有效性                         | 值、来源时间、接收时间、有效在线状态 availability 和质量分别表示；目录在线字段仅为快照。枚举、在线仲裁、质量原因优先级与恢复矩阵只在 Step 3 定义，成功查询或恢复连接不自动确认旧值。                  |
| 历史边界                               | 已接纳观测携带不可变账号、家庭、采集时归属和质量；后续切家不改其身份，可继续落库。Step 4 区分历史写入丢失与来源失效，明细清理时额外保留每能力一份必要值基线，以支撑保留期内长期不变状态的查询。       |

共享 schema 位于 `packages/api/src/contracts/`，新增 `household.ts`、`household-observations.ts`、`household-history.ts`、`household-agent.ts`，分别承载设备公共状态/命令、设备规范化观测、设备历史查询、设备规则/触发事件契约。家庭语义的类型化契约在对应阶段增补，不将上述文件视为已经包含人物、活动判断或有效要求的通用 schema。Step 2—5 建立各自 schema；Agent 契约的字段在这些步骤期间保持一致，Step 6 才启用规则和事件路由。沿现有导出入口提供类型和 Zod schema，不创建兼容别名。供应商 raw 响应只在适配边界解析，不进入共享契约。

## 所有者与故障隔离

| 所有者                     | 负责                                                                     | 不承担                                                                     |
| -------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 现有账号／目录／媒体服务   | 登录材料、凭据续期、目录同步、摄像头连接和资源清理；发布安全公共状态变化 | 通过页面访问驱动家庭采集；让迟到命令提交到新作用域                         |

| 历史 writer                | 有界批量写入、重试、质量时间线、采集会话和缺口；写入时保留原归属         | 决定当前 latest，或在切家时丢弃已接纳历史                                  |
| backend 规则服务（Step 6） | 对确定的能力和有效性执行条件、持续计时和事件生成                         | 对每条消息调用 LLM，或把快照恢复解释为漏掉的物理事件                       |
| Agent（Step 6）            | 维护只读状态副本、消费语义事件、绑定证据进行推理及记录任务结果           | 独立采集小米、将 checkpoint 当家庭状态源、宣称尽力而为通路可跨重启补齐事件 |

普通目录刷新遇到数据库故障时，当前家庭继续运行。已经接纳切家后，旧家庭已停止；新选择保存或初始化失败时保持不可用并显示错误，允许重试。规则变更和 Agent 持久任务启动需要保存成功，数据库故障时返回明确失败。进程重启时数据库不可用则不能假装恢复持久目录或家庭选择。各组件的队列上限、溢出、恢复与停止行为由所属 Step 给出，任何丢弃必须有可见计数，无法确定的丢失数量为 null。

| 迟到回调拒收、恰好达到容量边界、原子批次、重复写入身份、质量优先级、清理基线选择等内部确定性分支 | 接受实现审查：给出具体起始状态／输入顺序、源码位置、实际使用的条件／约束及由此可核对的结果，并结合已运行的对应业务链路。现有工具可复现时附操作证据；不要求为每个分支等待自然故障，也不要求自行增加故障注入入口。 |

账号／家庭隔离、单一状态权威、顺序与原子提交、资源有界及本步启用能力的正确性仍是完成门槛。规定证据缺失或检查不符时不能宣告通过；能由实现审查确认的内部确定性分支，不因没有人为制造对应故障而反复标为未验证。无法建立可核对结论的具体缺口须在实现前列入本步报告，不扩大为所有其他已验证能力的停工条件。未启用的设备能力不阻断其他已验证能力。

仓库要求：未经用户明确许可，不新增任何测试代码，包括临时自动化测试或故障注入脚本。各 Step 的验收条件不构成写测试授权；类型检查、lint、构建和手动运行观察照常执行。
