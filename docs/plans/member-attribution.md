# 成员短期外观归因实施计划

状态：待实施。当前能力与验证范围见[本地感知](../perception.md#持续成员身份分析)。本文维护本地人体外观归因的具体改动、参数与验收；主交付顺序仍由[家庭情景与自动化](household-automation.md#9-实施顺序与改动位置)维护。

## 目标与范围

近期任意一路摄像头通过现有人脸规则确认成员后，以该目标对应的人体外观建立短期参照。任意一路后续出现的人物，包括同一路的原轨迹或新轨迹，都可以匹配这些参照，形成“推测是某成员”的关联。摄像头只标记证据来源，不规定起点、接力顺序或必须经过的房间。

交付闭环为：人脸确认 → 短期外观参照 → 人体外观推测 → 后续人脸确认或纠正 → 现有成员活动记录。首期仅覆盖人物，不扩展猫狗识别。

复用已有 ReID（把人体外观转换成可比较向量的模型），不增加模型或推理次数，不新增数据库表。范围不含 Agent、性别推断、家庭在场前提、房间路线、位置汇总、人工纠错页面或自动人脸样本积累。采样修复单独验收，不在本文重做；输入缺失时明确保持未知。

## 现有接入约束

- `perception/tracking/tracker.ts` 内部保留人体外观向量，当前输出只有 `extracted / reused / missing` 等状态，家庭领域不能直接取得向量。
- `perception/service.ts` 在 `source.identity.associations` 中投影成员关联；活动服务要求有效的人脸身份观察，因此目标来源没有人脸结果时会跳过。
- `household/identity/activity-service.ts` 的活动缓存键包含成员 ID；`activity-repository.ts` 保存主体关联时只新增、不替换。外观推测被人脸纠正后，需要避免旧成员仍保留该活动。
- 当前 `candidate` 是直接识别的候选状态，不等于人体外观推测。保留依据区别，不将外观匹配标记成人脸确认。

## 1. 输出已有外观证据

修改位置：

- `apps/backend/src/perception/tracking/tracker.ts`
- `apps/backend/src/perception/tracking/runtime.ts`
- `apps/backend/src/perception/video/events.ts`
- `apps/backend/src/perception/service.ts`
- 按实际调用链同步调整计算进程装配和事件校验。

跟踪完成目标分配后，在内部 `tracking` 事件中附带本帧实际新提取的外观证据，与跟踪结果一起通过 IPC（进程间通信）交付。每份证据绑定家庭作用域、来源运行、媒体代次、帧序号、轨迹编号、观察时间、模型／处理版本及 128 维向量。证据身份由这些来源字段确定，不能只用局部轨迹编号。

只输出实测目标的新特征。预测框、缓存复用及多人框明显重叠的观察不作为新增支持；重叠判定复用已有框计算能力，具体门槛随实景校准集中维护。来源、帧龄及运行资格通过现有接纳检查后，再交给家庭身份模块。内部向量不进入公共查询、SSE 或窗口 JSON。

完成条件：任一特征可以定位到原帧与目标；旧运行事件被拒收；没有新增模型调用；浏览器响应不含向量。

## 2. 建立短期参照并归因

在 `apps/backend/src/household/identity/appearance.ts` 新增有界状态与匹配规则，通过 `apps/backend/src/main.ts` 装配并注入感知服务。感知提供证据，家庭身份领域拥有参照与归因。时间作为输入传入规则，不在匹配函数内读取全局时钟。类型从共享 schema 和实现推导，不重复维护类型定义。

### 参数依据与初始预算

参数分为源码约束、资源预算和待校准策略，不能把后两类写成已验证的识别参数。当前默认检测采样为 3 fps、`maxFrameAgeMs=2000`；人脸采样间隔默认 1000 毫秒，允许 500–10000 毫秒，确认要求至少 3 次支持且跨度至少为两个采样间隔。人脸证据默认保留 30 秒。人体轨迹失配超过 2000 毫秒后删除，静止特征最多按四个跟踪步骤复用；特征更新并非固定频率。

依据见 [感知配置](../../apps/backend/src/perception/config.ts)、[身份配置](../../apps/backend/src/perception/identity/config.ts)、[确认规则](../../apps/backend/src/perception/identity/analysis.ts)、[身份运行时](../../apps/backend/src/perception/identity/runtime.ts)和[人体跟踪](../../apps/backend/src/perception/tracking/tracker.ts)。这些是源码默认值，不代表当前部署覆盖配置或实际吞吐。

| 状态／参数 | 实施约束 | 参数性质 |
| --- | --- | --- |
| 等待同帧人脸结果的外观缓存 | 从原帧开始计时，不超过该来源 `maxFrameAgeMs`；每轨迹容量按 `ceil(sampleFps × maxFrameAgeMs / 1000) + 1` 推导 | 对齐现有人脸结果接纳期限；默认配置为 7 份，而非固定 5 份 |
| 临时轨迹数 | 全局最多 256 条；满时拒绝新条目并统计容量跳过，已有条目按期限清理 | 保守资源预算，不代表支持 256 人或任何摄像头规模 |
| 临时向量总预算 | 最多 8192 份，每份 128 个有限数值；同时限制元数据和序列化事件大小 | 按 64 位数值计算裸向量最多 8 MiB，另有对象／IPC 开销；达到任一上限即跳过，不能承诺所有配置无损缓存 |
| 成员外观参照 | 每人最多 5 份，最多沿用现有 32 名成员上限 | 资源起点；最多 160 份、裸向量约 160 KiB，不代表姿态覆盖充分 |
| 参照有效期 | 10 分钟仅作为校准候选；用 1、5、10 分钟候选离线比较后选择上线值 | 衣着可能立即变化，任何固定期限都不能证明身份有效 |
| 推测支持 | 至少 2 份实际新提取且身份不同的帧证据，间隔至少 500 毫秒；5 秒为待测积累窗口 | 抑制单帧偶合的策略起点；两帧仍高度相关，不是两次独立验证 |
| 推测有效期 | 5 秒仅作为待测的新外观支持期限；还须同时满足当前跟踪有效、目标未结束、参照未过期 | 不能跨过现有跟踪失效边界；不保证静止或过载时标签不闪断 |

临时缓存只解决单次人脸推理结果与原帧外观的异步关联，不等待三次确认全过程。确认出现时，优先使用本次新的人脸支持对应的外观；不要求保留全部较早确认帧。缓存被预算挤出或结果到达时不再合格，就跳过建参照，不能用邻帧补齐。

参照满额时优先保留不同来源的合格样本，再在同来源中按已知质量及时间替换；不能让单一路连续样本挤掉全部其他来源参照。首期没有朝向标签，不宣称按正面／侧面／背面分桶；同一路仍可占用全部名额，不要求多来源才能建立参照。状态只保存向量与必要元数据，不额外保留图片；参照只存在内存，重启后重新积累。

运行内到期用单调时钟，展示和记录保留观察时间；不能混用不同进程的单调时钟原点。接收方根据来源报告的帧龄换算剩余预算，迟到或时间关系无法核对的输入拒收。

### 建立参照

1. 只以现有直接人脸关联的 `confirmed` 为入口。
2. 以同一运行、媒体代次、帧序号／RTP 时间和轨迹编号，精确关联本次新的人脸支持与外观证据。只有本次支持属于已确认成员才建参照；不以首次 `confirmedAt` 或发布结果的最新帧号代替证据原帧。确认先到或外观先到都使用有界状态关联；该帧仅复用了旧外观或拿不到对应新特征时，不建参照。
3. 用人脸证据身份去重，消费过的确认不能重复延长参照期限。只有新的直接确认依据才允许补充参照，不能因旧 `confirmed` 尚未过期而持续采入整条轨迹。
4. 参照期限以真实观察时间计算，不从迟到处理时间重新起算。
5. 外观推测不能生成或刷新参照，也不能写入正式人脸参考资料。

### 人脸参考版本依赖与级联失效

每份外观参照必须保存建立它的直接人脸证据的完整 `identityReferenceVersionsSchema`：`contentVersion`（参考照片内容）、`eligibilityVersion`（识别资格）、`matchingVersion`（阈值与匹配规则）、`modelVersion` 和 `processingVersion`。这些是人脸确认依据的版本，和人体 ReID 自身模型／处理版本分别记录，不能混用。推测及待保存活动携带实际依赖的参照版本，不能在保存时换成当前版本来绕过校验。修改人脸阈值或差值规则必须同步更新 `matchingVersion`。

订阅现有 `identityReferences.matching` 的快照变化。在参考照片删除／替换／增加、匹配规则调整、识别资格变化或参考快照变为 `null` 时，若任一依赖版本不再相等，先使旧版本失去使用资格，再发布新的关联快照：

1. 删除旧版本外观参照，清除依赖它们的待确认支持和当前推测，立即撤下实时标签；不能等活动仓储拒写后才清理。
2. 首期版本是整个参考快照的版本，不推断只影响某个成员；按完整版本撤销全部不匹配参照。保持有界的已消费进度、冲突阻断及撤销记录，不能借版本切换重放旧确认。
3. 丢弃依赖旧版本的待写归属快照，停止重试；冻结在途写入继续由事务内版本校验决定是否可提交。旧写入回执不能恢复实时关联或替换更新的内存状态。版本改变之前已经合法提交的记录保留为历史，不代表当前身份仍有效。
4. 新快照就绪后，只有基于新版本、新接纳的人脸确认和对应外观才能重建参照；不能将旧向量重新标记为新版本。即使 `null` 后恢复相同版本号，也不自动恢复被清除的参照或重放已消费证据。

若同一活动后来取得新版本下的合法归因，仍保留活动状态中首次接纳的 `original`、纠正次数及最近纠正，再生成新版本待写快照。历史摘要可以保留旧版本来源；当前归属的保存资格只核验 `current` 的实际支撑版本，不能因 `original` 属于旧版本而拒绝合法更新，也不能利用它为旧 `current` 放行。参考配置失效本身不证明历史错认，不自动计为成员纠正；后续真实语义变更仍按活动状态规则累计。家庭撤权和成员删除继续遵守现有访问与数据生命周期规则。

### 目标匹配与结果选择

1. 任意来源的新人体特征与所有有效成员参照计算余弦相似度；向量须与参照模型／处理版本一致。每位成员取其有效参照中的最高匹配分数，再比较最佳成员与第二成员。
2. 最佳分数通过绝对门槛，并领先第二成员达到差值门槛，才形成一次支持。仅有一位候选时仍须通过绝对门槛。
3. 在支持窗口内取得至少两次指向同一成员的新证据后输出 `inferred`，两次必须有共同且仍有效的参照支撑；参照淘汰或版本改变后重新核对，不能拼接互不相容的支持。缓存复用不计数，也不刷新有效期。
4. 家庭身份模块同时消费原始 `identityObservation.tracks` 与 `identityObservation.recent` 的 `state`、证据和观察版本，不能只消费已投影的成员关联。原始状态为 `conflict` 时，即使 `label=null` 且关联为空，也立即清除该目标的外观支持及当前推测，阻止新推测和新参照建立。阻断持续到同一目标收到更新、有效的直接人脸 `confirmed`；仅变成 `unknown`、冲突证据过期或关联消失不解除阻断。目标从跟踪列表消失时进入结束核对，先处理结束证据，再按下节清理；新运行不能接纳旧运行事件。新证据支持不同成员或现有人脸候选指向其他成员时，撤下冲突的外观推测并重新积累，但不得绕过上述人脸冲突阻断。新提取的外观未达门槛或候选接近时也停止当前推测；单纯没有提取到特征只按原期限失效，不能当成反证。有效人脸确认优先。
5. 参照缺失、特征缺失、分数不足、候选接近或版本不一致时保留未知，并提供对应原因。
6. 目标轨迹结束时清理当前推测；该来源已经产生的合格参照可供其他轨迹继续使用，直到自身到期。家庭切换、撤权、成员删除／资格失效或模型版本变化时，清理受影响参照及其推测。原始人脸冲突或后续直接确认推翻该目标参照身份时，按下节撤销参照本身及其依赖，不批量改写其他历史轨迹。

### 冲突与参照撤销

每份参照保留唯一参照 ID、建立它的人脸证据身份及来源目标键；每份外观支持记录实际使用的参照 ID。对同一来源目标收到有效的人脸冲突或不同成员的直接确认时，在一次领域状态更新中执行：

1. 删除该目标已产生的参照，停止其参与任何成员匹配；首期无法精确定位换轨时间，保守撤销该目标此前全部参照，不连带撤销该成员其他来源目标的独立参照。
2. 清除所有依赖这些参照的待确认支持和当前推测，包括其他来源上的目标；不能只清除当前标签后保留累积次数。
3. 保存该目标已消费的人脸证据进度及撤销截止帧，截止帧取导致撤销的最新人脸证据帧；拒绝截止帧及以前的证据重建参照。观察版本也须单调接纳，不能由迟到的旧 `confirmed` 解除阻断。参照删除不删除这些去重与撤销状态。
4. 在同一次状态更新中向活动状态拥有者交付撤销原因、触发证据和被撤销的参照 ID。撤销必须覆盖依赖这些参照的待写／在途活动，不能仅通过下一次实时关联快照中缺少标签来推断；具体保存规则见下节。
5. 冲突后重新确认只能用截止帧之后的新直接确认支持与同帧新外观建立参照。不同成员被确认时也不把旧参照向量直接改名归给该成员。

### 结束目标的身份核对与清理顺序

原始身份观察按来源运行、媒体代次和单调观察版本接纳，`tracks` 与 `recent` 使用同一目标键及证据去重规则。一次完整观察的处理顺序固定为：先处理两个集合中的新增冲突／身份推翻及参照撤销，通知所有受影响活动；再处理其他合法状态更新；最后确认目标结束并清理。`recent` 重复出现在多次发布中不重复撤销、累计纠正或建立参照。结束目标只允许处理新的终止证据和撤销，不用它重新建立实时推测或外观参照。

跟踪列表中目标消失不等于其最后人脸状态已经交付。现有身份发布会合并更新，冲突可能只出现在随后发布的 `recent`；在取得对应终止摘要之前，保留该目标的参照归属索引、撤销进度和必要的活动状态，不提前按“正常结束”释放。终止摘要中的新冲突必须先删除该目标的旧参照并处理跨来源依赖，随后才能完成结束清理。活动的“已结束且保存完成”也必须包含这一步终止核对完成。

现有 `recent` 有 60 秒与 32 条上限，不能当成可靠事件日志。结束核对状态沿用有界目标预算，最多等待现有 `recentTtlMs`；若终止摘要因容量、期限或来源运行停止而无法取得，则撤销该目标尚存参照，原因标为 `terminal_identity_unavailable`，并沿用参照撤销的活动更新规则。不能在不知道终态时继续信任参照，也不把这种保守失效标成人脸已证实冲突。不得为腾空间静默删除未核对目标后继续使用其参照。

终止证据处理和撤销交付完成后才能释放目标的阻断与去重状态；之后拒收该目标的新正向推断，来源运行结束按现有运行资格拒收旧运行输入。正常、无冲突的终态允许已建立参照按自身期限继续供其他目标使用；若没有取得可信终态，按上述保守失效处理。活动更新只涉及下节规定的仍活动或保存未完成的集合，不因撤销批量重写已结束并保存完成的历史。


分数门槛和领先差值须由下述实景校准确定，不直接沿用单镜头跟踪阈值，也不将相似度展示为身份概率。现有跟踪使用余弦距离门槛 0.2；对归一化向量它对应相似度至少 0.8，但此值只约束现有跟踪关联，不能据此作为本功能的上线门槛。[Deep SORT 原实现](https://github.com/nwojke/deep_sort/blob/master/deep_sort_app.py)也将距离门槛与特征库容量作为独立参数，并不证明它们适合家庭成员归因。没有校准结果前只能采集分数和观察候选，不把外观结果写成成员归属。

完成条件：任意一路可建立及使用参照；同一路也适用；推测不会反向扩充参照；期限和容量不因重复观察无限延长。

## 3. 统一关联出口与活动保存

修改 `packages/api/src/contracts/perception.ts` 及必要的共享成员身份契约，把公开关联提升到来源级 `associations`，不再依附可为空的人脸观察。现有直接识别与外观推测由家庭身份领域统一选择结果；所有调用方同步更新，不保留兼容别名或双份权威关联。

| 依据 | 状态 | 必须携带的信息 |
| --- | --- | --- |
| 现有直接识别 | `candidate / confirmed` | 原识别证据与版本 |
| 人体外观 | `inferred` | 目标证据、参照证据、匹配分数、有效期与策略版本 |

公共结果使用判别 schema 表达不同依据。已有宠物直接识别保持其依据，不被误标为人脸；新增外观推测只接受人体目标。公共摘要不包含向量，目标来源即使没有人脸结果也可返回有效推测。来源级统一结果的生命周期由家庭身份模块管理，查询不能重复推进确认状态。

具体修改：

- `household/identity/activity-service.ts`：消费统一关联，外观分支不再要求目标来源有人脸观察；活动以家庭作用域、运行、媒体代次和目标轨迹标识，不以成员 ID 定义记录身份。
- `household/identity/activity.ts`：按依据构造活动，外观推测使用 `tentative`，保存参照摘要与实际时间，不保存向量，不伪造人脸证据。
- `household/identity/activity-repository.ts`：按实际依据校验成员资格和支撑参考版本，在同一事务中更新活动并替换主体关联，删除旧成员的主体关系，保留设备来源关系。

同一目标后续人脸确认为另一成员时，使用同一活动 ID 修正归属。写入沿用现有有界队列，串行保存该目标的更新；旧版本在途完成后必须继续保存最新版本，不能因去重或结束清理丢掉纠正。实时到期只停止当前使用，不删除当时成立的历史记录。历史原始观察不改写；纠正范围限于对应目标活动。

### 参照冲突撤销与异步写入

活动状态拥有者为所有尚未结束的活动保留当前归因依赖的参照 ID，包括已保存、没有待写更新的活动；另外为待写／在途快照保留各自实际依赖的参照 ID。两类依赖共同构成有界反向关联，不能在一次写入成功后就删除仍活动记录的依赖。目标结束但终止核对或最新版本保存未完成时，也继续保留活动状态及必要依赖。

撤销参照时，通知反向关联中的所有活动，而非只检查保存队列。仍活动且已保存的记录如果当前归因依赖被撤销参照，同样生成更高版本的未知归属、累计纠正并入队，最终删除旧成员主体关系。若最新当前归因已由独立有效证据支持，则仅使旧快照失效，不撤销该合法归属。只有“目标终止核对完成且最新版本保存完成”同时成立，才能移除该活动的依赖与内存状态；这些已经结束且保存完成的历史不纳入批量追溯。

冲突撤销和自然到期分别处理：

- **冲突撤销／确认推翻参照**：使仍活动或保存未完成、且依赖该参照的归属失效。活动拥有者同步生成更高 `revision` 的快照，将仍依赖该参照的 `current` 改为未知，原因记为 `reference_revoked`，保留撤销证据并按一次语义变更累计纠正。相同撤销重复交付不重复计数。若最新 `current` 已由独立有效证据支持，则保留该合法归属，但仍使旧在途版本失去保存资格。
- **自然到期／容量淘汰／目标正常结束**：只停止参照的后续使用，不推翻此前合法接纳的活动，不因保存排队而把过去成立的归因改为未知。家庭资格和人脸参考版本仍按各自规则校验。

待写项合并为拥有者的最新累计快照，禁止再次调度已撤销的旧归属。写入开始前核对所选版本及其撤销状态；单靠人脸参考版本和成员资格相等不足以放行。参照不存在不自动等于冲突撤销，须按明确原因区分。

对于已经在途的数据库写入，本期采用**串行保存更高版本的撤销／替代结果**作为竞态收敛保证，不声称进程内检查与数据库提交原子完成。若旧写入已进入无法取消的提交阶段，可能短暂保存旧归属；其回执只记录该旧版本已保存，必须继续调度拥有者的最新版本，在同一事务中移除旧成员主体关系并保存未知或独立有效的新归属。纠正写入不受普通活动更新节流阻挡，也不因轨迹结束或旧任务完成而清理。失败时保留最新快照并沿用有界重试，不重试旧归属；以最新版本成功保存作为该活动保存完成的条件。

撤销保存只核验当前家庭访问资格、活动身份、版本顺序及领域生成的撤销依据，不要求被撤销参照仍然有效或未知结果仍有可匹配成员。否则撤销本身会被旧匹配校验拒绝。新成员归属仍需通过对应有效证据校验。

上述保证限于进程正常运行和数据库恢复后能继续保存的情况；数据库不可用时实时标签先撤下，历史存储可能暂未更新，不能宣称两者已经一致。未保存撤销期间进程崩溃的恢复不在本期保证内，不以新增通用持久任务系统扩大范围。

### 活动原归因与纠正的存储约定

复用现有 `contextRecords.data` JSON，在共享契约中定义 `attribution`，不新增表。字段约定如下：

| 字段 | 保存内容与更新规则 |
| --- | --- |
| `original` | 首次接纳的归因快照，包含成员 ID／显示名、状态、依据类型、观察时间、接纳时间、策略／模型版本及有界证据摘要；创建后不覆盖 |
| `current` | 当前归因快照，结构复用 `original` 的 schema；撤销且暂无替代成员时显式表示未知及原因 |
| `revision` | 该活动的单调更新版本，用于拒绝旧写入；重试使用同一版本 |
| `lastCorrection` | 最近一次语义变更的前后归因快照、原因、触发证据摘要及处理时间；首次无纠正时为空 |
| `correctionCount` | 实际语义变更次数，重复提交不累加 |

证据摘要保留原始证据身份、来源运行／媒体代次／帧／轨迹、直接识别或匹配依据与参照身份，不保存向量和媒体字节。各快照的证据数组沿用对应能力的条数上限，原归因不能只引用会被顶层 `evidence` 覆盖的对象。

成员改变、推测升级为直接确认、冲突导致归因撤销属于语义变更；同一归因的新支持或结束时间更新只更新 `current` 和版本，不覆盖 `original` 或增加纠正次数。自然到期不视作历史纠错。

`activity-service.ts` 中按稳定活动 ID 管理的活动状态是归因快照的唯一拥有者。在首次接纳归因、尚未入队时，初始化不可变的 `original`、`current`、`revision=1`、`correctionCount=0` 和空的 `lastCorrection`。后续每次接纳更新都基于这个累计状态产生新快照；语义变更由拥有者递增纠正次数，并用变更前的 `current` 与新归因构造最近纠正。仓储和队列不重新计算这些字段。

队列可以合并待写更新，但必须保留完整累计快照，包括首次归因和期间所有语义变更的累计次数。开始写入时冻结所选版本，后续变化生成新快照；旧写入回执只确认其实际保存版本，不覆盖最新内存状态。首次插入前或写入在途期间发生的多次纠正同样累计，不能仅比较最终成员与数据库成员来计算次数。未保存的最新快照不能因轨迹结束而提前丢弃，沿用现有有界保存与失败处理；本方案不承诺进程崩溃前尚未落库的状态可恢复。

仓储在现有事务中读取该活动的已保存值：首次插入直接保存拥有者提供的累计快照，不能在插入时用最新 `current` 重建 `original` 或将纠正次数归零。更新只接纳更高版本，并校验 `original` 与已保存值一致、纠正次数不倒退；保存输入快照中的累计次数和最近纠正，不按数据库前后差异再次累加。同版本且同内容的重试为幂等，同版本不同内容或不可变字段冲突明确拒收，旧版本拒收；不能将调用方整条 `record` 无条件覆盖到数据库。更新 `data.attribution`、顶层摘要／确定性／当前证据及主体关系必须同一事务完成。`current` 为未知时移除成员主体关系，保留设备来源，不能为通过成员资格校验而继续挂在旧成员下。

首期页面承诺展示“首次归因、当前归因、最近一次纠正及累计次数”，不承诺完整逐次纠正时间线。多次纠正仍保留首次依据和最近一次前后依据；若需要每次修订的完整历史，另行设计，不无限增长 JSON 数组。

完成条件：先推测甲、后确认乙，同一活动更新为乙，甲的活动查询不再返回旧主体关联；迟到保存不能覆盖最新纠正；数据库失败不阻塞检测。

## 4. 接入现有页面

更新现有镜头身份展示、成员活动展示和相关 Web 数据适配；实施时按来源级 `associations` 的实际引用核对全部调用方。不要另建页面。

- 直接确认沿用“已确认”；直接识别候选保留原有含义。
- 外观推测显示“推测是某人 · 人体外观匹配”，详情提供参照来源和确认时间。
- 实时结果过期后移除推测标签；活动历史从 `attribution.original/current/lastCorrection` 展示首次与当前依据、最近一次纠正及累计次数，不宣称完整纠正时间线。
- 窗口原始人脸快照保持不变，后来形成的归因不能伪装成原帧人脸确认。
- 媒体已过期时保留摘要并说明媒体不可用，不延长媒体期限。

完成条件：没有目标人脸结果也能显示外观推测；人脸纠正后实时标签与成员活动一致；页面不把推测显示为确认。

## 5. 校准与验收

实施顺序：证据出口 → 归因模块 → 活动保存 → 页面 → 实景校准。采样链路的独立修复须核对输入可用性，不把未采到或未提取当成匹配失败。

收集同人同镜头、同人不同镜头、不同人相似衣着、换衣及长时间间隔片段，比较正确与错误成员的分数分布，确定绝对门槛和领先差值，再用另一组片段验收。不能在同一片段调参后把该片段当独立验证；无法区分的场景保持未知。只有单人素材时只验收单人覆盖，不能宣称已验证多人误归属。额外统计同帧人脸／新外观共同可用比例、每路新特征间隔和推测闪断次数；若当前“复用特征不计数、不续期”约束导致覆盖不足，记录限制再决定是否调整，不暗中延长有效期或增加推理频率。比较参照期限及支持窗口时固定素材和其他参数，最终选定数值、策略版本和覆盖范围后才启用活动写入。

| 场景 | 预期结果 |
| --- | --- |
| 任意一路确认后，同一路转身或重新出现 | 有合格新外观证据时可以推测 |
| 任意一路确认后，另一路出现 | 使用同一家庭参照库，无固定起始来源 |
| 全程没有直接确认 | 未知 |
| 重复交付、静止复用特征 | 不增加支持次数、不刷新期限 |
| 多人相似衣着、参照过期或特征缺失 | 未知或撤下失效推测 |
| 人脸 `conflict` 且 `label=null`、无成员关联 | 清除推测与支持，冲突过期变未知仍不重建，更新直接确认后才解除阻断 |
| 参照身份被推翻后，再输入两份匹配旧参照的外观 | 旧参照已删除，不能再次归到原成员 |
| 重放已消费确认或迟到旧 `confirmed` | 不重建已撤销参照、不解除阻断 |
| 后续人脸确认另一成员 | 当前标签和对应活动归属同步纠正，旧参照不直接改名复用 |
| 甲推测 → 乙确认 → 再次纠正，随后重读数据库 | 首次甲的依据仍在，当前归属及最近纠正正确，次数不因重试增加 |
| 断流重连、轨迹编号复用 | 不继承旧目标推测 |
| 家庭切换、撤权或成员失效 | 相关状态清理，迟到结果拒收 |
| 删除／替换参考照片，或调整阈值并更新匹配版本 | 旧参照、支持和实时推测同时失效，旧确认重放不能重建 |
| 版本变更时存在待写或在途活动，随后收到旧写入回执 | 待写旧归属丢弃，在途按事务版本校验，回执不能恢复标签或触发旧版本重试 |
| 新版本确认后更新原活动 | 当前依据使用新版本，首次归因与累计纠正摘要保留；仓储不以历史版本为当前资格 |
| 参考快照暂时为 `null` 后恢复 | 不自动恢复参照，等待新的合法确认 |
| 首次落库前依次接纳甲推测 → 乙确认 → 丙确认，队列只写最后版本 | `original` 仍为甲及其原依据，`current` 为丙，`correctionCount=2`，`lastCorrection` 为乙到丙；重试不增加次数 |
| 保存中发生人脸纠正 | 最新版本最终保存，旧主体关系删除 |
| A 的人脸冲突发生在两次发布之间，随后移入 `recent`，B 仍使用其参照 | 先消费 `recent` 新冲突、撤销 A 参照并更新 B，再清理 A；重复发布不重复纠正 |
| A 已从跟踪消失，但终止摘要尚未到达或最终丢失 | 保留结束核对状态；收到终态先处理，无法取得时保守撤销参照，不无限等待或静默继续使用 |
| B 仍活动、推测已保存且队列为空，A 的参照被撤销 | B 生成更高版本未知归属并入队，最终删除旧成员主体关系 |
| B 已完成终止核对且最新版本保存完成，A 后续被撤销 | 不批量重写 B 的已结束历史活动 |
| B 的推测依赖 A 的参照，B 尚未写入时 A 人脸冲突 | 待写快照变为更高版本的未知，首次推测摘要保留，不能首次落库成旧成员归属 |
| B 活动正在提交时 A 人脸冲突，参考版本和资格均未变 | 即使旧提交成功，也继续保存更高版本撤销；最终删除旧主体关系，旧回执不能丢掉撤销 |
| 上述撤销写入失败后恢复，或重复收到撤销通知 | 重试最新快照直至保存，次数不重复累计，目标结束不丢失待保存撤销 |
| 参照自然到期时 B 的合法活动正在保存 | 不生成冲突撤销；按历史接纳依据及现有资格完成保存 |
| 旧依赖写入在途，但 B 已取得独立直接确认 | 继续保存合法的最新归属，不被旧参照撤销误清为未知 |
| 多路持续运行 | 缓存不越界，不增加模型调用，不阻塞基础检测 |

记录可归属片段增量、错误归属、推测形成延迟及缓存峰值；覆盖率提升不能掩盖错认。未知原因至少区分无参照、无新特征、分数不足、候选接近及冲突。

实施时只运行直接相关的最小已有测试范围；新增测试或故障注入脚本须先取得用户明确许可。类型检查和必要的页面核对随实际改动执行。实现后把用法和未覆盖限制更新到当前功能文档，已完成施工步骤从本计划移除，不保存一次性验证日志。

## 6. 人体属性模型参考与可选评估

本节是后续可选评估，不增加首期依赖，不包含在下面的代码量估算中。截图提到的模型确有参考价值，但人体属性分类与成员身份匹配是不同任务；优先评估可见衣着和朝向的增益，不把性别或年龄预测用于成员归因，也不写入成员资料。

### 官方能力与适用性

| 候选 | 已核对的能力 | 本项目判断 |
| --- | --- | --- |
| PP-Human 的 PP-LCNet_x1_0 人体属性权重 | 接收人体裁剪，提供衣袖、下装、包、帽子、朝向等类别 | 若基础 ReID 暴露可复现问题，优先作为轻量属性候选评估 |
| PP-HGNet_small / tiny 人体属性权重 | 同类任务的不同模型选择 | 只有轻量候选效果不足且资源允许时再比较 |
| InsightFace Gender&Age | 官方模型包提供人脸年龄／性别分析 | 不解决背影缺脸问题，不纳入这条归因链路 |

[PP-Human 官方说明](https://github.com/PaddlePaddle/PaddleDetection/blob/release/2.9/deploy/pipeline/docs/tutorials/pphuman_attribute.md)列出上述人体属性模型。其属性准确率不是成员识别率，速度来自 V100 上 TensorRT FP16 的模型推理，不能当成本机 Mac 的端到端耗时。官方标签没有通用衣服颜色分类，不能直接承诺“黑色上衣”等输出。PP-LCNet 是网络结构名称，应选择对应人体属性权重，不能拿普通图像分类权重替代。

[官方后处理](https://github.com/PaddlePaddle/PaddleDetection/blob/release/2.9/deploy/pipeline/pphuman/attr_infer.py)部分字段通过最大值或二选一产生标签，不能直接把展示字符串当可靠事实。若接入，应保留所用衣着／朝向字段的原始分数，为低分、遮挡、裁剪不完整设置未知；未检出背包不等于确定无背包。[InsightFace 模型说明](https://github.com/deepinsight/insightface/blob/master/python-package/docs/model_zoo.md)用于核对模型包能力，不作为本项目新增人脸属性模型的理由。

### 可能有用的地方

- 朝向用于挑选互补的参照，不能因为同一个人转身就判定身份冲突。
- 衣袖、下装和携带物用于解释或辅助检查候选。衣着不一致可能是换衣，包和帽子也可以取下，单个属性不能直接判为不同人。
- ReID 与属性来自同一张人体图，存在相关误差；不能把两者当成独立证据叠加“置信度”，属性一致也不能让未达门槛的身份自动通过。

### 最小评估方式

1. 先完成基础 ReID 校准，保留它错归或无法区分的有代表性片段。
2. 在同一批原帧人体裁剪上离线评估 PP-LCNet 属性权重，比较“仅 ReID”与“ReID 加可见属性”；不先改在线调度或安装完整 PP-Human 管线。
3. 固定模型资产、许可、预处理和输出标签映射。若转换到 ONNX，核对转换前后分数及标签一致性，再测本机预处理、推理总延迟与内存；现有 ONNX Runtime 不代表该权重已可直接运行。
4. 用独立素材检查是否减少错归、是否只是增加未知，以及背影、遮挡、低光和换衣的表现。没有实测增益就不接入。
5. 只有验证有收益后，另定原帧裁剪保留、触发时机与计算预算。届时属于新增模型调用，不能继续套用首期“不增加推理次数”的承诺；不因本节提前创建模块或配置。

不含测试，预计新增 450–700 行、修改 200–350 行，涉及约 12–18 个文件。下表为新增与修改的合计估算，不是已确定的差异量，也不是必须达到的行数预算。
