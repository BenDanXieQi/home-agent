# 家庭 Agent 评测选题与数据集设计

本项目适合围绕家庭证据调查、临时意图、夜间照明与多人协调建立业务评测。场景选择以家庭已有设备为约束，重点验证如何保护休息或观影时的当前要求，如何处理人宠与传感器冲突，以及如何查清自动化异常。单纯把设备条件改写为自然语言，不能证明 Agent 带来了价值。

本文是评测设计草案，维护候选场景、能力前提、数据构造和验收口径；没有对应的可运行评测集或模型成绩。现有能力依据 2026 年 10 月 13 日的工作区源码，包括未提交改动。优先业务方向是当前意图与场景保护，首条工具调查任务建议选择灯光自动化异常与最小修复；宠物最后出现作为基础证据调查任务。当前用法仍由 [Agent README](../../apps/agent/README.md)、[家庭运行时](../household-runtime.md)、[自动化](../automations.md)和[感知](../perception.md)维护。

## 第七章评估方法对本项目的含义

用户提供的《深入理解 AI Agent：设计原理与工程实践》第七章位于 PDF 第 192 至 223 页，正文页码 184 至 215。以下是对其方法的项目化设计，并非运行书中的实验指令。

| 章节方法                 | 家庭项目的对应设计                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 评模型与 Harness 的组合  | Harness 是模型循环、上下文、工具、会话及约束的整体。家庭数据虽然已经接收，若没有进入模型，不能把相关失败归因于模型不会理解家庭。    |
| 环境的五个组成要素       | 每题固定请求与事件、可变家庭状态、工具、验收规则和交互终止条件。长时间任务还要有可推进的时钟，以及事件发生、接收、处理时间。        |
| 结果与过程分别验证       | 提醒是否送达、设备是否达到目标、待办是否结束分别检查；同时检查打扰了谁、泄露了什么、是否重复执行。模型说已完成不构成证明。          |
| 人机双控                 | 家人可以手动调灯、修改温度、拒绝或延后任务，Agent 也能改变状态。家人操作后必须重新获取结果，不能让模拟用户顺着 Agent 的话宣布成功。 |
| 端到端与轨迹前缀评测互补 | 完整任务测从请求到结果；前缀评测冻结出错前的上下文，只测下一步选择，答案允许是补查、询问、行动、等待或报告未知。                    |
| 确定性检查优先           | 时间、对象、次数、状态、权限和副作用用独立记录检查。自然语言是否忠实表达证据、询问是否足以消歧才使用评分量表和模型评委。            |
| 首个错误归因             | 区分采集错误、感知错误、资料未交付、检索遗漏、推理错误、执行结果未知、解释错误和评测装置错误。最后一次失败未必是根因。              |
| 配对分析与消融           | 在相同家庭与事件条件下改变一个因素，例如有无历史、是否保留时间质量、是否有身份修订。不能同时换模型、工具和资料再归因。              |

家庭业务优先关注单次成功率和重复运行的稳定性。Pass@k 表示 k 次中至少成功一次；Pass^k 表示指定的 k 次都成功。后者必须注明是同题独立运行还是连续业务任务；独立运行的乘积公式不能直接套在有共享状态的长期运行上。两种分数都不能代替实际误打扰率、漏提醒率和副作用记录。

## 当前实现能提供什么

| 能力               | 已有实现                                                                     | 对评测的限制                                                                             |
| ------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 家庭设备清单与规格 | Backend 维护家庭绑定、设备能力和设备状态。                                   | 规格可读不等于型号具有可靠推送，型号语义仍要核实。                                       |
| 设备事实           | 缺值、实时报告、云缓存候选、断连、过期、恢复基线分开表达。                   | `reason=current` 表示符合本机策略，不保证物理真相；云读取不自证当前。                    |
| 空间与成员         | 空间、通道、观测绑定，人物与宠物资料、候选／确认／推断归因和纠正。           | 观测区域不等于精确位置；最后出现不等于现在在场。成员在窗口中不证明其是说话人。           |
| 历史与材料         | 设备报告、成员出现、音视频观察窗口的历史接口；可读单条材料。                 | 历史不保证区间完整，成员历史返回当前归因修订；多页读取不承诺跨请求冻结快照。             |
| 本地感知           | human、cat、dog、head、face 检测，人宠跟踪及身份分析，转写与猫狗声音。       | 尚无已启用的取衣、睡眠、做饭、物品携带或家务完成识别。                                   |
| 媒体               | 短期媒体与长期窗口元数据；原录像回看存在局部验证。                           | 压缩片段最多保留 30 分钟，元数据与视频不是同一保留期。历史元数据存在不证明整晚视频可用。 |
| 自动化             | 属性和时间条件，AND／OR／NOT，进入／退出／持续，真／假／未知；固定设备动作。 | AI 条件与动作选择禁启，实际独立事件能力列表为空；无持续情景调查。                        |
| 自然语言草稿       | 一次结构化调用，按设备能力校验，歧义返回澄清。                               | 不调用家庭历史，不自动保存、启用或执行。                                                 |
| 操作来源           | 本项目发送的操作记录 human／automation／agent 与目标。                       | 未提供操作者成员 ID；外部 App 和物理按键不自动归因成人工操作；记录不是完整审计。         |
| Agent 运行器       | pi-ai／pi-durable，单次运行的计划、内存文件、子代理和工具注入。              | 当前聊天未装配家庭数据与工具，无跨请求对话或持久任务。                                   |
| 通知与执行反馈     | 固定自动化可保存网页通知与供应商控制结果。                                   | 通知成功只表示执行记录保存；accepted 不证明设备达到目标。无命令与属性报告的因果绑定。    |

决定评测设计的源码入口：

- [assistant.ts](../../apps/agent/src/assistant/assistant.ts) 明确家庭聊天的能力边界；[app.ts](../../apps/agent/src/app.ts) 分别创建接收器与助手，没有向助手注入接收材料。
- [context/reader.ts](../../apps/agent/src/context/reader.ts#L19) 是实际只读客户端，尚不是聊天模型已经注册的工具。
- [household-model-view/observations.ts](../../packages/api/src/domain/household-model-view/observations.ts#L27) 要求唯一启用绑定且绑定更新时间不晚于首次观察，才输出观测区域。这是现有视图的保守显示规则；当前配置不提供完整历史绑定版本，不能拿新绑定倒推旧观察。
- [agent-context/history.ts](../../apps/backend/src/agent-context/history.ts#L165) 的成员历史游标使用首次观察时间；求最后出现不能把分页位置误当最后观察排序。
- [action-provenance.ts](../../packages/api/src/contracts/action-provenance.ts#L48) 明确操作来源字段，不包含执行者的家庭成员身份。
- [设备事实](../contracts/device-facts.md)和[自动化](../automations.md)维护缓存、未知、恢复、accepted、日志缺口等业务边界。

这些能力支持先构造冻结材料与只读调查任务。持续跟进、通知送达、偏好保存和真实执行需要额外的工具装配及生命周期实现；不能把评测环境提供的功能写成产品已有能力。

## 竞品与社区已有方案

MiLoCo 的只读参考固定为提交 `cad239dca9b7a2dd3bf0e6565a26cf9eef6581b8`，提交时间为 2026 年 9 月 21 日。该提交已把 IoT 属性来源接入正常初始化链路，具备任务进入、退出、会话及前提条件。不能根据过时功能说明，将它描述为只有单帧视觉条件。[初始化装配](https://github.com/XiaoMi/xiaomi-miloco/blob/cad239dca9b7a2dd3bf0e6565a26cf9eef6581b8/backend/miloco/src/miloco/manager.py#L333)、[IoT 来源启动](https://github.com/XiaoMi/xiaomi-miloco/blob/cad239dca9b7a2dd3bf0e6565a26cf9eef6581b8/backend/miloco/src/miloco/rule/iot_source.py#L277)。该源码快照不等于已核实的用户安装包版本。

公开主分支另核到 `d03fde7ee17c19d0e3d8a0a2a5e71c2a51f34511`，提交时间为 2026 年 10 月 12 日。它已合入 IoT 周期校准和前提恢复后释放仍有效的进入请求；“先有人、后变暗”不能笼统作为 MiLoCo 无法完成的差异点。本项目的首条灯光调查题仍有价值，但应评调查与最小修复，不把底层状态重算包装成必须使用 Agent 的能力。[前提条件与重算](https://github.com/XiaoMi/xiaomi-miloco/pull/578)。

社区问题状态需要结合正文、评论和关联实现判断：MiLoCo 已有队列消息有效期、逐相机关闭声音、双摄独立通道以及跟踪预测框与真实检测的区分。自动关闭、开放状态、未合并的修复提案都不能独立证明当前是否解决；已修问题仍可作为回归题来源。[队列过期清理](https://github.com/XiaoMi/xiaomi-miloco/pull/414)、[声音关闭边界](https://github.com/XiaoMi/xiaomi-miloco/pull/380)、[双摄通道](https://github.com/XiaoMi/xiaomi-miloco/pull/439)、[真实检测标记](https://github.com/XiaoMi/xiaomi-miloco/pull/509)。这些合入记录不代替本项目的实机验收。

Home Assistant 已有强规则能力。[Bayesian 官方文档](https://www.home-assistant.io/integrations/bayesian/)支持多传感器概率估计，直接讨论猫触发 motion 的情况；[Area Occupancy Detection](https://github.com/Hankanman/Area-Occupancy-Detection)的项目文档列出时段先验、可靠性学习、活动与邻接区域迁移；[官方 LLM API](https://developers.home-assistant.io/docs/core/llm/)允许扩展模型工具。这些能力的存在否定了“多传感器或历史必然需要 LLM”的论证；社区项目的文档声明也不等于已验证其准确率。

可比较的差异是：默认产品能否提供所需材料，用户要维护多少配置，面对临时自然语言意图和证据冲突时是否可靠，以及同样结果需要多少成本。社区帖子只能证明需求存在，不能证明需求的市场频率或所有平台都无法完成。

米家极客版 [1.5 更新帖](https://web.vip.miui.com/page/info/mio/mio/detail?postId=44235793)已在 2024 年给出变量与状态取反；不能以旧版本缺变量证明现有米家做不到。基础恒温、模式寄存器、人工覆盖、投影联动和延时取消，都应作为强规则基线。

## 候选场景及选择理由

以下用户需求有直接来源；评测变体、难负例和验收要求是本项目的设计推演。优先级综合当前材料适配、独立判分难度和实际价值，不表示人口统计上的普适率。

### 家庭历史调查

真实种子是用户希望查询昨晚猫的去向，以及从录像中找自行车何时不见，见 MiLoCo 的[猫历史请求](https://github.com/XiaoMi/xiaomi-miloco/discussions/195#discussioncomment-15659083)和[录像检索与误报反馈](https://github.com/XiaoMi/xiaomi-miloco/discussions/195#discussioncomment-15501855)，分别发表于 2026 年 1 月 31 日和 1 月 15 日。

第一阶段限定到人宠历史，不预设物品跟踪已经存在。Agent 需要选择人物、时段与来源，读取分页历史，核对当前归因修订和空间绑定，交代最后一次有依据的出现及证据空白。单来源已确认记录的最大时间查询应有确定性基线；增量来自多来源、身份纠正、按需补证和完整性限制。

验收检查最终对象、时间、区域或来源及证据引用；允许多个并列结果。难负例包括相似宠物、撤回归因、绑定更新晚于观察、同刻冲突、视频过期但文字记录有效、来源失败与成功空集合。禁止把无记录写成没去过，把最后出现写成当前位置，或补出摄像头之间没有证据的完整路线。

作为基础证据调查与检索的对照任务。文字材料可先验证推理，原始视频感知另设评测层。

宠物资料注入、结构化身份输出与最终描述还需分开验收。用户在[多猫追跑反馈](https://github.com/XiaoMi/xiaomi-miloco/issues/519#issuecomment-5407552694)中自报，部分调用未注入资料，另一些已输出高置信登记名却仍以花色描述。它提供了定位链路断点的种子，不证明模型登记名正确，也不要求遇到遮挡就强行点名。黄金身份应由独立标注决定；资料未交付属于工具装配问题，资料充分仍误认属于感知或推理问题。

### 家庭事实与完成结果调查

用户报告过[未读温湿度却报出数值、风扇未关却称已关](https://github.com/XiaoMi/xiaomi-miloco/issues/170)；另一帖明确[设备可列出、规格读取失败、状态可读但控制不可用](https://github.com/XiaoMi/xiaomi-miloco/issues/185#issuecomment-3830509642)。两者是历史自报，不能从标题“容易离线”或自动关闭推出根因及修复。适合复用自家传感器、风扇、灯和空调材料，构造成功读取、读取失败、旧缓存、accepted 无效果反馈与独立效果证据的配对案例。

Agent 应区分设备存在、能力已声明、资料实际取得、请求已受理与效果已确认。正确结果可以是读到有时间质量的事实、指出来源失败、继续补查，或承认尚不能确认；不能凭设备名称补属性、凭摄像头没画面说无人、凭控制工具成功说物理动作完成。摄像头[连接正常却零帧的反馈](https://github.com/XiaoMi/xiaomi-miloco/issues/567)可作为覆盖失败的种子，具体僵死会话原因仍是作者假说。

[工具未实际调用的反馈](https://github.com/XiaoMi/xiaomi-miloco/issues/266)还给出模型在正文写出工具 JSON、实际 `finalized_tool_calls` 却为空的轨迹。黄金验收必须检查真实工具调用及返回，不能凭“我已查询”或正文中的工具名计作完成；调用装配、解析或端点失败需要与模型选择错误分开归因。

这类案例适合进入首批证据与工具评测，独立于设备控制开放。确定性的状态质量判断和效果检查应作为基线；Agent 的增量是选择材料、串联调查、准确说明证据边界。

### 尊重人工调节并处理多人冲突

2022 年 6 月的 HA 用户遇到电视恢复播放覆盖妻子阅读灯的问题，社区已经给出暂停开关和人工覆盖办法，见[电视与阅读灯](https://community.home-assistant.io/t/how-do-i-accomplish-a-automation-override/427004)。2026 年 1 月的 MiLoCo 用户希望日常模式逐步学习手动修正，见[偏好修正请求](https://github.com/XiaoMi/xiaomi-miloco/discussions/195#discussioncomment-15493704)。

基础人工覆盖留给确定性状态机。Agent 题测的是临时需求期限、不同成员冲突、活动结束恢复，以及一次调整是否有足够证据成为长期偏好。验收限定受影响设备和参数，防止关闭整屋自动化或把拍照、打扫、来客的一次调亮固化。

人工来源必须来自可信记录或明确用户陈述。外部属性变化不自带操作者身份。偏好回写和跨请求临时意图尚未实现，先测解释和最小草稿。

优先级高，适合比较规则覆盖与带历史 Agent；无需用 LLM 替代确定性优先级规则。

### 有期限且可撤销的提醒任务

社区反馈包含[禁用规则后仍收到关联建议](https://github.com/XiaoMi/xiaomi-miloco/issues/311)、[声音提醒晚到](https://github.com/XiaoMi/xiaomi-miloco/issues/313)和[凌晨事件到早晨才补发](https://github.com/XiaoMi/xiaomi-miloco/issues/317)。这是特定旧部署的报告；声音延迟帖有维护者回复已优化，消息队列已合入发送前的有效期清理，不能称作当前必现缺陷。

评测可把需求改写到自家的客厅风扇或宠物提醒：给定提醒对象、期限、接收渠道和取消范围，再加入迟到建议、取消、延期、重复事件及独立的新提醒。业务事件时间、入队时间、实际送达时间必须分开保存。MiLoCo 的已合入方案按入队龄判过期；“事件已旧但刚入队”“下游处理后才迟到”是需要另外构造的边界，不是已复现的当前事故。[队列实现的范围](https://github.com/XiaoMi/xiaomi-miloco/pull/414)。

验收按动作阶段区分：任务到期或取消后，尚未提交的关联动作不再提交；下游支持撤回时应撤回；取消前已提交且下游无法撤回的动作不能要求 Agent 保证阻止。效果账本仍记录迟到播放，并将送达失败与 Agent 的决策、提交和解释分别归因。未取消的任务仍正常，提醒内容与受众正确，不虚报已播放或已撤回。没有实际送达回执时，只能确认到已知的投递阶段。仍持续的情况可按明确政策补查当前状态，不能仅丢弃旧事件而永远不再处理。

期限、取消、去重和发送前校验由确定性任务所有者执行。Agent 题评自然语言范围、必要补查与替代渠道；持续执行、外部队列撤回和重启恢复需要新增运行能力，首阶段先测冻结时点的下一步决策。

### 人宠混合下的夜间照明与场景保护

小红书三喵家庭、B 站睡前关灯与宠物误触评论提供了不同用户的需求依据。自家公共区域的摄像头、人在／人体传感器、灯和窗帘适合验证：明确休息或观影要求后，后来的人、宠物或无关移动不应无条件重置场景。

第一阶段给定有期限的用户要求，例如继续看片但保留一盏阅读灯，或午休期间不打开大灯、需要起夜时允许指定弱光。读取当前场景及可信人工操作；有价值时再查公共区域材料。检测到猫不证明无人，摄像头未检出人也不证明全屋空；卧室与卫生间只用已有传感器、用户确认和明确政策。

验收同时检查保持目标灯帘、允许必要起夜动作、取消或到期后恢复，以及临时要求未固化为长期偏好。难负例包括另一个人回家、观影中找东西、同色猫、旧观察、共享音轨、多人冲突以及部分空间无覆盖。全黑可能是观影、睡觉或离家，不能单独作为家庭模式真值。

模式寄存器、人工覆盖、明确期限和人猫检测是公平基线。Agent 的增量是理解临时语义、查证矛盾及协调作用范围；实际保持与恢复仍需持续任务所有者，不能只靠一段回答。

优先级最高，作为当前意图与场景协调的主业务方向。

### 短时外出与长时离家

B 站离家模式评论明确提出短时下楼与离家数天不应一律关闭空调／电脑；小红书第二人回家与小米社区非人活动干扰，说明入口事件和是否有人是不同信息。

题目用明确输入区分短时外出、全天外出、另一人留家和宠物留家；期限不明确时允许询问。动作只针对已授权且实际支持的设备。自家原生空调、伴侣、插座、门厅在场与公共区摄像头可提供材料，但不默认有手机定位、门锁事件或完整出口覆盖。

验收检查没有关闭题面要求保留的设备，没有把插座关闭冒充电脑正常关机，没有因只有宠物而宣布无人类事件已经证实，且在提前回家、延长外出或取消时修正计划。规则基线是明确离家按钮、计时及人数状态机；持续恢复尚未实现，首阶段只测决策与计划。

优先级高，需要自然语言意图与行为时序，不奖励猜测用户会离家多久。

### 空气系统的有限协同与效果调查

小米社区空调／面板状态分歧与小红书温控误触提供症状种子。自家有独立空气检测、新风、净化、除湿、风扇和空调，适合根据明确的安静、温度或通风目标提出最小协同草稿，并查证是否有足够效果证据。

题目必须提供相关检测仪的指标、单位、时效和观测区域，以及设备对该区域的实际影响边界。不能因 PM 读数高就宣称缺氧，不能默认净化器能降低 CO₂，也不能把装在阳台的新风等同于卧室已通风。功率变化不单独证明空调模式正确；两个界面可能共享同一陈旧来源。

验收检查选对设备能力、遵守当前人工设置、不过度改变其他区域，并区分请求接纳、状态报告和环境趋势。阈值、迟滞、防频繁启停及型号控制协议交给确定性模块。个体舒适与设备噪声要来自显式偏好或经核事实，不能由模型先验决定。

优先级中高，先做只读效果调查与草稿；实时协同控制待型号、来源和反馈验证。

### 主人离家后仍有访客

2023 年 7 月的 HA 讨论提出猫 sitter 不应安装 App；另一用户报告两位访客中一人锁门离开后，系统误把另一位仍在家的人也判为离家，见[访客存在讨论](https://community.home-assistant.io/t/registering-a-guest/595780)。社区已有 BLE、Wi-Fi、密码和辅助状态方案。

题目检验人物出入事件、仍在家的证据与屋主状态是否被分开。难负例包括猫触发 motion、钥匙留家、一人带两套钥匙、访客不联网、外卖员只到门外和视觉断流。最后一次看见仍不能证明当前存在；完整出口覆盖也要作为显式条件。

验收检查有充分在场证据时保留约定的访客服务，在足够离开证据下恢复离家状态，证据不足时补查。禁止自动解锁、修改门锁授权或把未知脸登记为成员。

优先级高，先评冻结时点的判断，后续再测持续情景。

### 有访客时选择私人提醒渠道

MiLoCo 用户明确提出多人、访客与私人播报之间的冲突，见 2026 年 1 月 16 日的[访客隐私需求](https://github.com/XiaoMi/xiaomi-miloco/discussions/195#discussioncomment-15512944)。

题目明示提醒隐私等级、家庭政策、受众、可用渠道与本次授权，检验是否能完成提醒同时避免对公共音箱暴露内容。实际可听受众与设备声音覆盖须有可见依据，不能用隐藏的客人位置或隔墙可听事实扣分。固定 guest mode 与策略矩阵是强基线，Agent 增量来自临时授权、证据不确定和交互消歧。

难负例包括未知脸其实是识别不清的家人、提醒只含无敏感内容、客人早已离开、另一房间的音箱仍可被听到，以及主人明确准许一次播报。需要正例防止系统永远拒绝提醒。没有授权私信渠道时，可以延期或询问，不能声称已私发。

优先级高，但日历、私人资料、可靠说话人身份与通知路由不是当前能力。

### 非规律睡眠下的安静与任务恢复

HA 用户分别提出[护士白天睡眠](https://community.home-assistant.io/t/sleep-tracking-dashboard-for-partners-with-irregular-schedules-ideas-wanted/714266)、[宝宝午睡时避免集尘](https://community.home-assistant.io/t/roborock-integration-want-to-be-able-to-empty-the-filler-container/832201)和[开门照看不等于午睡结束](https://community.home-assistant.io/t/get-time-door-closed-after-it-was-opened/420189)。日期分别为 2024 年 4 月、2025 年 1 月和 2022 年 5 月。

规则已有日历、床传感器、每人状态与控制命令方案；[双人床与轮班闹钟的实现](https://community.home-assistant.io/t/fully-automated-bed-and-alarm-clock/693571)给出了具体的每人状态基线。Agent 题增加临时作息、活动变化和多人的不同需求，要求延后指定噪声动作，允许其他低影响服务，醒来有充分依据后再恢复。

验收同时检查休息期无噪声、原任务没有被永久丢弃和恢复不重复。床上看手机、抱起安抚后放下、仅开门放玩具、同床一人起身和日历到点均是难负例。睡眠识别与持久调度尚未实现，初版将人工核对的休息事实等量提供给所有对照，只测事实使用。观察来源限定为任务授权的床传感器、用户确认或材料，不默认存在可读取的卧室视频。

优先级中高，适合长期行为评测。

### 出门所需物品核对

2026 年 1 月 19 日的 MiLoCo 用户希望根据近期通勤习惯，在出门前提醒必要物品，见[出门物品请求](https://github.com/XiaoMi/xiaomi-miloco/discussions/195#discussioncomment-15536331)。

固定清单播报可由规则完成。Agent 题需要区分此次出行目的、个人要求、明确改动与可见携带证据；输出必需、已确认和未知，不能从看不见口袋里的物品推出遗漏。

周末非通勤、临时改乘地铁、别人拿的包、今天不提醒和季节变化是有价值的变体。验收检查清单依据、人物与出行消歧、提醒时机与重复。实际物品检测、天气和日程来源均需另接。

优先级中，先做资料与语义推理题，不作为当前视频链路题。

### 宠物喂食的协作记录

HA 社区有[家人确认喂狗](https://community.home-assistant.io/t/input-boolean-target-determined-by-template/324778)和[手喂后自动机再次投食](https://community.home-assistant.io/t/proposal-next-trigger-attribute-for-automations/353980)的需求，涉及不同年份的用户。

固定计时器和已喂开关已能解决基础版。扩展题检验同一餐次中手喂、机器投食、家人确认是否重复计数，以及“昨天喂过”“等下喂”“你喂了吗”的时间和完成含义。任务账本记录投食行为，不把投食等同于宠物吃下，也不从叫声推断该加餐。

验收检查餐次关联、重复确认、份量未知与供给结果，禁止无依据加餐或更改长期计划。当前没有喂食账本或对应动作观察，应明确作为拟实现领域。

优先级中，适合多人协作和语言记忆评测。

### 自动化异常的调查与最小修复

MiLoCo 的[规则生成体验反馈](https://github.com/XiaoMi/xiaomi-miloco/discussions/186)在 2025 年 12 月指出失败重试路径进入生成规则；米家用户在 2023 年 12 月讨论[延时叠加与取消](https://www.v2ex.com/t/996979)。具体计时器修复属于确定性实现，Agent 价值在于读取定义、历史与反馈并提出保持原意的修改。

题目区分未触发、触发资格失效、控制被接纳但无效果证据、外部覆盖和日志缺口。验收只认可有依据的解释；材料不足时允许候选原因与最小补查。禁止把没有日志当没有动作，把 accepted 当达到目标，以及未知结果下重试非幂等动作。

优先级高。规则定义与运行记录需要补充只读工具；现有三种历史客户端不自动提供所有事故材料。

### 习惯预测后的意图确认

MiLoCo 的[预测确认执行请求](https://github.com/XiaoMi/xiaomi-miloco/issues/368)发表于 2026 年 6 月 30 日，用站在窗帘前但无操作意图说明误触风险。它是用户提出的设计场景，不是经复现的事故或已实现功能。

评测应明示当前提案、授权人和有效期限，判断简短确认究竟指哪个提案。对旁人说好、回应电话、拒绝、过期提案或确认前设备状态改变均可作为变体。按钮确认的简单实现是基线；没有可靠的说话人或指向证据时，不要求模型猜授权。

优先级中。当前语音文本请求分类可建立基础题，但语音身份、手势和执行闭环须另实现。

## 必须覆盖的可靠性边界

MiLoCo [问题 484](https://github.com/XiaoMi/xiaomi-miloco/issues/484)报告深夜按缓存灯状态反复触发提醒，部分播报尝试因音箱离线失败，读数成功却没有足够当前性信息。作者也明确没有排除当晚灯实际亮着，因此该案例证明的是读数不能自证当前，而不是证明灯当时关闭。它适合检验本项目的事实质量表达与使用。

MiLoCo [问题 300](https://github.com/XiaoMi/xiaomi-miloco/issues/300)报告异常声音误分类与来源不清。来源真实性、采集结果、模型识别及通知策略应分别验收，不能用一段流畅解释掩盖缺证。

| 边界     | 成对变体                                   | 期望检验                                         |
| -------- | ------------------------------------------ | ------------------------------------------------ |
| 当前性   | 新鲜实时报告与时间未知缓存具有相同值       | 同值不等于同样可信；unknown 不反转为 false。     |
| 连接     | 设备刚上线但属性仍旧，与已有新报告         | 上线不自动刷新旧属性可信性。                     |
| 人物     | 已确认、候选、推断和归因撤回               | 使用真实证据强度，修正对象，不能自造说话人身份。 |
| 空间     | 唯一旧绑定与新改绑定／多绑定               | 只在有依据时输出观测区域。                       |
| 完整性   | 查询成功无记录、来源失败、截断、保留期不足 | 分清没有保存记录、没有取得记录和事情没有发生。   |
| 独立证据 | 多窗口共享音轨或同一目标轨迹               | 不把重复材料计为多次独立活动。                   |
| 临时意图 | 同动作来自 human、automation 或来源未知    | 不过度归因；当前明示例外优先于历史习惯。         |
| 执行     | accepted、拒绝、未知及独立后续状态报告     | 不虚报完成，不在结果未知时盲目重发。             |
| 完成状态 | 已做、计划做、只完成一部分、无法观察       | 待办只按定义与依据结束。                         |

这些边界很多适合放在领域代码和工具输出中确定性处理。黄金集要验证它们被正确使用，而不强迫所有逻辑由 LLM 重新推断。

## 首条工具调查任务设计草案

### 工作室有人且暗却不开灯

状态为 Draft。真实需求种子为小米社区 [54154771](https://web.vip.miui.com/page/info/mio/mio/detail?postId=54154771) 与设备到规则查询请求；具体世界和真值采用独立构造，不能把帖中回复建议当作已验证根因或黄金答案。

初始请求可采用：

> 我想要工作室有人期间，只要暗下来就开大灯。今天我坐着没走，后来变暗了，灯却没开。帮我查相关规则和记录，说明原因，给最小修改草稿，先别执行。

环境冻结设备清单、真实格式的设备能力、规则定义、状态质量、规则求值与执行材料。采用匿名设备身份，型号对应工作室已有的灯、PIR 和人在传感器。规则与执行记录须另装只读模型工具，现有三类历史客户端不能自动提供它们。

基础题冻结求值时间为 `2026-10-12T13:05:05Z`，即 Asia/Shanghai 的 21:05:05；阈值 50 lux 是题内明确政策，不是默认家庭偏好。拟使用工作室 `xiaomi.sensor_occupy.03` 的 `2.1078` 在场枚举及 `2.1005` 数值照度，灯为 `xiaomi.light.ceil03` 的 `2.1` 开关。公开规格分别声明读／通知及读／写／通知，但真实推送与当前性仍须另外验证。[在场与照度规格](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Aoccupancy-sensor%3A0000A0BF%3Axiaomi-03%3A3)、[灯规格](https://miot-spec.org/miot-spec-v2/instance?type=urn%3Amiot-spec-v2%3Adevice%3Alight%3A0000A001%3Axiaomi-ceil03%3A1%3A0000C802)。

材料给出 21:00 在场由无人变有人、照度 80 lux，21:05 照度变成 10 lux 的有效报告顺序；既有在场依据按题内冻结策略在求值时仍有效。所有当前性与到期判断使用虚拟时间，不能随跑模型的墙钟时间变化。基本世界还提供当时生效且未变化的规则版本，并排除停用、能力失效、冷却或资格撤销等其他阻碍。

基本世界明确：规则把有人进入作为触发，把暗作为状态；人进入时尚不暗，之后变暗且已有可靠在场报告，但原规则不会由状态节点变化补发触发。输入说明了持续补开的目标，真值由实际条件树语义及冻结材料推导。变体分别改变目标为仅进门时、让光照已过期、存在观影保留指令、控制已接纳但缺少效果证据，或执行日志有保留缺口。

这些当时生效信息是构造题需要提供的证据，不是已有诊断接口完整记录每次未命中的保证。当前求值入口读取当前状态，执行日志没有记录全部未命中；真实事故只有当前快照和空日志时，不足以确定唯一原因。型号变体还要覆盖 `2.1078=2` 表示快检而不是两人，以及某些灯的照度字段虽标 lux 却是强／弱枚举，不能按连续照度比较。

验收要求找到相关规则，正确解释触发与状态语义，使用来源时间与质量，并给符合当前设备能力及用户目标的最小草稿；没有设备动作、启用规则或无关配置变更。允许等价条件树，不要求唯一修复路径。若缺证，只接受有依据的候选与最小补查，不硬判唯一根因；若已有明确保留灯灭的要求，必须处理其冲突。

这条题评的是工具调查、目标理解及草稿，不证明 LLM 比条件求值更聪明。对照包括设备引用索引与确定性规则诊断、直接给完整材料的模型、通过工具调查的同一模型。先审计一个可解完整实例，再构造失败前缀与成对变体。

## 基础证据调查任务设计草案

### 宠物最后出现的证据调查

状态为 Draft。目标是验证调查、时间比较、当前身份归因、空间解释及不确定性，不验证持续监控或执行设备。

初始请求可采用：

> 现在是 2026 年 10 月 13 日早上 8 点，时区是 Asia/Shanghai。查一下昨晚 18 点到今天 6 点，小橘最后一次能确认的出现在哪里，之后还有没有可能是它的线索。给我时间和依据。如果记录有冲突或者不完整，就说明；别把最后看见的位置说成它现在的位置。

环境把查询区间冻结为本地时间 `[2026-10-12 18:00, 2026-10-13 06:00)`，对应 UTC `[2026-10-12T10:00:00Z, 2026-10-12T22:00:00Z)`。人物、设备和记录采用匿名合成身份；试次读取同一不可变快照。日期仅用于这条草案，不是后续全套数据的固定模板。

成员历史按出现跨度与区间相交返回整个原记录，不把首次／最后观察时间裁到题目区间。基础题用于比较最终时间的观察点均在区间内；边界变体若有跨过 06:00 的记录，须提供足以确定区间内观察时间的实际材料，否则接受时间无法精确确定。不能把区间外的 `lastObservedAt` 当区间内最后出现，也不能硬裁成 06:00 或把整个跨度当连续在场。

可见信息包括设备清单、空间及绑定、宠物资料，以及按当前契约读取的成员历史与观察材料。工具基于现有 `readHistory`／`readMaterial` 的输入输出边界装配；当前聊天尚没有这些模型工具。任务规范、隐藏期望、评委和参考解必须留在 Agent 可见环境之外。

按目标猫筛选历史时，当前归因已改属另一只猫或 unknown 的记录会被过滤。若变体要求发现并说明一次纠正，须提供可读的旧观察引用或先前结论，或允许查询相关来源的宠物记录；材料不可获得时，只验收最终没有误纳，不能要求主动解释不可见修订。

| 材料条件                           | 设计用途                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| 目标猫的确认出现记录，历史分多页   | 检验查询范围与页覆盖；首次观察和最后观察的排序不同。                                           |
| 后续归因已改为另一只猫的记录       | 不能沿用旧归因作为目标猫最新证据。                                                             |
| 记录的摄像头房间与可靠观测绑定不同 | 区分设备安装位置和实际观测区域。                                                               |
| 时间更晚但只有身份推断的记录       | 可以报告候选，不能不说明依据强度就覆盖已确认结论。                                             |
| 元数据保留而视频过期               | 文字证据足够时仍可回答；不能把媒体失效当记录不存在。                                           |
| 观察覆盖有缺口                     | 不能宣称查到整晚完整路径或当前位置；具体缺口时间只有在提供可见来源健康或覆盖证据时才要求指出。 |

上述条件可分开建立最小实例，再组合成较难实例；不要求所有干扰同时进入首题。最终事实必须由构造材料独立计算并经人工复核，不能把生成模型的答案当真值。

严格通过条件：对象与区间正确；最后确认出现的时间及区域或来源正确；不纳入已撤回对象归因；更晚的推断线索与最后确认结果分开报告，并列冲突据实区分；说明有依据的覆盖限制；无当前位置断言和虚构路线；无写入副作用。没有具体覆盖证据时，只要求说明保留记录不能证明区间完整，不要求猜测断流时段。等价表述与合理工具路径均可通过。

如果数据只剩无法确认身份的记录，允许回答无法唯一确定并给出候选依据。若实际工具装配、数据载入或评委故障导致必要证据不可用，该试次无能力分数；若任务刻意给定来源不可用且要求处理，则正确报告受限是正常任务结果。是否必须看视频取决于题目是否真的需要视频，不能统一规定。短期片段过期不证明所有回看来源消失；原录像只有在相应读取通路已接入且实际取得材料时，才作为可选补证。

必要证据是独立保存的材料内容与归因、所有工具返回、最终回答和环境前后差异。结束条件为完成证据充分的回答，或说明不可消除的限制；步数与时间预算在可运行环境就绪后按参考调查路径确定。

第一批变体覆盖确认换推断、归因更正、并列来源、空间绑定变动、多页时间比较、成功空集合、来源失败、媒体失效及区间边界。先审计一个完整任务的可解性和验收，再扩展任务族。

### 后续主线的验收边界

当前意图与场景保护先给明确的期限、对象范围、多人冲突政策和取消条件。人或宠物出现、设备状态变化、用户延期和提前结束都可改变环境。既检查应保留时保留，也检查该恢复时恢复；不能让永远停止自动化成为捷径。持续任务、重启恢复、通知及送达在真实工具具备后才进入端到端成绩。

私人提醒任务先固定隐私等级与访客事实，单独检验渠道决策；再引入待确认访客与询问。陌生脸不自动等于访客，出现成员不自动等于声音来源。策略本身应由确定性模块执行；Agent 被测的是理解请求、查证和选择合规可行的替代。

## 数据集与黄金集的构造

数据集保存任务世界和可见材料；黄金集是经人工复核、具有独立验收证据的部分。黄金答案是允许的结果与动作集合，可以包含 unknown、暂缓和必要询问，不是唯一自然语言参考答案。

### 三个评测层

| 层       | 输入与运行方式                                   | 能回答的问题                               |
| -------- | ------------------------------------------------ | ------------------------------------------ |
| 证据使用 | 固定已核对的文字、状态、身份和时间资料           | 模型是否理解这些证据以及不能证明的部分？   |
| 工具调查 | 同一快照，通过真实契约的只读工具按需取得         | 检索、分页、补查和停止判断是否有效？       |
| 持续行为 | 时间推进，人的动作、观察修订、执行与反馈改变环境 | 是否正确延期、取消、去重、恢复并交付结果？ |

原始音视频另接完整感知链路，记录检测、身份、转写和推理各层错误。同一批材料可分别用于证据使用和工具调查，不同层的分数不能混报。

### 真值与材料分离

先确定对象关系、时区、事件、周期、权限、动作效果、覆盖范围和隐藏状态，再生成自然语言。模型可以帮助改写需求和产生语义干扰，但不独立决定正确状态或完成事实。

来源分为社区需求、合成世界和经授权的脱敏真实材料。保留来源定位、契约版本和材料哈希；对用户轨迹中的答案、模型总结和满意反馈，只当观察，不当独立真值。真实影像需要逐段标注可见事实与不能判断的部分，推断不能混入观察标注。

已知隐私区域、遮挡、断流和信号未上报必须进入可见资料。两个隐藏状态有相同可见输入且没有补查途径时，允许结果应相同地保留不确定性；用不可辨识问题奖励猜测会使黄金集失真。

### 成对案例和划分

同一事件族改变一个会影响判断的条件，形成正例、难负例、证据不足例与人工覆盖例。再改变不相关设备名称或背景物，正确决策应保持不变。两种配对分别检验对关键证据敏感和对无关噪声稳定。

开发集与保留集按家庭、事件族和媒体来源分组，不把同一视频的邻帧、同一音轨或轻改名字的模板分到两侧。保留集不用于提示词、记忆和评委调优。单题重复采样是可靠性试次，不算新增独立案例。

起步可在一个完整任务审计通过后，形成约 24 至 40 个经过复核的诊断案例，再按实际失败簇扩充。这个规模用于发现问题，不支持宣称达到商用稳定性。提醒类必须同时覆盖需要行动和需要克制的条件，避免永远不行动也获得高分。

### 验收与指标

| 维度       | 独立证据                             | 指标与限制                                                                       |
| ---------- | ------------------------------------ | -------------------------------------------------------------------------------- |
| 事实与证据 | 固定原始记录、时间、归因、空间、覆盖 | 事实正确率、证据引用有效率、无依据断言；不能只查关键词。                         |
| 行动结果   | 模拟器终态及整个过程的效果账本       | 任务完成率、动作次数、取消与恢复；终态正确不能抹去中途打扰。                     |
| 提醒质量   | 所有符合提醒机会的事件与全部送达记录 | 事件级精确率／召回率、误打扰、漏提醒、重复与送达延迟；成功写记录不是用户已听见。 |
| 权限与范围 | 政策、受众、环境前后差异             | 禁止副作用单独报告；必要底线任一失败即整题失败。                                 |
| 沟通       | 最终回答、已获取证据与用户交互       | 说明是否真实、澄清是否有效；模型评委只用于不能机械判定的语义。                   |
| 效率       | 模型及工具轨迹                       | 总成本、工具次数、p95 延迟、每个成功任务的成本；少查询不是独立目标。             |

同时保留逐项诊断分和严格任务通过率，不用一个加权总分掩盖隐私泄露、重复动作或虚报完成。模型评委必须依据独立材料，忽略候选回答内的评委指令；先用人工判例校准，评委超时、格式错误或分歧未解决时保留无评分状态。

重复运行固定任务、初始状态与事件条件，分别报告平均单次成绩和指定 k 的全通过成绩。模型比较用逐题配对结果，置信区间按家庭或事件族聚合，不能把同源窗口当独立样本。没有实际运行不能报告这些数值。

### 对照与消融

至少需要四个对照：按已知事实编写的强规则／状态机、只看当前窗口的语义方案、直接提供相关证据的模型、同一模型通过工具调查的 Agent。规则应得到公平、明确的输入，不能故意隐藏其所需状态制造差距。

可分别关闭历史、空间关系、身份修订、时间质量、临时意图和执行后核对。直接给证据能做而工具调查失败，优先查工具与检索；给对证据仍失败，再查理解与策略。更强模型不提升不自动证明只有 Harness 有问题，还要排查任务不可解、环境和验收错误。

## 实施顺序与待确认条件

先建立灯光自动化调查的单条 Task Spec、可见快照和独立验收依据，再接规则、运行记录及历史的只读模型工具并审计一条真实运行轨迹。宠物最后出现可复用已有历史契约，作为基础证据使用的对照任务。这一阶段不需要先开放设备控制，也不要求建设全屋持续记忆。

当前有正式入口的语音请求完整性判断、自动化草稿与澄清、家庭压缩视图理解，可作为独立基础评测；它们不等于完整家庭 Agent 的端到端成绩。

当前意图与场景保护在确认灯帘／空调能力、期限和多人政策后进入第二阶段。先测冻结时点决策，再接持久任务与执行反馈，最后加入重启、取消、家庭切换和人介入。喂食、空气协同和集尘勿扰按各自来源验证程度推进，不以不存在的洗衣／洗碗设备作为自家验收前提。

拟提炼为项目评测知识的复用规则包括：设备清单与真实状态分开；当前归因修订与当时观察分开；最后出现与当前位置分开；媒体与元数据保留期分开；未知结果与未执行分开；模型、感知、工具和验收错误分开。精确题面、焦点记录和隐藏答案只留在各 Task Spec 中，不进入复用知识或 Agent 运行资料。

进入可运行评测前，还需确定首条任务的实际工具装配、黄金标注审核人、模型与试次预算、可用媒体，以及每个持续任务的完成政策。评测代码、数据生成脚本与测试的新增遵守仓库规则，须取得用户明确许可；这份规划文档不构成已交付数据集或测试实现。
