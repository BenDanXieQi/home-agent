# Step 4：保存有用历史，能查清发生过什么

**状态：待执行。** 前置条件是 Step 3 已接通真实采集。数据库基础可在 24 小时观察期间准备，保存哪些能力要根据观察结果决定。

[返回总览](../backend-household-perception.md)

本步完成三件事：

1. 按设备能力选择保存全部记录、状态变化或采样点。
2. 在后台批量写入 TimescaleDB，生成趋势摘要，定期清理旧数据。
3. 提供有范围限制的历史查询，让页面能区分“有记录”“没有变化”和“这段不知道”。

当前状态继续由家庭状态机维护。数据库变慢或不可用时，采集和页面上的当前状态照常工作；历史可以暂时不完整，必须说明缺了哪段。切家后不保留旧家庭的采集状态，已经接纳的历史按原家庭身份完成写入即可。

设备历史为[家庭语义模型](../household-model.md)提供证据，本步不做行为推断、长期记忆或可靠告警。一天内少见但重要的门磁、按钮等事件，仍可配置保存。

## 从采集结果到历史记录

### F1、F3：保存已经确认的含义

- [ ] 直接使用 Step 3 规范化并提交的结果，不在数据库写入器中重新解释供应商报文。写入器是应用启动时创建、专门负责批量保存历史的后台模块。
- [ ] 每条观测保存身份、顺序、时间、质量、策略版本和类型化值；物理量必须有明确单位，枚举关联规格，设备事件只保存经过校验的参数。

| 字段组 | 保存内容与用途 |
| --- | --- |
| 身份与归属 | `observation_id`、账号、家庭、设备、能力和采集当时的房间；防止串家庭，并解释当时设备在哪 |
| 来源与顺序 | `source_id`、`source`、`delivery_kind`、适用的 `read_semantics`、`collection_generation`、`scope_epoch`、`input_sequence`、关联的 `state_version`；含义沿用 Step 3 |
| 三种时间 | `received_at` 是后台收到的时间，作为明细表分区时间；`effective_at` 是后台采纳为当前值的时间；`observed_at` 是经过验证的来源观测时间，可以为空 |
| 值与质量 | 类型化值、单位、`quality`、`policy_version`、规格版本 |
| 是否用于当前状态 | 属性保存 `state_applied` 及未应用原因。采纳为当前证据时为 true，并记录 `effective_at`；候选或迟到记录为 false／null。设备事件不冒充属性状态变化 |

同值的可信刷新也可能成为当前状态证据。迟到记录可以保留供排查，但不能画成刚发生的新变化，也不能进入当前状态的统计。

- [ ] **F2：重试不重复入库。** 唯一键包含内部观测 ID 和分区时间，数据库约束须符合实际 TimescaleDB 版本。重试沿用原 ID、时间和归属；只有来源提供可靠消息 ID 时才做上游消息去重。
- [ ] **F9：历史保留当时的解释。** 设备换房只改变之后记录的归属；规格、单位和保存策略变化也保留版本关联，不改写旧记录。

### F5：选择保存哪些记录

保存策略沿用 Step 3 的 `history_mode`，与当前状态更新、规则是否启用分别配置。

| 模式 | 保存什么 | 查询时能说明什么 |
| --- | --- | --- |
| `none` | 不保存正式明细 | 不能重建这段值的经过；可独立启用汇总 |
| `all` | 全部已规范化、未确认重复的记录，包括标明质量的候选 | 结合有效性和缺口，解释后台收到及采纳的记录 |
| `changes` | 初次可信值、恢复后的可信值，以及已采纳值的每次变化 | 证据完整时，可重建后台观察到的状态经过 |
| `last_valid_per_window` | 每个 UTC 60 秒区间内最后一条已采纳的有效数值；初次和恢复后的可信值另存 | 只说明采样趋势，不能证明两点之间没有变化 |

- [ ] 选中保存的连续数值默认采用 60 秒采样；没有有效观测的区间不生成点。布尔、枚举和设备事件不采用这种采样。
- [ ] 数值可以显式配置正数阈值，额外保存相对最近一次已选入历史的有效值达到该差值的观测。阈值单位与能力一致，未配置就不开启；跨缺口重新建立起点，不比较缺口两侧。额外保存大变化仍不等于保存了全部变化。
- [ ] 一条观测命中多个保存理由也只写一次。计时器只结束窗口，不为凑点读取设备或生成观测。恢复时保存同值是为了确认“现在又知道了”，不把它当成物理变化。

## 批量写入与故障处理

### F4：数据库慢了，当前状态仍能用

采集把选中的记录交给一个有容量限制的队列，写入器按顺序批量保存。容量使用 [Step 3 E4](03-collection.md) 的统一限制，正在写但尚未确认的批次也计入。

| 项目 | 默认值 | 达到限制或失败时 |
| --- | --- | --- |
| 批量提交 | 每 1 秒或满 500 条，以先到为准 | 交给数据库；完成前保留该批次 |
| 单次数据库操作 | 5 秒，包含锁等待 | 用数据库或驱动结束操作，再按失败类型处理 |
| 瞬时失败重试 | 从 1 秒逐步增加，最长间隔 30 秒，并随机错开少量时间 | 保留原批次，避免连接故障时反复紧密重试 |
| 正常退出等待 | 最多 10 秒 | 尽量写完；超时报告未确认数量并退出 |

- [ ] 连接中断、超时等瞬时失败按上表重试。提交结果不确定时仍使用同一唯一键，不能换 ID 再写。
- [ ] 入队前完成字段校验。数据库仍发现不可重试的记录内容错误时，丢弃整个失败批次并记录缺口和数量。
- [ ] 表结构、权限等系统性错误暂停写入，公开错误，修复后重启 backend。暂停期间仍受队列容量限制，不启动额外恢复服务。
- [ ] 队列满时拒收新的历史记录，保留尚未确认的批次，并按 F11 记录缺口。历史丢失不改变仍在正常采集的当前值质量。
- [ ] 切家和退出账号后，旧记录仍按原账号、家庭和时间写入；不能因为它已不是当前家庭而改写或误归属。查询时另行校验当前访问权限。

首期不承诺断电或数据库长期故障期间零丢失。错误进入现有 `history_health` 和脱敏日志。

## 记录“不知道”的时间段

历史里的“最后一个值”不足以证明后面一直正常。例如门磁最后一次报告为关闭，随后断线，就不能把整段断线时间都画成关闭。

- [ ] **F10：保存有效性变化。** `validity_changes` 记录来源断开、设备离线、能力过期、可信值建立、策略改变和本轮家庭运行结束。每条记录保留唯一 `change_id`、账号／家庭、影响范围、前后质量、原因、生效时间、提交时间，以及 Step 3 的顺序和策略字段；有关联观测时保存其 ID。重试不换 ID。

有效性与对应观测在同一次状态提交中产生。能力到期时直接记录原定到期时间，不等下一条上报。连接恢复或设备上线只说明通路恢复，值是否重新可信仍按 Step 3 判断。影响范围以变化发生时的设备归属为准。只要保存某能力的明细或汇总，就必须同时保存解释它所需的有效性记录。

- [ ] **F11：保存数据缺口。** `collection_gaps` 记录来源中断、输入丢弃、历史丢弃、进程中断和时间不确定等原因，包含账号／家庭、可确定的来源或能力范围、开始／结束时间、影响明细还是汇总，以及已知丢失数量；不知道数量就明确标为未知。

数据队列满了也要能记录丢失原因。写入器另保留最多 2 MiB 的缺口和有效性记录，数据库恢复后优先保存。同一家庭、同类原因可合并为一段较宽的未知区间；连这部分容量也不够时，扩大到家庭范围，不能为追求逐条精确而无限积压。恢复后先保存缺口，再宣告相关时间段处理完成。仅打印日志不算已保存缺口。

明细丢失不必然意味着汇总丢失：已经独立保存的汇总保留自己的结果和有效覆盖。缺口只影响确实缺少证据的那种数据。

### F12：用完成时间判断重启后哪段不确定

每次家庭运行在 `collection_sessions` 中保存开始时间、`scope_epoch`、最后完成的历史时间和是否正常结束。

- [ ] 每个 5 分钟窗口结束时，先确认设备观测队列已经排空；仍有积压就暂不推进完成时间。随后处理该时间之前应生效的到期变化，结束采样和汇总，把本段明细、有效性、摘要和已知缺口交给写入器，最后排入本段完成标记。
- [ ] 只有前面的记录已经写入，或其丢失事实已经保存，才能更新完成时间。标记无法入队或写入失败时保留原完成时间。`input_sequence` 用于恢复同一毫秒内的处理顺序。
- [ ] 正常停止时结束当前片段并按相同顺序写入结束标记；切家不等待它完成才初始化新家庭。
- [ ] 重启发现上次未正常结束时，把最后完成时间到新实例启动之间保守记为未知；没有完成标记就从上次开始时间算起。已保存的独立汇总仍保留，丢失的未完成部分不重算、不补造。

写入积压会让这个不确定区间变长。没有对应运行记录或必要有效性证据，也不能推断历史连续。页面通过 `history_health` 展示写入异常和尚未确认的时间范围。

## F7：生成趋势摘要

汇总只对明确配置 `metric_kind` 且开启 `summary_enabled` 的能力执行。输入使用采样前、已采纳且质量有效的逐条观测；因此一分钟内温度 20→30→20，即使明细只保存最后的 20，摘要仍能记住收到过 30。

有效初值或恢复值只支持其后的区间，不能补算恢复之前的状态。迟到候选、未知缓存和其他无效值不参与计算。

### 三类数值怎样计算

| 指标类型 | 算法与限制 |
| --- | --- |
| `gauge`，如温度、湿度 | 把每个已知值保持到下一条有效观测、失效时间或窗口结束，以最先到来者为准。平均值为 `sum(值 × 有效秒数) / sum(有效秒数)`；没有有效时长就返回 null |
| `power`，功率 | 先统一为 W，按相同有效区间计算 `sum(W × 有效秒数) / 3600`，得到 Wh |
| `counter`，累计读数 | 只对已经验证单调累计且有明确重置信号的能力启用。相邻可信读数在同一运行、同一策略且中间无缺口、无重置时求非负差，差值计入后一个读数所在窗口 |

这些计算都不能跨断线、过期或待确认区间延续旧值。计时器可以用仍有效的值完成一段统计，但不延长它的有效期。`min/max` 是实际收到的有效观测的极值，不是对物理世界完整极值的承诺。

累计量跨窗口可以沿用上一条可信读数，跨缺口或重置则重新建立起点。无法解释的下降按未知处理，不能自动当成归零。例如 10:04:50 读到 100，10:05:10 读到 110，确认增量 10 计入后一个 5 分钟窗口；它不是精确分摊到每分钟的物理消耗。

### 每个窗口只保存已知的那一段

- [ ] 5 分钟和小时窗口都按 UTC 对齐。5 分钟表以账号／家庭／能力、`window_start`、`scope_epoch` 和 `policy_version` 唯一定位；每行保存本轮运行、当前策略在窗口内实际覆盖的 `segment_start`／`segment_end`。
- [ ] 窗口结束、切家或策略改变时结束当前片段。回到同一家庭也使用新一轮运行标识，不覆盖旧片段。普通来源重连只增加该片段内的未知时间。
- [ ] 保存指标类型、积分分子或确认增量、有效／未知时长、min/max、合格观测数 `received_count`、输入口径和时间轴。窗口完成后作为一个整体写入；重试沿用原身份。摘要依据自身计算和写入结果确认完成，与明细是否保存分别处理。
- [ ] 每次写入 5 分钟结果时，在同一数据库事务中根据该小时已有的 5 分钟结果重算小时行。重试使用替换结果，不重复累加。小时均值仍用总积分除以总有效时长，不平均各窗口均值。
- [ ] 开放的窗口标为暂定（`provisional`）；已完成且成功保存的片段为 `finalized`，表示计算已结束，不表示每秒都有数据。确认丢失计算输入的片段为 `incomplete`，缺少的部分按未知处理。小时仍在收集时保持暂定；小时结束，或本轮家庭运行／策略提前结束时，确认对应的 5 分钟片段已经处理后结束小时片段，缺少输入就标为不完整。
- [ ] 查询合并同能力、同窗口、同策略下不重叠的运行片段；未采集时段只算一次未知，不把每次切家的空白重复累加。不同策略分开返回。片段时间重叠且无法证明先后时，涉及冲突的片段整体按未知返回，不猜测如何扣除局部积分。

内存只保存当前窗口所需的累计量，最多 20,000 项或 4 MiB；到上限时停止为超出部分生成摘要并记录缺口。结束的片段进入已有历史队列，不另建无界等待集合。明细与摘要分别保存、分别说明完整性；不能用已采样的明细重算并覆盖原摘要，也不能在原输入清理后重新猜算。

## F6、F14：保留和清理

按表统一保留时间，不提供逐设备的期限配置。TimescaleDB 按时间分块保存数据，下表的“块”就是清理时整块删除的范围；实际 SQL 按安装版本验证。

| 数据 | 保留期限 | 块长度／清理周期 |
| --- | --- | --- |
| 属性明细 `device_observations` | 30 天 | 1 天／每小时 |
| 设备事件 `device_events` | 90 天 | 1 天／每小时 |
| 5 分钟摘要 `metric_summaries` | 30 天 | 1 天／每小时 |
| 小时摘要 `metric_hourly_summaries` | 365 天 | 1 天／每小时 |
| 诊断观测独立表 | 24 小时 | 1 小时／每小时 |
| 有效性、缺口、运行记录 | 至少 93 天；仍在解释保留数据的记录继续保留 | 定期清理 |

正常清理下，前四表可能比期限多保留 1 天 1 小时；诊断记录约保留 24—26 小时。查询返回这个口径，清理失败进入历史健康状态。诊断录制仍受 Step 3 的一次录制时长和容量限制，不混入正式表。

### 留下解释状态所需的起点

门磁可能连续 35 天没有变化。若只删掉 30 天前那条“关闭”，昨天的查询就会失去起点。因此保留每个属性的一份旧值副本，用来解释查询范围开始前已经是什么状态，称为“值基线”。它不是新上报。

- [ ] 删除属性明细块前，先从即将删除的明细和已有副本中，选出最后一条已采纳属性记录，保存到 `history_value_baselines`；每个账号／家庭／设备属性至多一份。保留原 ID、时间、值、质量、顺序、版本和当时归属，不从当前值倒推。
- [ ] 清理和写入由同一个写入器按顺序执行。先保存基线，再删除对应旧块；保存失败就跳过本次删除并报告错误。不能另开自动清理绕过这个顺序。
- [ ] 这份副本只用于查询起点，不补回明细列表、不计为新观测、不刷新有效期、不重新参与汇总。仍能解释保留范围内的状态时，即使早于 30 天也保留；其所支持的区间完全退出查询保留范围后再删除。
- [ ] 同样保留查询起点之前最后一份有效性状态，以及解释它必需的缺口、运行记录和策略／规格版本。值基线说明“当时是什么”，有效性记录说明“这段是否仍然可信”，两者不能互相代替。尚未结束的缺口不能按创建时间直接删除。

如果无法证明旧值顺序，或被清理的记录实际上仍落在请求的生效时间范围内，就把相应区间标为未知；一份旧值副本不能冒充完整变化记录。长期摘要自身保存有效覆盖、未知时长和统计口径，相关明细删除后仍按原口径解释。

## F8、F13：查询历史

当前值从家庭状态机读取。历史接口读取已经保存的记录，并说明值的来源、时间、保存方式和缺口。

### 先约定“时间”和“完整”

默认时间轴为 `backend_effective`，即后台确认该值生效的时间。只用 `state_applied=true` 的属性记录重建状态；同一毫秒内按同一运行的 `input_sequence` 排序。`received_at` 只用于接收明细和分区，`observed_at` 单独展示来源时间，不混在一条状态曲线上。

查询先找到开始时间之前最后一条值基线和有效性状态，再顺序应用区间内变化，排除数据缺口和 F12 尚未确认的部分。缺少任何必要证据就标为未知。`changes` 可以省略持续有效期间的同值刷新，不能因为最后一条值记录很旧就单独判它过期；以保存的有效性时间线为准。

每个能力的 `value_basis.kind` 说明保存方式：

| 值 | 含义 |
| --- | --- |
| `changes` | 整段都保存全部记录或变化；仍需结合基线、有效性和缺口判断完整性 |
| `sampled` | 区间内采用过采样，只能展示趋势，不能算任意数值条件的准确持续时长 |
| `unavailable` | 区间内未保存或缺少策略依据，不承诺整段重建；优先于 sampled |

“有效覆盖时长”是状态按策略保持可信的时间，不等于“温度高于 28 度”的时间。计算后者需要完整变化记录，并读完该区间所有分页；采样点之间不能自行补成完整经过。

**系统时间异常时停止相关统计。** 若后台系统时钟回跳，停止本次运行的历史区间计算和摘要，报告时间异常并提示修正时钟后重启。当前采集继续，明细保留原时间和处理顺序，不确定的时间段和未保存的开放摘要记为未知，不能算负时长或覆盖已有摘要。运行中的到期判断按实际经过的时长计量，不因系统时钟调整延长有效期。

### HTTP 接口和范围限制

三个 GET 沿用本机访问校验。账号从授权上下文解析，必填的 `home_id` 必须是该账号当前仍有权访问的家庭，不接受任意 `account_id`。设备能力按请求时间内的历史归属校验；设备后来移除或换房，不应让合法的旧历史消失。

`start`／`end` 使用 UTC RFC 3339 毫秒字符串，要求 start < end，查询 `[start,end)`。`capabilities` 是 URL 编码的 JSON 数组，由共享 API 统一构建；属性项为 `{device_id,siid,piid}`，事件项为 `{device_id,siid,eiid}`。

| 接口 | 额外参数 | 返回内容 |
| --- | --- | --- |
| `GET /api/mijia/history/observations` | `time_axis=backend_effective\|received`，默认前者；`limit`、`cursor` | 生效轴返回已采纳属性及状态上下文；接收轴返回含候选、迟到值的明细，不能用于状态曲线 |
| `GET /api/mijia/history/events` | `limit`、`cursor` | 按 received_at 查询设备事件，另带来源时间、交付种类、参数和质量；展示历史不触发即时规则 |
| `GET /api/mijia/history/summary` | `grain=5m\|1h` | 对应粒度的摘要、覆盖、口径和完成状态；缺失值为 null，不能补零 |

| 限制 | 默认／上限 | 超限处理 |
| --- | --- | --- |
| 一次查询能力数 | 1—20 个 | 返回输入错误 |
| 明细／事件跨度 | 最多 7 天 | 要求缩短时间范围 |
| 明细分页 | 默认 500 条，最多 2,000 条 | 用游标继续查询 |
| 状态上下文 | 有效性变化与缺口合计最多 2,000 条或 1 MiB | `context_complete=false`，受影响能力的覆盖标为未知，要求缩短范围 |
| 汇总跨度与点数 | 最多 366 天，所有能力合计最多 10,000 点 | 要求缩短区间、减少能力或选择 1h；不同策略分段也计入点数 |
| 单次 JSON 响应 | 最多 4 MiB，含包络与上下文 | 明细在完整行边界结束并返回游标；汇总超限返回明确错误 |

明细响应为 `{ items, next_cursor, time_axis, history_health, retention }`。生效轴额外返回 `state_context = { baselines, validity_changes, gaps, context_complete, coverage, value_basis }`；接收轴的 `state_context=null`。上下文始终覆盖请求的整个区间，不随本页首末记录缩小；每能力至多一份区间前值基线和有效性基线。旧值副本只放入 baselines，items 只包含尚未清理的实际明细。

分页按 `(selected_time, scope_epoch, input_sequence, observation_id)` 升序，selected_time 由所选时间轴确定。游标绑定账号、家庭、过滤条件和完整排序键，篡改或换条件复用返回输入错误，不能跳过同毫秒记录。多页查询不承诺冻结数据库；写入追赶期间，旧时间段可能新增已确认记录，响应须提示历史未完成，重新查询才能取得它们。

汇总的 start／end 必须与所选 UTC 粒度对齐，不自动扩大范围。返回 `time_axis`、`input_basis`、`retention` 和覆盖状态，区分尚未结束、缺失和已过保留期。累计量须说明是“按后一个读数归属的窗口确认增量”。未启用汇总的能力返回 `capability_not_summarized`，不临时套用平均算法。
