## 交付范围

本步保存明确选中的属性观测和设备事件，提供有范围限制的查询，显示来源、质量及已知缺口。已知有用的记录可以立即保存，实际消息量用于调整范围和资源预算，不要求先观察满 24 小时。

查询回答“后台当时收到什么”，不承诺还原任意过去时刻的完整设备状态，或证明两条记录之间从未变化。跨保留期的状态基线、精确条件时长、功率积分、累计能耗、小时／全年统计等，只有具体场景需要时另行定义口径和验收；本步不预建相关表与接口。

后台当前值仍由家庭状态机维护。数据库变慢、不可用或历史记录丢失，只影响历史完整性，不降低正常采集得到的当前值质量。

## 保存范围与记录语义

保存范围由 Step 3 的本机配置确定：`history_enabled=true` 的属性或事件保存全部通过校验并被接纳的观测，不按值去重，不建立多种采样策略。未启用的能力不保存。高频能力是否需要限选或以后增加采样，由实际场景和消息量决定；达到资源上限时明确报告丢失，不悄悄改变保存口径。

每条记录保存：

| 内容                                                                         | 用途                                                                                        |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| observation_id、account_id、home_id、device_id、能力标识及当时房间           | 保留原始身份与归属，名称改变不改写历史                                                      |
| scope_epoch、source_id、collection_generation、input_sequence、state_version | 关联所属运行、来源和处理顺序                                                                |
| received_at、observed_at、effective_at                                       | 原始接收 UTC、可为空的可信来源时间、被用于当前值的时间；候选或迟到值的 effective_at 为 null |
| source、delivery_kind、read_semantics                                        | 区分实时推送、读取、缓存及已知重放，不把它们都称为新发生事件                                |
| value／事件参数、单位与必要枚举说明、规格与来源契约版本                      | 保留当时可解释的值，不依赖后来改变的展示资料                                                |
| observation_quality、state_quality、state_applied                            | 原观测 quality、当时被采纳为 latest 的质量；未采纳时 state_quality=null                     |
| policy_version、适用的新鲜度方式及期限                                       | 记录所用配置依据；需要解释的少量字段随记录保存，不依赖独立策略版本库                        |

规则触发与原始设备事件不同，不能为获得事件历史把属性变化伪装成 `siid/eiid` 事件。尚无独立事件通路时不启用该能力。

## 有界写入与恢复

写入器随应用启动和退出，可使用独立 XState actor 管理等待、写入和恢复；不负责切换或同时运行其他家庭。正常停止时停止入队，按关闭期限尽量写完；维护改绑须在旧运行与写入器结束后进行。未完成记录仍保留原身份，不能转交新家庭。

复用 Drizzle 与现有 PostgreSQL／TimescaleDB。下述拆批方式、分块粒度和清理周期是本步的初始实现选择，可按实际记录规模与故障处理成本调整；调整后仍须满足有界资源、坏记录隔离和明确保留口径的要求。原始接收时间用于时序分区；唯一键包含 observation_id 和分区时间，重试沿用原身份。数据库提交不确定时先按同一键确认或安全重试，不生成新 ID。

| 项目           | 初始工程预算与处理                                          |
| -------------- | ----------------------------------------------------------- |
| 队列           | 沿用 Step 3 E4：最多 10,000 条或 16 MiB，包含正在写入的批次 |
| 批次           | 每 1 秒或 500 条提交，以先到为准                            |
| 单次数据库操作 | 最长 5 秒；确认底层操作结束后才释放在途名额                 |
| 瞬时故障       | 1 秒起退避，最长间隔 30 秒，复用原批次                      |
| 关闭           | 最多等待 10 秒；未确认数量单独报告，不宣称已保存            |

队列满时拒收新历史记录并计数，不阻塞设备状态提交。坏记录通过有界、顺序拆批定位，合法记录继续保存；连接、权限或表结构错误不按坏数据反复拆分。系统性故障公开原因，写入器按有界退避检查恢复，不要求另建恢复服务。

入队记录固定内容，后续观测不能再修改。私有队列和计数可以直接更新；发布到公共状态的健康摘要使用不可变提交。

## 缺口与健康状态

采集断开、输入丢弃、历史队列拒收和进程异常分别记录，不混成“设备离线”。`collection_gaps` 保存所影响的能力或来源、开始／结束时间、原因及已知丢失数量；未知数量为 null。队列外只保留有界缺口摘要，连续同类故障可扩大范围合并，细节不确定就如实标记，不承诺逐条丢失审计。

`collection_sessions` 记录每次运行的开始、结束及是否正常退出。上次未正常结束时，查询提示未确认尾部可能丢失；已经保存的观测仍有效，不因为运行异常抹掉它们。没有运行或缺口证据时，不声称整个查询区间完整。没有每五分钟的完成标记、全序列回执或跨运行片段积分协议。

历史恢复后继续保存新的合格观测，即使与 latest 同值也正常入库。恢复前的缺口不填成旧值，收到新点后也不推断缺口中一直相同。本步不重建连续状态，因此无需清理边界值基线或恢复时的人工合成观测。

历史写入器维护 `history_health`，经家庭状态机和 Step 5 发布：`{ scope_epoch, status, reason, pending_count, pending_bytes, last_saved_at, updated_at }`。status 为 idle／healthy／degraded／recovering，reason 为安全枚举。它是当前写入健康摘要，不是全历史完整性证明；详细缺口仅按需查询。退出或重新初始化清空运行摘要。

## 查询与清理

本机接口只查询当前绑定账号和家庭。请求携带预期的稳定身份 `{ account_id, home_id }`，后台独立解析当前授权和绑定并核对；身份不匹配返回 409，未授权时拒绝访问，不能凭请求身份选择其他家庭。查询及响应返回前均核验当前访问资格，客户端只将响应展示在匹配的账号和家庭下。普通历史查询不要求当前采集运行的 scope_epoch；同一家庭跨重启的历史可查询，记录仍保留原运行身份。本步不提供浏览其他绑定家庭历史的入口，也不混入其他账号或家庭的记录。

| 接口                                | 参数与返回                                                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GET /api/mijia/history/observations | account_id、home_id、capabilities、start、end、limit、cursor；返回属性记录、next_cursor、保存口径、已知缺口与 history_health |
| GET /api/mijia/history/events       | 同上，能力使用 siid/eiid；只在真实事件来源启用后提供对应记录                                                                 |

时间范围为 UTC `[start,end)`，默认按 received_at 查询和分页，返回原始时间及 input_sequence。分页排序键为 `(received_at, scope_epoch, input_sequence, observation_id)`；该排序用于枚举记录，不证明物理因果顺序。系统时钟跳变时标注时间不确定，不能用回拨的时间计算负持续时长。运行内处理顺序看 input_sequence，业务计时继续使用单调时钟。

查询能力最多 20 个、跨度最多 7 天；每页默认 500 条、最多 2,000 条，响应最多 4 MiB。游标绑定稳定账号和家庭身份、过滤条件和排序键，每页独立检查当前访问资格；同一绑定下后台重启不使游标失效。排序键中的 scope_epoch 是历史记录的原运行标识，不要求等于当前运行。已知缺口信息超过响应预算时标为不完整并要求缩小范围，不把省略的缺口说成不存在。分页不冻结数据库，写入恢复时旧时间段可能新增记录；响应说明仍在恢复，用户可重新查询。

查询只显示保留的观测与可确认缺口。区间前的值、没有记录的空白和未启用保存的能力，都不能画成已确认持续状态；页面不以插值暗示完整经过。查询响应不写回当前状态。

本步记录初始保留 30 天，缺口与运行记录保留到不再解释保留期内的数据；尚未结束的缺口不按创建时间直接删除。原始表按天分块、每小时清理，实际保留可能多一个块及清理周期；返回实际保存口径，清理失败进入 history_health。期限是按部署空间和场景调整的工程参数，不是必须提供 30 天完整记录的承诺。

使用 `device_observations`、`device_events`、`collection_gaps`、`collection_sessions`，表与迁移由现有 Drizzle 管理。没有正式明细与诊断重复入库要求；需要录制临时观察时使用 Step 3 的可选限量本机文件。

## 完成条件

- [ ] 所选设备的真实观测可保存并查询；未支持事件不伪造记录。
- [ ] 同值上报、未知缓存与实时变化保留各自来源和质量，不承诺连续重建。
- [ ] 数据库故障不停止当前采集；积压有界，丢失与恢复可见。
- [ ] 同一记录重试不重复入库，坏记录不连带丢弃整个正常批次。
- [ ] 停止与重启后的记录身份正确，异常退出可能丢失的范围不被说成完整。
- [ ] 查询与清理遵守时间、条数、响应预算和当前绑定范围；同一绑定重启后可继续分页，改绑或访问撤销后旧请求不能查询其他家庭或继续取得未授权数据，时钟异常不会产生虚假的时长结论。
- [ ] 完成总览中适用的共同检查；不以高级统计或完整历史页面未实现阻塞不依赖它们的场景。
