# Step 2：选择家庭，统一后台状态

**状态：实现已交付，主要实机链路已验证；完整验收仍有下述限制。** 当前实现见 [家庭运行时](../../household.md)。

[返回总览](../backend-household-perception.md)

本步完成三件事：

1. 记住用户要管理的家庭，重启后恢复它的房间和设备目录。
2. 用一个随应用运行的 XState 家庭状态机维护家庭状态，无人打开页面时也继续运行。
3. 把已有页面改为订阅这份状态，账号、登录、目录和播放状态都从这里更新。

通常只使用一个家庭。账号下有多个家庭时可以选择和切换，同一时间只运行被选中的家庭。切换允许暂时不可用：停止旧家庭、清空运行状态，再初始化新家庭。页面上的房间筛选、分类和搜索只影响显示。

真实采集在 Step 3 接入，历史在 Step 4、规则在 Step 6 接入。本步的 `latest`、`source_health` 和 `rule_status` 为空。人员、空间关系等[家庭语义模型](../household-model.md)也在后续场景中实现，本步只建立稳定的账号、家庭和设备身份。

## 保存和恢复家庭

- [x] **B1：保存选择。** 家庭选择关联稳定的供应商账号身份和 `home_id`。账号身份包含供应商、用户 ID 和区域，登录会话更新不改变它。凭据继续保存在现有加密存储中。
- [x] **B2：保存目录。** 持久化家庭、房间、设备及其归属，记录 `last_seen_at`、同步状态和归档标记。外部 ID 按账号隔离；未分配房间用空值；名称和归属保留米家原始信息。
- [x] **B4：确定默认家庭。** 优先恢复已有的有效选择。没有选择时，只有一个家庭就自动选中；有多个则等待用户选择。

### B6：初始化完成后再运行

应用启动恢复时，可以展示同账号、同家庭的持久目录，并标为“尚未同步”。主动切家按 B5 清空运行状态，从空目录重新初始化。

家庭选择保存成功、账号授权有效，并取得本次作用域下的完整目录、成功保存和提交后，才允许采集、主动读取和新播放。账号恢复过程中已经取得的合格目录直接复用。

初始化失败时显示所在阶段和错误，保持不可用，允许重试。已经运行的家庭遇到普通目录刷新失败时，继续使用上次确认的目录和既有任务。确认失去设备访问权限时停止对应任务；失去整个家庭的访问权限时回到家庭选择。

## 同步目录和设备规格

- [x] **B3：完整同步后更新目录。** 在后台取齐、校验目录并检查容量，再用一次事务保存，随后提交给家庭状态机。保存前和家庭状态机提交时都核对当前账号实例、作用域和请求版本，旧请求结果不能覆盖新目录。失败或不完整的返回保留当前家庭上次已提交的目录，并显示错误；新设备和新归属在保存失败时不生效。完整清单中缺失的对象按 B11 归档。持久化复用现有账号服务的串行写入入口，结果通过状态机事件生效。
- [x] **B10：复用现有目录刷新。** `MijiaService` 中的 `DeviceDiscovery` 负责启动、账号恢复、切家、结构变化通知和显式刷新的目录请求。保留它已有的后台发现周期，校正漏掉的变化。重复触发合并为一个进行中任务和一次后续刷新；持久化失败只保留最新完整目录供重试，替换候选时保留已经确认的撤销，切换作用域时取消旧任务。失败重试沿用该所有者的退避与暂停机制。公开最近云同步时间、最近保存时间和错误；保存失败标为 `storage_degraded`。目录刷新只读取家庭、房间、设备及归属。
- [x] **B11：移除及时生效。** 完整清单确认设备移除、转出，或收到明确的访问撤销时，先在家庭状态机中撤销相关任务资格，并在同一次提交中更新设备及能力状态，再异步取消读取、订阅或播放并保存归档。归档失败交给 B10 重试，过期任务或旧缓存不能恢复已撤销的资格。历史记录保留原归属。新设备则在目录保存、提交后加入任务范围；换房只影响之后接纳的观测。
- [x] **B7：保留当前家庭用到的规格。** 规格由家庭模块保存，设备按规格服务返回的标识和版本共用一份资料，相同规格的并发请求合并。设备移除后释放不再被引用的规格和型号对应关系，切家或退出时释放旧家庭资料，同账号凭据续期继续复用。规格与目录一起遵守 Step 5 的大小限制。
- [x] **B8：后台补齐规格。** 目录就绪后补齐缺失的规格，型号或规格版本变化时重新准备，并发上限为 3；瞬时失败额外重试 2 次，间隔为 2 秒、10 秒。单台失败只影响该设备；重试耗尽后等待相关信息变化或用户显式重试。重复刷新同一目录复用已有规格，不重置失败重试次数。规格不按时间自动过期，用户可通过下方入口重新获取。新规格校验并提交成功后才替换旧版本，刷新失败保留原版本并显示错误。请求沿用现有超时，普通 GET 只读已有状态。
- [x] **B9：派生分类。** 使用“设备类型＋能力标签”，保留 MiLoCo 的 `category`、readable/writeable/notify 及属性、事件、动作标识。Step 3 接入本机配置中的用途和别名，按稳定账号／家庭／设备身份保存，云端刷新保留这些本地字段。

### 超时和资源上限

以下限制处理数据库卡住、响应过大和失败数据积压。规格资料直接供当前家庭使用；请求期间的临时数据在完成、失败或取消后释放。

| 对象                       | 默认限制                                                        | 达到限制时的处理                                                                                                                                         |
| -------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目录和家庭选择的数据库事务 | 单次 5 秒，包含锁等待                                           | 用数据库或驱动的超时／取消能力结束事务，确认事务结束后释放协调队列。仅让调用方停止等待不算取消；提交结果不确定时先核对持久化结果，不盲目重试或报告回滚。 |
| 单次规格响应               | 复用 Step 5 目录与规格的 4 MiB 上限                             | 读取时超限即停止并报错；解析后仍须通过 C13 的家庭总量检查。保留已提交版本，首次加载则显示该规格未就绪。                                                  |
| 待保存目录和归档重试数据   | 每个 epoch 至多一份最新完整目录，连同归档重试数据合计最多 4 MiB | 超限候选整体拒收，报告 `capacity_degraded`，保留上次完整目录；已经确认的访问撤销仍按 B11 生效。                                                          |

容量按序列化数据计算，同时监测实际内存占用。以上参数与重试参数集中放在 backend 运行配置中。公共投影、输入队列和 SSE 的上限分别使用 [Step 3 E4](03-collection.md) 与 [Step 5 的容量约定](05-live-web.md)，引用其定义，不另设一组数值。

### 重新同步入口

沿用 `POST /api/mijia/devices/refresh`，请求必须包含 `scope_epoch` 和 `target`。`target` 有三种取值：

- `directory`：刷新目录。
- `specs`：重新获取当前家庭用到的规格，同一规格只请求一次。
- `all`：刷新目录，提交后重新获取对应规格。

普通目录同步只补齐缺失或已变化的规格；显式规格刷新使用 B8 的并发和重试限制，相同目标的在途操作合并，重复点击不重置重试次数。

接纳后返回 HTTP 202 `{ state_version }`，其中版本是接纳时的已提交版本。页面通过订阅查看完成或失败结果。旧 `scope_epoch` 返回 409，切家时取消旧任务。这个入口只刷新目录和规格。

## 切换家庭

`scope_epoch` 是当前账号和家庭这一轮运行的标识。命令和异步结果携带它，backend 据此拒绝已经过期的操作。

**B5：先停止，再重新初始化。** 切家请求携带目标 `home_id` 和预期 `scope_epoch`，通过状态机的统一输入入口接纳，按以下顺序处理：

1. 校验账号、epoch 和目标家庭归属，通过后接纳切家。
2. 生成新 `scope_epoch`，使旧家庭任务和观看资格失效，清空旧目录、规格、latest、采集及规则运行状态，进入目标家庭的 `initializing`。页面立即显示“正在切换”。
3. 取消旧请求、订阅和观看，保存新家庭选择。保存失败就停在这里，显示错误，允许重新选择或重试。
4. 重新获取目标家庭目录并补齐规格，满足 B6 后进入 `running`。

家庭选择和账号写入复用现有账号服务的串行入口，一次保存结束后才写入下一次选择，不等待云端初始化。数据库和云端请求在状态机外执行，结果作为事件发回并核对当前 `scope_epoch`；旧结果直接丢弃。失败后保留目标家庭的错误状态，不恢复旧家庭继续服务。重新选择同一目标也可以重试失败的保存或初始化。

这次清空针对旧家庭的运行状态和采集、观看等任务。已接纳的历史由独立写入器按原归属完成，不带入新家庭运行。重启读取最后一次保存成功的家庭选择；命令响应丢失时，页面以订阅状态为准。

## 后台运行时

### 模块分工

本步在 `apps/backend/src/household/` 创建以下模块：

| 文件            | 职责                                                     |
| --------------- | -------------------------------------------------------- |
| `runtime.ts`    | 创建、启动、停止家庭状态机，连接现有账号、目录和媒体服务 |
| `machine.ts`    | 家庭生命周期、事件处理和状态提交                         |
| `projection.ts` | 从已提交的家庭状态生成可对外发布的业务快照               |
| `stream.ts`     | 将状态变化发送到 SSE，处理慢连接和断开清理               |
| `routes.ts`     | 家庭选择、诊断快照和状态订阅接口                         |
| `repository.ts` | 保存、读取家庭选择和目录                                 |

`machine.ts` 定义状态和转移规则；`runtime.ts` 创建并启动按这些规则运行的实例。XState 将这个运行实例称为 actor。下文用“家庭状态机”指这个实例，代码中的 `actor.start()`、`actor.subscribe()` 分别用于启动和订阅状态变化。

供应商协议仍由 `mijia/` 负责。Step 3 再创建 `collection.ts` 和 `observations.ts`，Step 4 再接入 `telemetry/` 历史写入器。

- [x] **C1：使用稳定版 XState。** 锁定依赖版本，确认它在项目 Bun／TypeScript 环境中的状态提交和订阅通知行为满足 C12。
- [x] **C2：随应用启动。** 在 `main.ts` 启动 `runtime.ts` 中的家庭运行模块，连接现有服务和路由。账号、登录、目录和媒体服务主动通知公共状态变化；接线时先订阅，再同步读取初值。页面访问不负责启动或刷新家庭状态机。
- [x] **C8：按职责保留资源管理。** 家庭状态机维护统一业务状态。账号凭据、目录请求、媒体连接仍由现有模块管理；Step 3 增加一个由 XState 管理的采集任务，随家庭作用域启动和停止，负责订阅和读取。

### C3：生命周期

| 状态               | 含义                                                         |
| ------------------ | ------------------------------------------------------------ |
| `unbound`          | 没有可用账号                                                 |
| `waiting_for_home` | 账号已就绪，等待选择可访问的家庭                             |
| `initializing`     | 正在保存家庭选择、清理旧资源或初始化目录；失败时显示阶段错误 |
| `running`          | 账号就绪，目录满足 B6，公共状态订阅已接好                    |
| `stopping`         | 应用正在退出和释放资源                                       |

`running` 表示家庭运行时就绪，采集是否成功由 Step 3 的 `source_health` 单独表示，规格也可以继续补齐。初始化失败显示所在阶段和错误；运行后的普通刷新失败保留 `running`。切家进入新家庭的 `initializing`，失去家庭访问回到 `waiting_for_home`，退出账号回到 `unbound`。

### 状态如何提交

- [x] **C4：统一公共状态和版本。** 家庭状态机保存账号作用域、家庭选择、目录、规格准备状态，以及账号、登录和媒体的安全公共状态。公共版本为 `state_version = { scope_epoch, sequence }`：新作用域从 0 开始，一次公共变化加 1；同一次提交涉及的所有实体一起生效，内部变化和 no-op 不加版本。快照和增量都从已提交状态按共享 schema 的字段白名单生成。凭据、登录私密材料、连接和 Promise 等留在各自服务中。
- [x] **C5：切换作用域时清空运行状态。** 应用启动、绑定或更换账号、退出、切家、家庭访问撤销时生成新 `scope_epoch`。切家按 B5 同时提交目标家庭和空的运行状态，随后重新初始化。同账号凭据续期保留家庭状态，只重建受影响的连接。Step 3 使用 `collection_generation` 区分同一作用域内的新旧采集实例。
- [x] **C6：异步操作与状态更新分开。** 网络和数据库操作由状态机管理的异步任务或现有服务完成，结果作为事件发回。状态机内的异步任务随所属状态进入而启动、退出而停止，底层请求的取消仍按 C7 执行。家庭状态机的状态更新保持同步。
- [x] **C13：提交前检查容量。** 按 Step 5 的统一预算检查候选状态，合格后才提交状态及其容量计数；超限保留上次合法状态并报告 `capacity_degraded`，不截断实体，也不先提交再交给 SSE 拒绝。访问撤销仍立即生效；缓存展示和已有任务是否继续按 B6 处理。

**C12：状态提交后再执行后续操作。** 在 `actor.start()` 前注册一个应用级 `actor.subscribe` 出口，接收已提交状态，分发本次通知和后续操作：

- 状态与操作描述一起提交，context 只保留最近一次不可变提交结果，供内部分发使用，不进入公共快照或持久恢复。被拒绝或提交失败的输入不执行后续操作。
- 每条接纳输入独立完成一次转移，用 `scope_epoch/input_sequence` 识别本次提交，投递前标记已处理。即使公共状态未变，也要执行这条输入产生的后续操作。
- 出口同步分发，不等待网络或数据库。某项失败由对应模块报告，其他项继续，不重发整批。

Step 3 的逐条观测处理、Step 4 的历史写入和 Step 6 的规则处理接入这个出口。

### 资源清理和播放

- [x] **C7：停止时释放实际资源。** 取消在途请求、解除订阅、清除计时器并停止接收新输入。正常停止、取消和异常共用可重复调用的清理逻辑。迟到结果和清理回调只能作用于它们所属的作用域；Step 3 的采集结果还要匹配活动实例。
- [x] **C9：播放跟随当前家庭。** 摄像头列表来自已提交家庭目录，新播放须满足 B6 和当前媒体绑定条件。切家时先使旧 epoch 和媒体 revision 的请求失效，再由现有媒体模块释放旧观看资源。两种标识各管各的生命周期。播放是否可用由实际媒体连接决定，目录中的在线字段或未知在线状态不单独阻止播放。
