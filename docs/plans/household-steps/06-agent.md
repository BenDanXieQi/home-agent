# Step 6：让实际场景触发一次 Agent 分析

**状态：待执行。** 依赖固定家庭运行时与所选场景需要的真实采集；使用历史时才依赖 Step 4。无需等待所有设备、历史界面和统计能力完成。

## 场景与输出

先从当前已验证设备中选一个实际问题，明确输入、触发含义和结果用途，例如在具备对应证据时分析持续开门或环境读数越界。设备不可用时换用已验证的场景，不用模拟消息宣告完成。

本步的自动触发产生一次有依据的分析，输出保存到原任务 checkpoint，记录 task_id、事件身份、触发时间和所用证据。这完成的是可复核的工程链路，尚未交付用户日常可见的提醒或解释。用户主动提问仍由现有聊天接口返回，但该入口不会自动展示后台分析记录。具体场景需要用户看到自动分析时，接入最小的已有输出渠道，并验收用户确实能看到结果；不以 checkpoint 保存成功代替这项交付。

本步不建立建议公共状态、建议接纳 API、通知发送或任务列表页面。实际通知、持续建议或设备动作在有明确输出场景后单独定义投递与生效边界。家庭语义判断的受控提交另见[家庭模型](../household-model.md)，不与普通分析记录混用。

Agent 不运行、推理失败或执行记录保存失败，不影响后台采集与页面；任务失败不自动重跑，也不操作物理设备。

## 本机场景配置

场景配置放在 `data/household-config.json` 的 `rules` 中，启动时读取：`{ id, enabled, template, parameters }`。id 是本机稳定场景标识，template 只对应已经实现的具体场景函数，parameters 按该模板校验设备能力、阈值、持续时长及启动等待期限。只实现实际启用场景需要的模板，不先建立任意嵌套条件语言。

backend 加载本轮启用配置，使用内容与模板实现版本确定 rule_version；它区分本次使用的配置，不能单凭版本号还原触发含义；实际含义随事件证据保存，不建立在线版本管理。修改或停用配置后停止并重新启动运行，旧任务按运行身份失效。本步没有规则配置数据库、CRUD API、版本并发写入或禁用规则分页管理。

模板必须满足：

- 能力真实存在、规格与来源适用，Step 3 配置允许参与场景判断。
- 使用明确单位与确定比较，不运行用户脚本、不让模型猜条件真假。
- 缺少必要证据时结果为未知；只有明确成立才触发。
- 定义重复触发与恢复语义，不对每条同值上报重复调用模型。

公共 `rule_status` 只投影本轮启用场景的 `{ rule_id, rule_version, status, reason }`，status 为 active／suspended；不保存历史配置。具体模板规模随实际场景配置确定，文件和运行集合遵守集中资源预算，不把支持大量通用规则作为交付目标。

## 后台判断与触发

条件判断使用普通领域函数，在家庭状态机同次提交的前后数据上执行，不访问网络、数据库或模型。更新设备状态、场景运行状态和触发证据后，再发布事件与调整计时器。复用 Step 2 的 XState／Mutative 提交路径；某个场景计算错误只暂停该场景。

按实际场景选择需要的触发方式：

| 方式              | 可表达的含义           | 证据边界                                                         |
| ----------------- | ---------------------- | ---------------------------------------------------------------- |
| device_event      | 真实按钮、门铃等事件   | 需要独立且已验证的事件来源；相同参数不代表同一事件               |
| property_edge     | 后台观察到关→开等变化  | 前态可信、后态为顺序明确的实时推送，中间连续性有效；沿用 Step 3  |
| condition_entered | 条件由假或未知变为真   | 启动或恢复时已成立可触发，但注明这是当前成立，不伪造刚发生的变化 |
| condition_elapsed | 条件按有效策略持续成立 | 变为假／未知或连续性失效时取消；后台重启重新计时                 |

这张表说明允许的语义，不要求为没有实际来源和场景的方式提前建通路。持续计时使用单调时钟；XState 延迟事件只提出检查请求，按 Step 3 等待此前观测处理边界后，再核对质量、条件和配置版本。没有新上报也可到期检查，但不能用一次测量自动证明持续成立。

## 事件证据与传输

复用现有状态 SSE 取得只读副本，另以 `GET /api/mijia/semantic-events?scope_epoch=…` 传送场景触发。本阶段选择复用共享协议，不为每个场景新增一条连接，也不以全量副本追平作为纯证据分析的条件。

每条 semantic_event 包含：

| 字段                                      | 用途                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| semantic_event_id、event_sequence         | UUID 与本轮连续事件编号，关联和检测重复／缺口                                                                       |
| account_id、home_id、scope_epoch          | 固定绑定及本轮运行身份                                                                                              |
| rule_id、rule_version、trigger_kind       | 对应本机场景和实际触发方式                                                                                          |
| state_version、generated_at、start_before | 触发提交版本、生成时间及最晚启动时间                                                                                |
| trigger_evidence                          | 当时使用的模板标识、实现版本、实际生效的必要参数，以及设备与能力、值、来源观测 ID、时间、质量、必要前后态或持续依据 |

触发含义按本次实际使用的模板及参数保存，必要参数包含已展开的默认值，例如比较方式、阈值、单位和要求持续时长。事件证据原样随任务输入保存到 checkpoint；即使本机配置后来修改，也能区分“温度 29℃ 且超过 28℃”与其他条件，无需保存完整配置或恢复规则版本库。证据包含本次推理所需的最小事实，不靠稍后查询改写触发时发生的事情。字段结构与证据总计最多 64 KiB，超过则拒绝本次触发并报告原因，不能截断必要证据。当前事实可另查，输出须与触发时事实区分。

连接注册后先发 `event_ready { scope_epoch, event_sequence }`，再按序发送新事件；初始化期间产生的事件有界暂存。重复编号忽略。同一运行内收到编号递增但不连续、身份合法且证据完整的事件时，记录缺失编号区间，并以收到的编号继续跟踪；该事件仍按下文任务接纳条件处理，不因缺号这一点而关闭连接。缺失事件不补造，也不使后续独立事件的证据失效。身份冲突或非法消息关闭重连，连接故障按恢复策略处理；无法确定的漏收区间标为未知。每 15 秒心跳、45 秒无有效消息重连；等待、重连与发送预算复用 Step 5，每连接最多待发 256 条或 2 MiB，写入超时只影响该连接。

事件流只发送订阅建立后的事件，不重放停机或断线期间事件；重连以新的 ready 编号为起点，错过区间可确定则记录，否则标未知。维护重新绑定在旧服务停止后发生，新运行不接续旧事件编号。

## Agent 任务

事件合法、未超过 start_before 且没有已知运行撤销时，进入一个有界等待队列。场景配置在运行中固定，启动资格来自已接纳事件及本轮运行；不为每个任务查询一个在线规则管理接口。落后的状态副本不能提前否定较新事件，收到明确退出、停止或设备访问撤销时取消受影响的等待中及运行中任务，设备级撤销只影响依赖该设备的任务。

设备采集临时断流（例如 MQTT 断线）只使依赖该来源的当前条件、连续计时及旧采集任务失效，不撤销已接纳事件的分析资格。证据已经充分的纯证据分析可以继续，包括尚在等待队列且未过启动期限的任务；需要当前值的工具如实返回来源与质量限制，不能把旧证据当作仍然成立的当前条件。Agent 状态 SSE 临时断流同样不取消纯证据分析。

启动等待期限按场景时效设置，初始 60 秒；运行超时独立使用现有 Agent 配置，从实际启动起计时，覆盖模型、工具与 checkpoint 保存。期限按单调时钟消耗，排队时间不挤占已启动任务的运行预算。

等待队列初始最多 100 条或 8 MiB，同时运行最多 2 项；这些是按实际家庭任务量调整的工程预算。入队前清理过期项，仍满则拒收新项并计数。取消须传到底层，实际操作未结束前仍占名额；库抛出超时不等于资源释放。

每项任务使用独立 task_id／LangGraph thread_id，复用现有 LangGraph 和 PostgreSQL checkpointer，durability 为 sync。图只描述本次模型与工具流程，不复制 backend 的家庭状态机；事件队列不写成可跨重启恢复的任务平台。现有 checkpoint 存储是 Agent 自身依赖，不意味着必须先实现设备历史库。

模型结果与状态记录绑定原事件和原运行。停止或维护改绑后，不将迟到结果显示为新家庭的当前事实；已经保存的旧分析仍是原家庭的历史执行记录。没有后台建议发布对象，也没有“持续有效建议”的资格承诺。

## 查询工具

- 当前状态使用共享 schema 与 applyChanges 维护的只读副本，按相关设备和能力提取，每次最多 100 个能力。返回值、时间、来源、observation_quality、当前 quality、在线状态及采集健康。
- 状态连接断开时标为未同步，当前值工具返回 `household_state_unsynchronized`；明确请求上次已知事实时必须标为过时。纯触发证据分析可继续，不因短暂断流抹掉已接收事实。
- 一次性读取走 Step 3 的 properties/read，沿用命令期限、逐项结果和状态版本核对，超时不自动重发；它不能把未知时间云缓存升级成即时事实。
- 历史工具只在场景依赖且 Step 4 已交付时注册，查询范围和保存口径沿用 Step 4。不依赖历史的场景不等待该工具，也不提示模型虚构历史。

模型输出不写回设备状态或家庭语义判断。来源过期和质量不可用的原因如实返回，不以零、false 或猜测补齐。

## 追踪与实现位置

backend 的 household/rules.ts 承担具体模板配置、条件和计时，semantic-events.ts 负责事件流；Agent 的 household/state-client.ts、event-client.ts、tools.ts、tasks.ts 负责副本、事件、查询与执行。共享事件契约在 packages/api 中定义，不提前注册未实现接口。

记录 semantic_event_id、规则版本、task_id、thread_id/runId、触发版本及使用的当前状态版本。推理正常结束并成功保存 checkpoint 才记为完成；队列拒收、启动过期、运行超时、失败、取消和事件缺口分别计数。完整分析在 checkpoint 中，日志与 OTel 按现有脱敏规则保存关联信息。

## 完成条件

- [ ] 至少一个真实配置场景完成观测、触发、分析与记录，能说明其解决的问题和证据限制。
- [ ] 只依赖当前事实的场景，不等待高级统计、完整历史页面或在线规则管理。
- [ ] 首次值、未知缓存与恢复值不伪造事件；持续检查不会越过先到的观测。
- [ ] 同值上报不重复触发条件进入；实际独立事件按其身份分别处理。
- [ ] 状态 SSE 断流、设备采集断流与事件缺口分别处理；同一运行内合法且证据完整的递增事件跳号时记录缺口并继续接纳，不为缺号强制重连；临时采集故障不取消已接纳的纯证据分析，明确停止、退出或访问撤销取消相应任务。
- [ ] 本机配置修改后，原任务 checkpoint 仍可凭模板标识、实现版本、必要生效参数及观测证据解释当时为何触发；旧分析不会变成新运行的当前事实。
- [ ] 队列、并发、期限和真实取消有界；失败不自动重跑。
- [ ] 能按任务关联核对 checkpoint 的分析结果，不把“已完成”误报成通知已送达或动作已执行。
- [ ] 执行总览中的适用检查，再按[家庭语义目标](../household-model.md#后续实施拆分与验收目标)接入该场景实际需要的判断、要求或动作。
