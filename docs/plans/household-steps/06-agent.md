# Step 6：让设备变化触发 Agent 建议

**状态：待执行。** Step 1—5 完成后再进入本步。

[返回总览](../backend-household-perception.md)

本步让 Agent 根据设备变化给出建议。例如，后台确认“门持续打开一分钟”，就把这次触发的依据交给 Agent，由它结合当前状态和历史做解释。

正常流程是：

1. backend 按规则判断设备事件和属性变化，普通条件判断不调用模型。
2. 条件满足时，backend 发出一条规则事件，附上触发时用到的设备值、时间和来源。
3. Agent 确认自己保存的家庭状态已经更新到对应版本，再启动推理，记录建议与依据。

Agent 未启动或推理失败，不影响后台采集、历史记录和页面。本步只做设备级推理建议，不操作物理设备；现有聊天入口继续按用户请求运行。人员活动、视觉判断和长期记忆按[家庭语义目标](../household-model.md)另行实施。

## 后台怎样判断规则

### 规则配置

规则保存在 `perception_rules`，按 `account_id/home_id` 归属，包含规则 ID、版本、是否启用、触发方式、条件、事件有效期和更新时间。

规则通过校验并保存成功后生效，每次修改增加 `rule_version`。同时更新 Step 5 的 `rule_status`，取消旧版本的计时和任务资格；保存失败就继续使用原版本。禁用也是一次版本更新，不删除已经被历史证据引用的版本。

本步提供本机接口，不要求另建规则编辑页面：

| 接口 | 请求与结果 |
| --- | --- |
| `GET /api/mijia/perception-rules` | 返回当前家庭已加载的规则及 `state_version`。 |
| `PUT /api/mijia/perception-rules/:rule_id` | 请求为 `{ scope_epoch, expected_rule_version, definition }`。创建时预期版本为 `null`，更新时必须匹配现有版本，否则返回 409。成功返回新规则版本及 `state_version`。 |

规则 ID 使用 UUID；一次只保存一条规则，请求最多 32 KiB。最多启用 100 条规则；每条最多引用 32 个能力、包含 32 个条件节点，嵌套最多 4 层。以上限制集中配置，超限时说明原因。

条件使用明确的设备能力和比较运算，例如“温度大于 28 ℃”，支持相等、不等、大于、小于及其组合。数值必须有相同单位或经过已确认的换算。条件不执行用户脚本，也不让模型猜测真假。

缺少可靠数据时，条件结果为“未知”：

- “全部满足”中，只要有假就为假；没有假但有未知，就为未知。
- “任一满足”中，只要有真就为真；没有真但有未知，就为未知。
- 只有结果明确为真才触发。

### I4：四种触发方式

- [ ] **I4：按家庭状态机接纳输入的顺序评估规则。** 用本次更新前后的状态同步计算条件、计时变化和触发证据，不访问网络、数据库或模型。状态提交成功后，才启动或取消实际计时器、发布事件。某条规则计算出错就暂停它并报告 `rule_evaluation_failed`，不阻塞其他规则和设备状态更新。

| 触发方式（`trigger_kind`） | 示例与含义 | 初始化和中断后怎么办 |
| --- | --- | --- |
| `device_event` | 收到一条已验证的实时按钮、门铃等事件。每次独立事件分别处理，相同参数不代表重复。 | 只接受当前有效订阅的实时事件；快照和补读不能冒充新发生的事件。 |
| `property_edge` | 同一属性由连续有效推送确认“关 → 开”等变化，且附加条件成立。 | 首次值、补读值和断线后的首次推送只建立比较起点，不触发变化事件。 |
| `condition_entered` | 条件从不成立或未知变成成立时触发一次，例如“温度超过阈值”。 | 启用规则或恢复可信状态时，已满足条件也可触发，但注明 `rule_enabled` 或 `state_recovered`，只说“当前成立”。 |
| `condition_elapsed` | 条件连续成立指定时长后触发一次，例如“门持续打开一分钟”；条件离开成立状态后才能重新计时。 | 从本次确认成立时开始。变为假或未知、相关采集中断、输入丢失、切家或规则变化都取消计时。 |

属性变化规则要求前后两个值来自同一采集实例的连续有效实时推送。例如补读得到“关”，随后第一次推送“开”，只能建立推送的比较起点；之后连续推送“关”才可以确认一次变化。条件型规则仍可使用可靠的补读值判断当前条件。

持续时长 `duration_ms` 支持 1 秒至 24 小时。条件成立时安排一次到期检查，即使设备不再上报也会检查。到期后回到家庭状态机，先核对当前质量和条件；仍有效且成立才发事件。计时不受系统时间回拨影响，也不把已过期数据当成持续成立；后台重启后重新计时，不接续停机前的时长。

规则依赖的能力须在 Step 3 配置中启用 `rule_eligible`（允许参与规则）；关闭该项时暂停相关规则。不存在、规格不匹配或未验证的能力不能启用相应规则，返回具体原因。属性变化规则必须有已验证的推送能力。已启用规则暂时失去可靠数据时标记 `suspended`，恢复后按上表重新建立条件。跨设备条件只表示后台处理到的已知状态，不声称各设备是在同一物理时刻测量的。

## 规则事件要带什么依据

协议沿用 `semantic_event` 这个名称，本文称为“规则事件”。事件记录的是触发时发生了什么，不能在 Agent 稍后执行时用新值改写它。

| 字段 | 含义 |
| --- | --- |
| `semantic_event_id` | 这条事件的 UUID，用于关联任务和日志。 |
| `account_id/home_id/scope_epoch` | 事件所属账号、家庭及本轮运行标识。 |
| `event_sequence` | 当前 `scope_epoch` 内从 1 递增的事件编号，用于发现重复或缺失；与状态版本分开。 |
| `state_version` | 触发依据所属的已提交状态版本。 |
| `rule_id/rule_version` | 产生事件的规则及版本。 |
| `trigger_kind` | 上表中的四种触发方式之一。 |
| `generated_at/expires_at` | 生成时间及任务最晚有效时间。有效期由规则设置，默认 60 秒，允许 1 秒至 1 小时。 |
| `trigger_evidence` | 本条规则用到的事实和来源。 |

`trigger_evidence` 按触发方式填写：

- 设备与能力标识、采集时的房间和规格版本、来源 `observation_id`。
- 属性变化前后的值、质量、来源、观测和接收时间；设备事件则记录 `siid/eiid/arguments`。
- 每个条件实际用到的值、质量和来源；持续条件还记录开始时间、检查时间、要求时长和实际确认时长。
- 规则启用、状态恢复或本地计时到期等原因，不能伪造一条设备上报。

共享格式按触发方式规定必需字段，只带本规则需要的证据。事件本身应足以解释触发，不要求 Agent 再查询可能已清理的历史。Agent 执行时可以读取更新的状态，但输出要区分“触发时”与“现在”。

事件连同字段结构最多 64 KiB，按 UTF-8 JSON 计算。生成时超限就暂停该规则，将 `rule_status` 更新为 `status=suspended`、`reason=evidence_too_large` 并记录原因；不能截断必要证据。只有成功生成新事件才增加 `event_sequence`。

## Agent 使用两条连接

- [ ] **I1：启动时取得完整家庭状态。** Agent 随服务启动订阅 Step 5 的公共状态，取得快照并按连续版本更新。状态同步后再订阅规则事件。每次状态重连都用新快照替换旧状态；Agent 重启也重新取快照。

| 连接 | 内容与恢复方式 |
| --- | --- |
| `GET /api/mijia/events` | 与 Web 完全相同的公共状态、版本、校验和重连方式，使用 Step 5 的统一连接限额。 |
| `GET /api/mijia/semantic-events?scope_epoch=…` | 只接收订阅建立后的新规则事件，不重放断线期间的事件。 |

两个接口都沿用本机访问校验。尚未选定家庭时不建立规则事件连接；请求中的 `scope_epoch` 已过期时返回 409 `household_scope_changed`，Agent 等待新的状态快照。

### 事件连接的消息顺序

1. backend 同步注册订阅并取得当前事件编号，先发 `event_ready { scope_epoch, event_sequence }`，表示本连接从哪个编号之后开始。准备这条消息时产生的新事件暂存后按顺序发送。
2. 此后发送 `semantic_event`。Agent 只接受同一家庭下的连续编号；已经接收的编号直接忽略。发现跳号、无效消息或家庭变化，就关闭连接并记录缺口。
3. 每 15 秒发送 `heartbeat`；45 秒没有有效消息就断开重连。心跳不能用来跳过未收到的事件。
4. 连接发生积压等错误时，可以发送 `event_gap { scope_epoch, reason, from_sequence, to_sequence }` 再关闭；发不出提示也直接关闭。无法确认的边界使用 `null`。

Agent 在当前 `scope_epoch` 内只需记住最后完整接收的事件编号，不论后续任务执行还是拒绝，这个编号都向前推进。重连拿到新的 `event_ready` 后，记录这两个编号之间错过的区间，以 ready 的编号为新起点；无法确认丢失数量时记为未知。切家重置编号，事件 ID 用于追踪。

事件连接复用 Step 5 的等待和重连参数：响应头 10 秒、首条 `event_ready` 30 秒；收到 ready 并稳定 60 秒后重置退避。每连接最多待发 256 条或 2 MiB，写入最长 15 秒，所有消息按顺序发送。超限或超时只关闭这条连接、释放订阅和缓冲，不阻塞规则计算。

这条连接允许断线或进程停止时丢事件，缺口必须可查。重新拿到状态快照不能证明期间没有事件，也不能据此补造按钮、开门等事件。本步不增加持久事件队列、重放和自动重新执行。

## Agent 怎样执行任务

### I2、I6：一个等待队列，最多两个推理任务

- [ ] **I2：先等关联状态，再运行。** 每条事件绑定原账号、家庭和规则版本。Agent 收到合法且未过期的事件后，进入同一个等待队列；只在状态副本同步、同一 `scope_epoch` 且版本不低于事件的 `state_version` 时启动。等待状态最多 5 秒，超时标记 `state_sync_timeout` 并跳过。追上版本后再核对 `rule_status`，避免用旧规则状态提前拒绝新事件。
- [ ] **I6：限制排队和模型并发。** 一个等待队列按接收顺序处理，最多等待 100 条或占 8 MiB，包含等待状态同步的事件。队列满就拒绝新事件并计数，不覆盖已经接纳的按钮事件。同时最多运行 2 个感知任务；使用现有 Agent 模型超时配置，并受事件有效期限制，取更早的截止时间。排队时已过期就跳过，不调用模型。

每个接纳任务生成独立的 UUID `task_id`，也用作 LangGraph 的 `thread_id`。复用现有 PostgreSQL checkpointer 和 `durability: "sync"` 保存这次推理的输入与执行过程。这里的 checkpoint 是任务记录，不是家庭状态库；不把每条状态更新存入其中，也不拿它恢复旧事件队列。

运行时始终保留触发证据。需要当前状态时，只提取规则相关设备和能力，不把整个家庭放进每次模型输入。同一规则的两个任务可以并行完成，结果各自带触发时间和事件 ID，不用完成先后改写设备事实。模型失败、任务超时或 Agent 重启后不自动重跑。

### 断线、切家和取消

状态连接断开时，Agent 停止接收新任务，取消等待项和运行项，关闭旧事件连接。重新同步后只处理新订阅的事件。仅事件连接断开、状态仍同步时，已经完整接收的任务可以继续，缺失事件不补造。

切家、退出、规则修改、停用或暂停时，同样取消相关任务和工具调用。输出建议前再检查任务未取消、未过期，家庭和规则仍有效、状态仍同步；不满足就不发布为当前家庭建议。backend 对工具命令独立核对作用域，不能只依赖 Agent 已发取消。

取消会向底层请求发送信号；请求尚未真正退出时，仍占一个执行名额。迟到成功不能把已取消、过期或失败的任务改成完成。事件接收时计算剩余有效时间，之后按实际经过的时长结束等待和执行，避免时钟回拨延长任务。

### I3、I5：本步提供哪些工具

- [ ] **I3：提供状态、历史和一次性读取工具。** 当前状态从已同步副本按设备和能力读取，每次最多 100 个能力，返回状态版本、值、来源、时间、质量、候选值、在线状态和采集健康。副本未同步时返回 `household_state_unsynchronized`；若明确请求上次已知数据供解释，标为过时，不能当当前条件。
- [ ] **I5：保留来源，不把推理当设备事实。** 只有 Step 3 定义为 `valid` 的数据可作为有效事实。未知、未映射、未确认或不可用的数据返回原因，不拿零、false 或猜测代替。本步模型输出是建议，不写回设备状态。

历史工具使用 Step 4 的有界查询。一次性读取使用 Step 3 的 `properties/read`：请求最多等共享契约规定的 35 秒，响应后最多再等 5 秒让副本追上结果版本，再返回逐项结论和当前值。任务本身更早到期则提前取消；HTTP 超时只说明结果未确认，不自动重发，也不直接用命令响应覆盖状态副本。

本步不提供设备写操作、视觉工具或语义候选提交接口。后续能力按各自实施步骤接入，不改变这里“事实由 backend 接纳，建议由 Agent 解释”的分工。

### I7：结果能追溯到哪次触发

- [ ] **I7：使用现有追踪记录任务结果。** 记录 `semantic_event_id`、规则版本、`task_id`、LangGraph `thread_id/runId`、触发状态版本、推理开始时的状态版本，以及完成、失败、取消、过期或拒绝的结果和原因。只有推理流程正常结束并成功保存 checkpoint 才记为完成。

事件缺口、队列满、等待状态超时、过期、失败和取消分别计数，通过现有追踪系统（OTel）和脱敏日志查看；不要求另建任务列表页面。事件连接的缺口与 Step 4 的采集缺口分开记录，不把它们说成设备离线。

Agent 退出时停止接纳任务，取消连接和模型调用，按现有关闭期限等待执行结束，再关闭 checkpoint 连接池。

## 完成条件

- [ ] Agent 不运行时，后台采集、历史和 Web 正常工作，不因此增加云端请求。
- [ ] 事件比对应状态先到时会等待；启动后仍能区分触发时证据与执行时状态。
- [ ] 连续两次相同参数的按钮事件分别处理；重复传输同一编号不会重复运行。
- [ ] 初始值、补读和断线恢复不伪造属性变化；持续条件在无新上报时也能到期检查，中断和重启后重新计时。
- [ ] 断线重新取得状态和事件起始编号，明确记录错过的事件，不用快照补造历史。
- [ ] 切家、规则停用、超时后的旧任务不会发布有效建议，迟到结果不会复活任务。
- [ ] 队列和并发有上限；证据太大时暂停对应规则并说明原因；模型失败不会自动重跑。
- [ ] 每次触发与结果都能追溯到规则版本和原始依据，数据未知时不编造事实。
- [ ] 执行总览中的共同检查，更新当前实现文档与仍未验证的限制。

完成本步后，按[家庭语义目标的后续实施顺序](../household-model.md#后续实施拆分与验收目标)继续推进；设备级建议不等于已经实现家庭语义或自动控制。
