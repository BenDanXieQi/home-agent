# Step 5：把后台状态显示到页面

**状态：G1—G11、H1—H6 的账号／家庭／目录／媒体订阅实现已随 Step 2 交付，其验收限制见 Step 2；采集与历史界面待执行。** 采集入口依赖 Step 3，历史入口依赖 Step 4。

[返回总览](../backend-household-perception.md)

页面和 Agent 都订阅后台维护的同一份状态。这里使用 SSE（服务器发送事件）：客户端建立一个持续连接，后台有变化就推送，不需要页面反复询问。

正常流程只有三步：

1. 连接成功，先收到一份完整状态，称为 **快照**。
2. 此后只接收变化，例如一个温度更新、一个设备移除。
3. 断线后重新连接，重新拿完整快照。切家时清空旧家庭显示，等待新家庭初始化。

Step 2 按本文件的 G1—G11、H1—H6 完成账号、登录、目录和播放页面的订阅。本步沿用这套实现，补上采集展示、一次性读取和历史入口，并完成整体检查。前后端同批更新，共用一套协议。

本步只发布下表中的设备和运行状态。[家庭语义模型](../household-model.md)中的人员、宠物、区域和媒体样本在对应阶段另行定义，不自动塞进这份状态。

## 页面和 Agent 收到什么

### G1、G3：一份可公开的状态

- [ ] **G1：在 `packages/api` 定义共享数据格式。** 用 Zod 校验发出的消息和收到的数据。保留 MiLoCo 目录、规格字段的原义；本项目新增的质量、版本等字段单独定义。
- [ ] **G3：状态统一从家庭状态机取得。** 账号、登录、目录、媒体等模块先把变化提交给 Step 2 的家庭状态机，再从已提交状态生成对外数据。未就绪部分明确标注状态，不阻塞整张快照。

协议将可公开的状态命名为 `projection`。它只包含明确允许公开的字段，内容如下：

| 数据类别（`entity`）                                                        | 标识与内容                                                                                                                                                     |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `account`、`login`、`connection`、`media`、`household`、`projection_health` | 各只有一份，使用固定 key；分别表示账号、登录、连接操作、媒体、家庭选择和整体健康。退出时更新为空状态。                                                         |
| `home`、`room`、`device`                                                    | key 分别为 `{ account_id, home_id }`、`{ account_id, home_id, room_id }`、`{ account_id, device_id }`；保留云端字段、归属和本地补充信息。                      |
| `spec`                                                                      | 用规格标识 URN 和版本区分；多个设备可以引用同一份规格。                                                                                                        |
| `latest`                                                                    | 用 `{ device_id, siid, piid }` 标识属性；包含最近值、来源、时间和质量。                                                                                        |
| `source_health`                                                             | 用 `source_id` 标识来源；包含连接、认证、订阅覆盖和当前采集实例 `collection_generation` 的状态。                                                               |
| `rule_status`                                                               | 用 `rule_id` 标识规则；值为 `{ rule_id, rule_version, enabled, status, reason }`，status 为 `active \| suspended \| disabled`，reason 使用共享的安全原因枚举。 |

页面和 Agent 接收相同的完整状态，按各自需要选取显示内容。Step 6 的规则事件通过另一条连接发送，不与这里的设备状态变化混用。

几个容易误读的字段按以下口径使用：

- `device.availability` 是 Step 3 定义的设备在线状态。没有可靠依据时显示 `unknown`。云目录的 `isOnline` 只作带时间的诊断信息，不能覆盖它；未知在线状态也不单独禁止播放或一次性读取。
- `device.read_enabled_properties` 是已配置可读的 `{ siid, piid }` 列表。Step 2 或尚未配置时为空，不重复发送完整采集策略。
- `rule_status` 在 Step 1—5 为空。Step 6 修改、停用规则时，要同时发布它的新状态，让 Agent 及时停止旧规则任务。
- 暂时无法对应规格的 `latest` 可以用于诊断，质量为 `unknown`、原因为 `unmapped`；不作为规则或模型的有效事实。原始诊断样本不放进公共状态。

### G2：每条消息说明哪次变化

`state_version = { scope_epoch, sequence }` 表示状态版本。`scope_epoch` 是 Step 2 定义的本轮家庭运行标识；`sequence` 是从 0 开始的整数，每次提交公共变化加 1。SSE 消息直接携带这两个字段。

- [ ] **G2：实现以下四种消息。** 一次提交涉及的变化放进同一条 `state_change`，一起校验、一起生效。例如移除设备时，同时移除它的属性和能力引用。心跳、重连通知和没有公共变化的处理不增加版本；同值上报若更新时间或质量，仍是公共变化。

| SSE 消息名        | 必需字段                                | 含义                                              |
| ----------------- | --------------------------------------- | ------------------------------------------------- |
| `snapshot`        | `scope_epoch`、`sequence`、`projection` | 完整快照，替换客户端保存的整份状态。              |
| `state_change`    | `scope_epoch`、`sequence`、`changes`    | 该版本的全部变化，全部成功后才更新页面。          |
| `resync_required` | `scope_epoch`、`sequence`、`reason`     | 要求重新连接；可附 `retry_after_ms`，不推进版本。 |
| `heartbeat`       | `scope_epoch`、`sequence`               | 表示连接仍在工作，不表示设备在线或数据新鲜。      |

`changes` 只支持两种操作：`{ op: "upsert", entity, key, value }` 新增或替换一个完整条目；`{ op: "remove", entity, key }` 删除条目。每类数据都有固定的 key/value 格式，key 必须与值中的身份相符。整批数据校验失败时不应用其中任何一项。

## 首次连接、断线和切家

- [ ] **G4：先接好变化通知，再取快照。** 服务端同步完成订阅注册和已提交快照的读取，中间不等待异步操作。快照发送期间暂存后续变化，随后按顺序发送比快照更新的消息，避免首次连接漏掉变化。整个快照来自同一次提交；遇到切家则关闭旧连接，由新连接读取新家庭。
- [ ] **G5：只按连续版本更新。** 客户端先校验并应用快照，此后只接受同一 `scope_epoch` 下的下一版本，已应用的重复版本可以忽略。出现版本缺口、新家庭标识、非法变化或 `resync_required` 时，停止更新，标记未同步并重新连接。心跳不推进版本；心跳中的家庭标识变了，也要重新同步。
- [ ] **G6：每次重连都取当前快照。** 不保存断线重放队列，也不使用 `Last-Event-ID` 补历史。重连间隔从 1 秒逐步增加到最多 30 秒，并加入少量随机错开；遵守服务器给出的最短等待时间。完整收到快照并稳定同步 60 秒后恢复初始间隔，不因刚连上 TCP 就反复快速重试。
- [ ] **G8：检测断流并释放资源。** 服务端每 15 秒发心跳；客户端 45 秒没有有效消息就重新连接。取消、异常和断开都执行同一清理逻辑：退订、清计时器、释放缓冲并停止发送。客户端取消旧连接后忽略其迟到结果；后台退出时主动结束长连接。
- [ ] **G9：使用现有 HTTP 框架发送。** Hono 使用 `streamSSE`，连接前沿用本机访问校验，连接后的错误发送安全提示或直接关闭。禁用缓存，并确认 Vite 代理及时转发消息。

断线恢复的是当前状态，不保证补齐断线期间的全部设备事件；事件历史使用 Step 4 的查询接口。页面断线时可以保留旧数据显示“尚未同步”，但切家、退出账号时立即清空旧家庭，不靠旧快照维持可用。

## 防止大数据和慢连接拖住后台

这些限制防止异常响应或慢客户端持续占用内存。Step 2、Step 3 和 SSE 共用配置，容量按 UTF-8 JSON 序列化后的字节数计算。1 MiB 为 1,048,576 字节。

| 项目                                       | 默认限制                                                             | 达到限制时                                                           |
| ------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `latest`                                   | 2 MiB，最多 20,000 个属性，两者先到者生效                            | 拒绝本次超限更新，标明受影响的覆盖。                                 |
| 家庭、房间、设备目录与规格                 | 合计 4 MiB                                                           | 目录整批拒收，保留当前家庭上次完整目录；规格保留原版本或显示未就绪。 |
| 账号、登录、媒体、健康、规则状态及协议开销 | 合计 2 MiB                                                           | 保留报告容量错误和存储错误所需的空间。                               |
| 完整快照或单条业务消息                     | 8 MiB，包含版本和消息结构                                            | 不能截断后冒充完整状态。                                             |
| 每连接待发变化                             | 最多 256 条或 2 MiB，包含正在发送的变化；另允许一份最多 8 MiB 的快照 | 关闭该连接，客户端稍后从新快照恢复。                                 |
| SSE 连接                                   | 状态连接最多 16 条；Step 6 的规则事件连接另最多 2 条                 | 建立订阅前返回 503，默认 `Retry-After: 30`。                         |

候选状态通过容量检查后才提交；大小计数与状态一起更新，不为每次属性上报重新序列化整个家庭。发送快照前再校验最终大小；如果仍超限，报告容量检查错误并停止发布，不能靠反复重连处理同一个超大快照。

超限时标记 `capacity_degraded`，不能把未接纳的数据说成已经同步。已运行家庭的普通刷新失败按 Step 2 B6 处理；明确的访问撤销仍立即生效。新家庭从空状态初始化，不复用旧家庭。首期使用这套固定上限，不增加分页快照等另一套协议。

- [ ] **G7：每条连接按顺序发送。** 快照、变化、心跳和提示共用一个发送队列，单次写入最多等待 15 秒。超时、队列满或单次变化超出待发预算就关闭连接；重连提示发不出去也照常清理。慢连接不能阻塞其他连接或触发额外云端读取。
- [ ] **G11：连接先限额，再分配资源。** Web 和 Agent 使用同一状态连接上限，获准后才注册订阅、准备快照和缓冲。所有关闭和失败路径都释放占用。

## 登录材料单独读取

- [ ] **G10：公共状态使用字段白名单。** SSE 不包含凭据、Cookie、token、SDP 或内部连接对象。登录公开状态只有 `id`、`status`、脱敏 `error` 和 `material_version`。二维码或验证材料准备好、发生变化时，登录模块更新 `material_version` 并通知状态机。

页面据此调用 `GET /api/mijia/login/:id/material`，响应为 `{ id, material_version, qr_image_url, verification_url, expires_at }`。不适用字段为 `null`，`expires_at` 为 UTC 时间或 `null`；响应设置 `no-store`，沿用本机访问校验。只返回当前有效尝试的材料，Agent 不接收这些资料。

## 页面如何使用

### 先完成 Step 2 的页面迁移

- [ ] **H1：应用统一管理订阅。** 使用 Hono RPC 的 fetch 建立连接、`eventsource-parser` 解析 SSE、共享 Zod 格式校验消息。组件不自行连 SSE。长连接直接读取 `Response.body`，不经过普通 JSON 请求的 12 秒总超时。连接、取消、超时和重连由同一个管理器负责。接入时确认解析库的缓冲限制用法并锁定依赖版本。
- [ ] **H1a：等待和解析都有上限。** 响应头最多等待 10 秒，只接受成功状态和 `text/event-stream`；503 按服务器要求稍后重试。响应头到达后最多等 30 秒收齐第一份快照，之后使用 G8 的断流期限。分段交给标准解析器，缓冲上限默认是 9 × 1,024 × 1,024 个字符；库按字符计数，所以收到完整消息后仍要检查其 UTF-8 数据不超过 8 MiB，再解析 JSON。出错或取消就释放读取器和解析器，走同一重连流程。
- [ ] **H2：每个标签页只存一份状态。** 一个浏览器标签页只建一条状态连接。快照和变化更新同一份缓存，现有 Jotai 从中派生显示值。
- [ ] **H3：移除被订阅替代的轮询。** 删除米家状态的 `refetchInterval` 和窗口聚焦、重连时的重复 HTTP 拉取。标签页重新可见时检查 SSE，必要时重连；无关的服务设置查询继续保留。
- [ ] **H4：账号页面以订阅状态为准。** `AccountGate`、`use-login.ts` 和命令处理等待状态同步后再决定页面。命令响应只说明操作结果，不覆盖后台状态。二维码材料按当前 `id` 和 `material_version` 读取，同版本请求合并；显示前再次匹配，尝试变化时清除旧材料。失败显示错误、允许重试。账号页面沿用现有扫码登录与后端静默 OAuth 组成的统一会话，不新增独立授权页面或第二套登录状态；扫码材料、Cookie 和 token 不进入家庭状态。推送鉴权及状态采用 Step 1 在此前提下实际核实并启用的契约；未具备的能力展示具体限制，不提示用户另做 OAuth，完整会话接纳也不能代替推送连接与订阅确认。
- [ ] **H5：播放跟随家庭和媒体状态。** 新播放须满足 Step 2 B6，且家庭标识、媒体 revision（媒体模块的当前版本）和绑定状态仍有效。播放可用性由媒体连接决定，不用目录在线字段或轮询时间判断。SSE 短暂中断时保留已有播放器；切家、退出账号时立即释放。
- [ ] **H6：切家允许暂时不可用。** 选择器显示“被管理家庭”，说明更换会停止旧家庭的感知、自动化和观看。命令携带已同步状态的 `scope_epoch` 和目标 `home_id`；接收新家庭标识后清空旧内容，显示初始化进度或错误，失败后允许重新选择、重试。房间、分类、在线和能力筛选只影响本页显示；在线筛选使用 `availability`，未知状态单独显示；搜索同时匹配云端名称和本地别名。

### 本步增加采集与历史显示

- [ ] **H7：说明数据来自哪里、是否可用。** 设备详情显示在线状态、属性最后上报和变化时间、采集来源、订阅覆盖及不可用原因。订阅失败或“采集过载，已暂停”时提供 `connection/retry` 按钮，分别重试失败订阅或重建采集，进展以 `source_health` 为准。浏览器断线显示“状态未同步”，不要写成设备故障；设备离线、数据过期和容量不足分别说明。
- [ ] **H7a：一次性读取显示逐项结果。** 根据 `read_enabled_properties` 提供读取入口，按 Step 3 发起命令。使用共享契约的 35 秒 HTTP 期限，不自动重发；响应后最多再等 5 秒，让本页订阅状态追上响应的 `state_version`，再显示逐项结论。部分失败不能说整批已刷新；未追上显示“状态未同步”，HTTP 超时显示“读取结果未确认”。等待期间切家就丢弃旧结果，正常 SSE 同步继续。
- [ ] **H8：页面只更新需要的部分。** 温度变化只更新相关显示，不重复传输、重建规格等静态资料。
- [ ] **H9：历史由用户按需查询。** 设备详情按能力和时间范围调用 Step 4 的明细、事件、汇总接口；明细使用游标翻页，汇总选择 5m 或 1h。显示采样或变化记录口径、有效覆盖、缺口和数据保留范围；没有依据的时间段不连成正常曲线。明细为空时，若 `state_context` 提供区间起点前的状态且能证明持续有效，仍可显示这段持续状态。历史响应只用于历史页面，不回写当前状态，也不定时轮询。

## 接口清单

按所属步骤实现接口，不提前注册空路由。已有命令继续使用，页面状态统一通过订阅更新。

| 接口                                                                          | 用途                                       |
| ----------------------------------------------------------------------------- | ------------------------------------------ |

| `GET /api/mijia/state`                                                        | 显式诊断时读取内存中的安全快照。           |

| 登录、验证、退出                                                              | 现有账号命令。                             |
| `GET /api/mijia/login/:id/material`                                           | 按需读取当前登录材料。                     |

## 完成条件

- [ ] 初次打开、断线重连、标签页恢复可见都能取得完整状态；同一次变更不会在页面上只生效一半。
- [ ] 多开页面不会增加云端读取，没有用于状态恢复的 HTTP 定时轮询。
- [ ] 切家后旧内容和观看立即清空，初始化失败有明确错误；旧连接和旧登录材料不会覆盖新状态。
- [ ] 设备未知在线状态、浏览器断线、属性过期和订阅失败能区分；一次性读取的部分失败、超时不会误报成功或自动重发。
- [ ] 超大数据、慢连接和写超时都有明确处理，内存不会随积压持续增长，其他连接仍能工作。
- [ ] 快照不泄露凭据和登录私密材料；连接关闭后订阅、计时器和缓冲都释放。
- [ ] 执行总览中的共同检查，更新当前实现文档与仍未验证的限制。
