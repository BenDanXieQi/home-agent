# Step 3：接收设备变化，维护当前状态

**状态：待执行。** 前置条件是所需设备通路已按[米家来源契约](../../reference/mijia-source-contract.md)验证，Step 2 已能选择并运行一个家庭。

[返回总览](../backend-household-perception.md)

本步让后台持续接收设备消息，记住每个属性最近的值，并说明这个值现在是否可信。比如温度计报告 25℃，页面应能看到数值、收到时间和连接状态；断线后保留 25℃，但明确提示它可能已经过时。

先接通所选场景的真实数据，明确有用的属性和事件可以立即保存；持续观察用于校准保存范围和资源预算。需要的历史记录由 Step 4 接入，场景分析由 Step 6 接入，两者不必等待观察满一天。人员活动等[家庭语义](../household-model.md)属于后续场景，不混进设备原始状态。

## 本步使用的几个名称

| 名称                    | 在本文中的意思                                                           |
| ----------------------- | ------------------------------------------------------------------------ |
| 设备清单                | 家庭、房间、设备及其归属关系                                             |
| 观测                    | 一次设备上报、读取结果或在线通知                                         |
| 来源                    | 数据来自哪条设备消息连接或读取通路                                       |
| 家庭状态机              | Step 2 启动的 XState 实例，负责按规则更新并提交家庭状态                  |
| 公共状态                | 家庭状态机已提交、供页面和 Agent 读取的数据                              |
| `latest`                | 每个设备属性的当前值，以及它的来源、时间和有效性                         |
| `quality`               | 所在记录的有效性；观测与当前值的字段关系见下文                           |
| `availability`          | 设备的在线、离线或未知状态                                               |
| `source_health`         | 数据连接、授权和订阅是否正常                                             |
| `scope_epoch`           | 本轮固定家庭运行标识；重启、退出、明确失效及维护改绑后的新运行使用新标识 |
| `collection_generation` | 这一轮采集连接的标识；重连或更换凭据后换新标识                           |

“最近读到过”与“现在仍然有效”分开表达。连接成功、设备在线、某个属性可信，也分别记录。

下文的“接纳”表示观测通过校验，进入本次状态处理；“提交”表示这一批状态变化一起生效。家庭状态机先提交状态，再执行读取、计时和历史保存等后续操作。

## 采集如何运行

`household/collection.ts` 管理订阅和读取；`household/observations.ts` 校验消息并交给家庭状态机。小米协议继续由 Step 1 的 `properties/` 和 `protocols/` 实现。

采集使用 Step 2 家庭运行范围内的 XState actor 管理启停、观察、过载恢复与暂停；订阅适配可用 callback actor，单次异步读取可用 promise actor。actor 只拥有采集资源与运行进度，latest、质量和公共版本仍由家庭状态机统一提交。协议连接重连与凭据更新继续由现有米家观察模块负责，采集 actor 消费其状态，不再另设一套协议重连循环。

退出采集状态时取消观察、读取和待执行计时；清理仍须调用适配器取消接口、转发 AbortSignal，并等待在途资源真正退出再启动冲突任务。保留 scope_epoch 与 collection_generation 检查，不能仅靠 actor 已停止排除外部迟到回调。属性仲裁与质量规则使用纯函数，不为每个属性创建 actor。

- [ ] **D10：随家庭运行。** 绑定家庭初始化完成后启动采集，无人打开页面也继续接收消息。退出、停止或设备移除时取消对应任务；纠错改绑须先结束旧运行，再修改绑定并重新初始化，不与另一家庭并行运行。
- [ ] **D7：订阅后补齐必要的值。** 使用 Step 1 的 `observeDevices` 和 `readProperties`。初次启用、设备加入、规格就绪、设备重新上线或连接恢复时，对缺值或待确认的属性读一次。同一属性已有读取任务就复用，重复刷新设备清单不再读一遍。
- [ ] 读取仅用于初始化、恢复和用户显式请求。没有推送能力时显示限制，不增加周期属性轮询。

自动读取针对已配置 `read_enabled` 的可读属性。明确离线的设备暂缓读取；在线未知仍可读取。单个属性失败不阻塞其他属性，没有推送通路的可读属性也可以单独读取。

请求参数沿用 Step 1：共用串行读取批次，每批最多 150 项、请求最多 30 秒；上线后等待 20 秒合并短时间内的重复通知，重连补读等待 15 秒。认证失败交给账号模块，服务端限流按其要求等待。其他失败显示原因，等待下一次真实触发或用户重试。

### 订阅失败与数据连接状态

连接正常不代表全部设备已经订阅成功。`source_health` 分别记录连接、认证、待订阅／已确认／失败数量、覆盖范围、最近确认和观测时间。未验证或不支持的能力，以及采集是否暂停、暂停原因，也明确列出。

显式重试沿用 `POST /api/mijia/connection/retry`。只有部分订阅失败时，重试这些订阅并保留正常连接；采集因 E6 过载暂停时，按来源适配器的恢复方式恢复接收；只有连接或订阅实际停止时才重建，补读须有已验证的能力和恢复基线需要。并发与确认期限使用 Step 1 的 16 项、10 秒；重复点击合并，结果通过状态订阅显示。

MIoT 通路沿用 Step 1 已确认的解释：活动连接上的合法属性／在线推送按实时消息处理，使用接收时间；云缓存读取按初始参考值处理。订阅确认前收到的合法消息照常校验和保存，原观测的 `quality` 按能力、来源、值和时间依据判断，不因等待订阅确认这一点而降级；采纳为 latest 时保留为 `observation_quality`。依赖该订阅维持有效的 `latest.quality` 按下文优先级标为 `unconfirmed/subscription_unconfirmed`，不据此建立连续状态或持续条件。确认订阅不刷新原观测时间，不补造此前发生的事件或连续性。独立设备事件需要真实通路支持，不能用属性变化冒充。

## 接收什么数据

- [ ] **D1：分清三类消息。** `property_report` 表示属性值，`device_event` 表示按钮、告警等独立事件，`availability` 表示在线状态。
- [ ] **D2：在适配入口校验。** 用共享 Zod 数据格式检查身份、类型、规格和大小，再送给家庭状态机。账号和家庭归属由 backend 关联。
- [ ] **D3：只做有依据的去重。** 每次接纳的观测分配 `observation_id`，历史写入重试保持同一 ID。供应商重传按 Step 1 确认的消息身份／序号规则处理，范围限定在它实际有效的连接内；没有可靠依据就标为无法判定。相同数值可以是新的上报，按钮事件尤其不能按值去重。
- [ ] **D4：拒收旧任务和错误消息。** 旧运行、旧连接、身份冲突或格式错误的消息不更新当前状态。只保留原因计数和少量脱敏样本，限制见 E2。
- [ ] **D5／D6：接收、保存和展示分别决定。** 当前家庭的合法推送可以进入最新值和统计；历史只保存选中的能力；页面和规则只使用各自需要且已解释清楚的字段。MiLoCo 的消费白名单与规格 `notify` 标记不能直接充当接收或历史白名单。复用其文件前核对许可。

### 观测字段

属性使用真实的服务标识 `siid` 和属性标识 `piid`；独立事件使用 `siid/eiid`，参数按事件规格校验；在线通知只带设备与在线事实。

| 字段                                              | 含义                                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `account_id / home_id / device_id`                | 账号、家庭和设备身份                                                                         |
| `scope_epoch / source_id / collection_generation` | 所属家庭运行、数据来源和采集连接                                                             |
| `observation_id`                                  | 本次被接纳观测的内部 ID                                                                      |
| `input_sequence`                                  | 沿用 Step 2 的进程内状态提交序号，从 1 开始；本进程内不重置，用于顺序关联，不是数据库回执    |
| `siid / piid / value`                             | 属性标识和经过类型校验的值；超规格范围报错，不悄悄裁剪                                       |
| `source`                                          | `push` 上报、`initial_read` 初始化读取、`reconnect_read` 恢复读取、`on_demand_read` 按需读取 |
| `delivery_kind`                                   | `live` 实时、`baseline` 初始参考、`replayed` 重放、`unknown` 无法确认；由来源通路决定        |
| `read_semantics`                                  | 读取返回的是 `cloud_cache` 云缓存、`device_live` 设备即时值，还是 `unknown`；推送不填        |
| `observed_at / received_at`                       | 可信观测时间／backend 接收时间；没有可信观测时间时前者为 null                                |
| `source_event_id / source_sequence`               | 来源实际提供的消息 ID／序号，没有就不填                                                      |
| `read_started_at`                                 | 读取开始时间，用于识别读取期间发生的新上报                                                   |
| `quality`                                         | 下文的有效性结构                                                                             |

记录时间使用 UTC；运行内处理顺序使用 input_sequence，超时、有效期和持续条件按单调时钟计量。检测到系统时钟跳变时标注时间不确定，不据原始 UTC 重排已提交状态或推算持续时长。来源时间只有通过 Step 1 验证才可信；比接收时间晚超过 5 秒或超出已验证偏差时，将 `observed_at` 置空并记录异常。旧消息可能只是晚到，不能仅因它很旧就认定设备时钟错误。

### 当前值保存什么

`latest` 按 `{ device_id, siid, piid }` 保存一份当前值。未映射的合法属性在条目数和数据大小未超限时也可保存，但标为未知，不进入规则判断。

| 字段                                             | 含义                                                                        |
| ------------------------------------------------ | --------------------------------------------------------------------------- |
| `has_value / value`                              | 是否已有值；缺值用 false／null，不能冒充 0 或 false 的设备值                |
| `observation_id` 和来源字段                      | 当前值来自哪次观测；没有值时为 null                                         |
| `observed_at / received_at / effective_at`       | 来源时间、原始接收 UTC、被采纳为当前值时的 UTC；处理顺序另看 input_sequence |
| `last_reported`                                  | 最近收到合法实时上报的时间；读取和重放不推进它                              |
| `last_changed`                                   | 后台最近观察到已有值改变的时间；首次赋值为 null，同值不更新                 |
| `last_read_at`                                   | 最近一次成功读取的时间                                                      |
| `read_candidate`                                 | 一份无法确认比当前值更新的读取结果，供诊断使用                              |
| `observation_quality / quality / policy_version` | 原观测质量、当前有效性和采用的配置版本                                      |

读取候选（`read_candidate`）是暂时无法确认比当前值更新的读取结果。它包含 `value、read_semantics、received_at、observed_at、observation_id、observation_quality`，计入当前值的数据大小上限。新的可信观测到来后清除候选；保存候选会超过上限时，只报告该次读取失败，不降低原有可信值的质量。

## 怎样判断一个值能不能用

`quality` 为 `{ status, time_basis, reason }`。`time_basis` 表示时间依据：`source` 使用可信设备时间，`received` 使用已验证实时通路的接收时间，`unknown` 表示无法确认。

| status        | 页面和规则应怎样理解                                                         |
| ------------- | ---------------------------------------------------------------------------- |
| `valid`       | 能力、来源、值和适用时间已确认；用于持续状态的证据还须满足其更新与连续性要求 |
| `unconfirmed` | 有值，但可能是旧缓存、恢复后的旧值或已过期；可以展示，规则按未知处理         |
| `unavailable` | 设备明确离线，或所需连接／授权不可用；保留旧值并显示原因                     |
| `unknown`     | 尚无值、能力未映射或来源语义未验证                                           |

新鲜度按能力的上报方式和使用场景定义。周期测量使用有依据的 `max_age_ms`，依据包含预期上报间隔、允许延迟及该条件可容忍的数据年龄。变化上报在初值、订阅与恢复语义已验证时使用 `until_gap`，保持到明确断线、离线或丢报。无法确定有效时长时，保留观测事实，但不把它持续外推为当前状态。未验证的能力不参与规则。

观测的可信度与持续更新能力分别判断。已验证的设备即时读取可以成为读取时刻的有效事实；在能力策略允许的有效时长内，也可用于当前条件，是否有推送不单独决定它的质量。没有持续更新依据时，不能据此宣称某条件一直成立。未知时间的云缓存仍是待确认值；当前米家读取按来源契约归为未知时间的云缓存。

观测的 `quality` 随该观测保存；采纳为 latest 时复制到 `latest.observation_quality`，没有观测则为 null。`latest.quality` 按当前事实重新计算。两者复用同一质量结构，前者不随断线或到期改写；读取候选也以 `observation_quality` 保存其观测质量。工具同时返回两者，区分“当时测得”与“现在仍有效”。没有持续适用依据时，当前值使用 `unconfirmed/freshness_unverified`，保留原观测的时间和可信度。新鲜度或连续性失效不抹掉此前已确认的观测事实。

### 多个原因同时存在时

从当前事实重新计算质量，按下表从上往下选第一个适用原因。原始事实仍保留，便于一个原因解除后显示另一个。

| 顺序 | 条件                                                                     | 公开结果                                                          |
| ---- | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 1    | 能力未映射／尚无值／来源或策略未验证                                     | `unknown`：`unmapped / no_observation / contract_unverified`      |
| 2    | 设备明确离线／该值持续有效所依赖的连接或授权不可用                       | `unavailable`：`device_offline / source_disconnected`             |
| 3    | 该值依赖推送维持有效，但所需订阅被拒绝／等待确认                         | `unconfirmed`：`subscription_rejected / subscription_unconfirmed` |
| 4    | 当前值受数据超限、丢报、非法值、时间异常、过期、恢复或适用时长未确认影响 | `unconfirmed`，原因按下面的顺序选择                               |
| 5    | 以上均不成立，满足有效条件                                               | `valid / confirmed`                                               |

第 4 项的原因顺序为 `capacity_exceeded、collection_gap、invalid_value、source_time_invalid、expired、restoring、cached_unverified、freshness_unverified`。原因只作用于它实际影响的证据：推送订阅故障不否定独立即时读取在有效时长内的事实。`read_failed` 用于读取失败诊断，不因一次读取失败就推翻已有可信值。

例如温度已过期，设备又离线，先显示“设备离线”；设备重新上线后显示“值已过期”，直到收到可信新值。连接恢复和订阅成功本身不刷新旧值的时间。到期事件只更新质量，且须仍匹配当前属性版本；读取候选不延长有效期。

### 在线状态单独判断

`availability` 为 `{ status, source_id, collection_generation, observed_at, received_at, reason }`，状态是 `online / offline / unknown`。每个设备使用 Step 1 确认的在线通知来源；没有证据时来源和时间为空。

连接断开、授权失效、订阅丢失或采集重建后，在线状态变为 `unknown`，等待新的可信通知。设备清单中的 `isOnline` 只是获取清单时的记录，属性读取或视频连接成功也不自动把它改成在线。

reason 使用 `confirmed、no_observation、unsupported、contract_unverified、source_disconnected、subscription_unconfirmed、subscription_rejected、source_time_invalid、collection_gap`。只有当前有效的 `offline` 阻止新属性读取；未知不阻止尝试读取或播放。

## 新消息和读取结果冲突怎么办

- [ ] **D8：保护较新的值。** 读取开始时记下属性版本。期间收到新推送，较晚返回的读取响应不能直接覆盖它。只有来源序号或观测时间可信且可比较时，才据此判断先后；否则实时推送按当前连接的接收顺序处理。
- [ ] **D9：区分值更新与事件。** 同值实时上报更新收到时间和有效期，不产生“值变了”的事件。初始化、恢复和主动读取用于建立当前状态，不推测断线期间发生过什么。

| 收到的数据                           | 怎样处理                                                             |
| ------------------------------------ | -------------------------------------------------------------------- |
| 可信实时推送                         | 通过顺序检查后更新当前值；没有可信连续基线时建立新的比较起点         |
| 已验证为当前状态的初始消息           | 可以建立当前值，是否有效仍按质量规则判断                             |
| 设备即时读取                         | 没有被期间的新推送超过时可更新当前值；不自动证明设备在线             |
| 带可比较设备时间的云缓存             | 只有比当前证据新才替换，新鲜度按原时间判断                           |
| 没有时间保证的缓存／未知读取         | 尚无值时作为待确认初值；已有值时只保存读取候选                       |
| 已确认晚到、重放或交付性质未知的消息 | 不凭到达时间覆盖新状态；可作为符合条件的历史证据，不触发即时规则事件 |

“属性边沿”表示后台依据可信前态与后态观察到的变化，例如“关门→开门”。前态可以来自有效推送，也可以来自已验证为当前状态的读取或初始消息；后态须是顺序可确认的新实时推送，且基线建立到后态之间的订阅连续、没有已知丢报或失效。读取与推送的顺序无法比较时不建立这种连续性。只有首次值、未知时间缓存或缺口两侧的不同值时，只建立新基线，不报告新边沿。读取本身不补造断线期间的变化。

例如先确认当前为“关”，随后在连续有效订阅中收到“开”，可以报告“后台观察到关→开”，无需再等待第二次推送；没有来源时间时不声称知道精确的物理发生时间。独立按钮事件按自身已验证的实时通路和消息身份处理，不要求先有属性值。

## 用户主动读一次

沿用 `POST /api/mijia/properties/read`：

```ts
// 请求
{ scope_epoch, properties: [{ device_id, siid, piid }] }
// 响应
{ state_version, results: [{ device_id, siid, piid, status, observation_id, error_code }] }
```

请求最多 100 项、32 KiB，同一属性去重，并与当前连接已有的读取任务合并。backend 检查家庭归属、可读性和配置；家庭尚未就绪返回 HTTP 409 `household_not_ready`，运行已失效的旧请求也返回 409。

| 每项 status | 含义                                                 |
| ----------- | ---------------------------------------------------- |
| `applied`   | 已进入当前值；仍须看 quality，不能直接说“全部已确认” |
| `candidate` | 只保留为读取候选                                     |
| `unchanged` | 合法结果，但没有替换当前值                           |
| `failed`    | 没有可接纳结果；附错误原因                           |

合法接纳结果带 `observation_id`，否则为 null；成功时 `error_code=null`。错误枚举为 `not_in_scope、not_readable、capability_unverified、device_offline、source_unavailable、rate_limited、deadline_exceeded、upstream_error、invalid_response、capacity_exceeded`。候选因超过数据大小上限而被丢弃时返回 failed，不报 candidate。

整条命令最多 30 秒，包含等待和实际请求；客户端等待响应最多 35 秒，再等状态订阅追上响应版本最多 5 秒。这三个值放在共享契约中，Web 和 Agent 直接引用。到期未完成的项报告 `deadline_exceeded`。共享读取在仍有其他等待者时继续，无人需要时取消。

逐项业务结果用 HTTP 200 返回，格式错误沿用通用请求错误。命令返回已经提交的 `state_version`，页面仍从订阅取得值。超时或状态没有追上时显示“结果未确认／状态未同步”，由用户决定重试，不自动重发整条命令。

## 一条输入怎样成为公共状态

设备观测按收到顺序进入有条数和大小上限的 FIFO。退出、停止、访问撤销及采集故障立即进入家庭状态机，不等待观测积压，但影响范围分别处理：

- 退出、停止或明确访问撤销作废相应运行或设备的任务，并取消受影响的 Agent 分析。
- 临时采集故障只更新对应来源的健康，失效依赖该来源的当前条件、连续计时及旧采集任务；独立有效的读取证据仍按自身质量与期限使用，不撤销整个运行。已接纳且证据充分的纯证据分析可继续，不能因 MQTT 等设备采集断流而一并取消，具体任务边界见 [Step 6](06-agent.md#agent-任务)。

属性到期与场景持续条件检查使用同一 FIFO 的处理边界：回调触发时记住已经入队的末项，处理完此前观测后才检查；此后新入队的观测不无限延后该检查。每个属性或场景计时仅保留一份待检查边界，取消或作用域失效时释放；不占满观测队列，也不建立通用任务队列。边界内发生丢弃时先提交对应缺口、失效依赖它的连续性，再做检查。实际检查仍须核对属性／规则版本、当前质量和单调截止时间。

因此，持续开门计时到期前已经收到的关门消息必须先处理；有积压时不能只凭尚未更新的状态触发。设备清单或策略变更涉及身份、归属和解释变化时，旧观测保留入队时的上下文，提交时再核验是否仍有资格，不重新归到新设备定义。所有状态更新经过同一同步提交点，`input_sequence` 表示实际提交顺序，不是入队总数。

1. 校验当前家庭、连接和设备归属，判断消息是否可接纳。
2. 读取变更前的状态，计算本次新值、质量、准备保存的历史记录和统计。Step 6 的规则计算也使用这份变更前后数据，此时不做网络或数据库操作。
3. 一次提交本次状态、规则运行状态和后续操作描述。每次状态提交递增 `input_sequence`；只有公共内容改变才增加 `state_version.sequence`。同时记录属性是否被用作当前值证据（`state_applied`）、该次提交的 UTC `effective_at`；候选和迟到值的 state_applied/effective_at 为 false／null。
4. 按 Step 2 C12，在状态提交后统一发布状态、调整计时器，将历史记录交给 Step 4，并向 Step 6 发布带本次证据的事件。

候选公共状态复用 `@home-agent/api/immutable`，保留未变化条目引用；本次设备状态与场景结果一起接纳，提交后再执行外部操作。优先使用现有提交路径，不先建设变更键或 patches 优化机制。用实际家庭消息量观察处理耗时、内存和事件循环延迟，出现瓶颈后才优化对应扫描或复制路径，且保持现有 upsert/remove 协议与原子性。

旧任务或无效消息若直接被拒收、没有进入状态提交，就不占 `input_sequence`，也不执行本次业务操作。数据超限时，业务更新不生效，但记录或保留错误标记的提交仍占号，不执行被拒绝输入提出的业务操作。已接纳输入即使没有公共变化，只要进入提交也占号，仍可有历史或事件结果。同一进程内不重置这个序号；后台重启后重新编号。逐条提交保证快速的“开→关”不会被合成一个最终值；页面可以减少渲染次数，但不改变业务处理顺序。

设备清单按其存储契约提交；本机场景与采集配置启动时校验加载，版本用于追溯解释，不建设在线配置生效事务。数据库等待不阻塞状态机，异步结果仍须匹配当前运行。

停止时丢弃未接纳观测并记录数量；已交给历史写入器的记录按关闭期限尽量保存，维护改绑等待旧运行结束，不把积压转给新绑定。`input_sequence` 用于顺序和关联，历史写入不为每个序号建立确认账本。

## 配置哪些属性值得使用和保存

来源和能力解释由 Step 1 的 `mijia/properties/source-profiles.ts` 提供。`household/policies.ts` 按设备型号和能力定义默认策略；本机 `data/household-config.json` 可以覆盖具体设备的别名、用途和允许调整的策略。

- [ ] **D14：绑定生效配置。** 默认模板按型号与能力匹配，具体设备配置优先。配置只在启动时读取；语法错误或重复设备键显示配置错误并停止采集，单项能力不匹配只停用该能力。账号和诊断功能仍可用。
- [ ] 合法配置按内容及模板实现确定 policy_version，并记录本轮生效时间。当前采集只依赖已校验的本机配置；历史记录保存需要解释的来源、单位、质量及策略字段，配置版本不依赖单独的数据存储服务。修改配置后停止并重启相关运行，不能在运行中隐式热更新。
- [ ] 向页面发布 `read_enabled_properties: [{ siid, piid }]`，表示已经验证并启用的一次性读取能力。页面无需再读取本机文件或自行推导资格。

本机文件结构如下；文件可省略，账号和设备 ID 只出现在本机配置中：

```ts
{
  devices: [
    {
      account_id,
      home_id,
      device_id,
      alias,
      usage,
      capabilities: [{ siid, kind, iid, overrides }],
    },
  ],
  rules: [{ id, enabled, template, parameters }],
}
```

`rules` 由 Step 6 定义，不使用场景触发时可省略。`kind` 是 property 或 event，`iid` 对应属性 piid 或事件 eiid；alias、usage 可省略，capabilities 默认空。`overrides` 只允许下表的读取、新鲜度、历史保存、展示和场景开关，不修改来源验证结论。

| 策略字段                                                     | 含义与默认值                                                                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `policy_id / policy_version / effective_at / capability_key` | 生效配置身份、版本、时间和具体设备能力                                                                                       |
| `mapping_verified / source_contract_verified`                | 来自 Step 1 和规格验证，不接受手动填写“已验证”                                                                               |
| `read_enabled`                                               | 是否允许主动读取；默认 false，能力可读且通路已验证后启用                                                                     |
| `freshness_mode / max_age_ms`                                | 周期测量或即时读取使用有依据的 `max_age / 正数`；已验证变化上报用 `until_gap / null`；没有持续适用依据用 `unverified / null` |
| `history_enabled`                                            | 是否保存该能力的全部接纳观测，默认 false；明确需要的能力可立即启用，记录口径见 Step 4                                        |
| `display_enabled / rule_eligible`                            | 已映射能力默认可展示；默认不参与规则，验证语义后启用                                                                         |

可覆盖字段为 `read_enabled、freshness_mode、max_age_ms、history_enabled、display_enabled、rule_eligible`。覆盖值须符合能力已验证的适用范围，不以手填长时限升级证据保证。历史保留期限由 Step 4 定义，具体场景配置见 Step 6。

## 用真实使用校准配置

基础计数、消息量和队列健康随采集交付；间隔分布、排行榜、报告文件和诊断录制按来源验证或排障需要实现，不作为接通设备、保存已选观测或接入 Agent 的统一前置条件。下列可选诊断能力启用时仍须遵守保存与资源预算。

- [ ] **D11：统计实际消息量。** 按设备和能力记录收到次数、变化次数、同值次数、可确认的重复次数、无效次数、字节量、间隔分布与最近收到时间。独立事件单独统计。没有可靠消息身份时重复率为“无法判定”，不能拿同值率代替。
- [ ] **D12：观察实际使用。** 覆盖所选场景的正常操作、同值上报和断连恢复；可以持续一天了解频率，但不作为开始保存或 Agent 接入的等待门槛。
- [ ] **D13：按需录制诊断数据。** `--record-household-observations` 开启本轮规范化观测录制，默认关闭；本机文件最多 24 小时、100,000 条或 128 MiB，任一达到即停止，停止运行同时结束录制。只保存校验后字段，不保存供应商原始报文或凭据，也不依赖 Step 4 的表。

统计报告写入 `data/diagnostics/household-collection/report.json`，只保留一份，包含运行标识、时间、流量最高的 20 项和队列／错误情况；写入失败不影响采集。录制文件沿用同一目录，开始新录制前按总预算清理过期文件，不累积无界诊断数据。

## 数量过大或处理不过来时

上限集中放在运行配置中，是项目的初始资源预算，不是供应商或框架硬上限。用首轮实测的消息量、条目大小、队列高水位和处理延迟校准；新鲜度等会改变业务判断的策略按能力单独验证。

| 编号 | 对象               | 初始上限和处理                                                                                                           |
| ---- | ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| E1   | 当前值             | 最多 20,000 项或 2 MiB，包含读取候选；按 Step 5 提交前检查，给质量和错误字段留空间。超限保留旧值并标待确认，新键不接纳。 |
| E2   | 单次输入与诊断样本 | 单值 16 KiB、消息 256 KiB；更小的协议限制优先。脱敏样本最多 100 条或 256 KiB，覆盖最旧样本，新运行清空。                 |
| E3   | 一轮处理量         | 每轮最多 128 条观测，然后交还事件循环；低流量立即处理，不固定等满批次。                                                  |
| E4   | 观测缓冲           | 单一先进先出队列，最多 2,048 条或 4 MiB；数据按接收顺序处理，不按类别切出配额。                                          |
| E4   | 历史缓冲           | 独立于采集，最多 10,000 条或 16 MiB，包含正在写入的批次；具体失败处理见 Step 4。                                         |
| E7   | 统计输出           | 启用日志或报告时，每 10 秒合并更新，不逐条打印高频消息。                                                                 |

大小按序列化数据估算，并监测实际内存。公共状态与 SSE 的限制统一见 Step 5。

**E6：观测过载时限定丢失范围并恢复接收。** 队列满时拒收新观测，记录受影响来源或能力、缺口与可确定的丢弃数量；无法确定细分范围时按受影响通路处理。缺口通过不经过观测队列的控制事件先提交，失效依赖丢失观测的当前值与连续计时；在线状态仅在其证据也受影响时改为未知。独立读取证据按自己的适用时长判断，不因推送过载一并撤销。清除受影响范围内尚未处理的旧观测并计入丢弃数，避免缺口前积压重新建立可信基线；随后以缺口后的可信数据恢复，遵守来源的实时、缓存和重放语义。

本地队列满不等于来源连接故障。短暂过载默认保留正常连接，释放积压后继续接收；适配器有经过验证的暂停能力时可以暂停输入，但不能把积压转移到无界缓冲。只有持续过载无法通过本地处理限制，或适配器必须断开才能停止输入时，才停止受影响来源的采集。停止后按有界退避恢复；实际断开的连接和订阅由现有米家模块重建，旧连接迟到消息按采集代次拒收。补读仅用于有已验证读取能力且需要恢复基线的属性，并遵守既有并发与限流预算，不因每次溢出自动补读。

`source_health` 区分丢弃后继续接收、暂停输入、等待恢复和持续过载暂停，公开缺口及原因；只有安排了重试才显示下次重试时间。反复恢复仍过载时暂停自动恢复，连续失败预算初值为 5 次，连续健康运行 60 秒后清零，按实测校准。用户可通过 `connection/retry` 重启暂停的恢复流程；重复请求合并，不并行建连，也不绕过供应商限流。退出或停止取消恢复计时，只有当前作用域能恢复采集。

**E5：历史尽力保存。** 单纯历史写入失败或历史缓冲溢出，只影响历史完整性，实时最新值继续更新。进程异常退出时，内存里尚未保存的数据可能丢失；Step 4 记录已知缺口和未确认范围，首期不承诺可靠告警或断电零丢失。

## 完成条件

- [ ] 无人打开页面时仍能接收设备变化；退出、停止及重新初始化后旧任务不会写回当前状态。
- [ ] 同值上报可更新收到时间；未知缓存和恢复值不补造事件，可信连续基线之后的第一次实时变化可以触发边沿。
- [ ] 读取期间的新推送不会被晚到的云缓存覆盖；读取失败不抹掉已有可信值。
- [ ] 断线、离线、过期和能力未知能分别展示；重新连上不能把旧值自动变成有效。
- [ ] 订阅失败可单独重试；即时读取按自己的时间与来源判断，不以有无推送决定可信度；明确离线时暂缓读取，在线未知仍可尝试。
- [ ] 采集配置启动时生效，历史故障不阻止当前采集；已明确要保存的能力不等待观察满一天。
- [ ] 到期检查不越过此前已收到的观测；积压期间已收到关门不能触发持续开门，退出和撤销不等待积压。
- [ ] 观测质量保留原值，latest 当前质量独立变化，字段在历史与工具中保持同义。
- [ ] 瞬时过载记录缺口并自动恢复；持续过载有明确暂停原因及重试入口。慢数据库或慢页面不会造成无限积压。
- [ ] 能根据实际使用说明哪些属性值得保存及其数据量；新鲜度按能力的更新规律与使用场景验证。
- [ ] 采集 actor 停止后观察、读取与计时资源实际释放；协议恢复只有现有米家模块负责，旧回调不能写回。
- [ ] 未变化条目保留引用；使用实际流量确认处理成本，只有观察到瓶颈才扩大优化范围。
- [ ] 按总览完成共同检查，更新当前实现文档与仍未验证的限制。

按场景需要接入 [Step 4](04-history.md) 的历史或 [Step 6](06-agent.md) 的分析，并用 [Step 5](05-live-web.md) 展示已交付状态。
