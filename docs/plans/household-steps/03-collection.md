# Step 3：接收设备变化，维护当前状态

**状态：待执行。** 前置条件是 Step 1 的设备通路已验证，Step 2 已能选择并运行一个家庭。

[返回总览](../backend-household-perception.md)

本步让后台持续接收设备消息，记住每个属性最近的值，并说明这个值现在是否可信。比如温度计报告 25℃，页面应能看到数值、收到时间和连接状态；断线后保留 25℃，但明确提示它可能已经过时。

先观察一天的真实数据，再决定哪些值得长期保存。历史入库在 Step 4，规则和 Agent 推理在 Step 6。人员活动等[家庭语义](../household-model.md)属于后续场景，不混进设备原始状态。

## 本步使用的几个名称

| 名称                    | 在本文中的意思                                        |
| ----------------------- | ----------------------------------------------------- |
| 观测                    | 一次设备上报、读取结果或在线通知                      |
| `latest`                | 每个设备属性的当前值，以及它的来源、时间和有效性      |
| `quality`               | 当前值是否还能使用；具体状态见下文                    |
| `availability`          | 设备的在线、离线或未知状态                            |
| `source_health`         | 数据连接、授权和订阅是否正常                          |
| `scope_epoch`           | 当前家庭这一次运行的标识；切家后换新标识，沿用 Step 2 |
| `collection_generation` | 这一轮采集连接的标识；重连或更换凭据后换新标识        |

“最近读到过”与“现在仍然有效”分开表达。连接成功、设备在线、某个属性可信，也分别记录。

## 采集如何运行

`household/collection.ts` 管理订阅和读取；`household/observations.ts` 校验消息并交给家庭状态机。小米协议继续由 Step 1 的 `properties/` 和 `protocols/` 实现。

- [ ] **D10：随家庭运行。** 家庭初始化完成后启动采集，无人打开页面也继续接收消息。切家、退出、设备移除时取消对应任务。切家沿 Step 2 先清空旧运行状态，再初始化新家庭，允许暂时不可用。
- [ ] **D7：订阅后补齐必要的值。** 使用 Step 1 的 `observeDevices` 和 `readProperties`。初次启用、设备加入、规格就绪、设备重新上线或连接恢复时，对缺值或待确认的属性读一次。同一属性已有读取任务就复用，重复目录刷新不再读一遍。
- [ ] 读取仅用于初始化、恢复和用户显式请求。没有推送能力时显示限制，不增加周期属性轮询。

自动读取针对已配置 `read_enabled` 的可读属性。明确离线的设备暂缓读取；在线未知仍可读取。单个属性失败不阻塞其他属性，没有推送通路的可读属性也可以单独读取。

请求参数沿用 Step 1：共用串行读取批次，每批最多 150 项、请求最多 30 秒；上线后等待 20 秒合并短时间内的重复通知，重连补读等待 15 秒。认证失败交给账号模块，服务端限流按其要求等待。其他失败显示原因，等待下一次真实触发或用户重试。

### 订阅失败与来源健康

连接正常不代表全部设备已经订阅成功。`source_health` 分别记录连接、认证、待订阅／已确认／失败数量、覆盖范围、最近确认和观测时间。未验证或不支持的能力，以及采集是否暂停、暂停原因，也明确列出。

显式重试沿用 `POST /api/mijia/connection/retry`。只有部分订阅失败时，重试这些订阅并保留健康连接；采集因 E6 过载暂停时，重新建立采集连接、订阅和补读。并发与确认期限使用 Step 1 的 16 项、10 秒；重复点击合并，结果通过状态订阅显示。

MIoT 通路沿用 Step 1 已确认的解释：活动连接上的合法属性／在线推送按实时消息处理，使用接收时间；云缓存读取按初始参考值处理。订阅确认前收到的合法消息照常校验和保存，但暂不认作有效值；确认订阅不补造此前发生的事件。独立设备事件需要真实通路支持，不能用属性变化冒充。

## 接收什么数据

- [ ] **D1：分清三类消息。** `property_report` 表示属性值，`device_event` 表示按钮、告警等独立事件，`availability` 表示在线状态。
- [ ] **D2：在适配入口校验。** 用共享 Zod 数据格式检查身份、类型、规格和大小，再送给家庭状态机。账号和家庭归属由 backend 关联。
- [ ] **D3：只做有依据的去重。** 每次接纳的观测分配 `observation_id`，历史写入重试保持同一 ID。供应商重传按 Step 1 确认的消息身份／序号规则处理，范围限定在它实际有效的连接内；没有可靠依据就标为无法判定。相同数值可以是新的上报，按钮事件尤其不能按值去重。
- [ ] **D4：拒收旧任务和错误消息。** 旧家庭、旧连接、身份冲突或格式错误的消息不更新当前状态。只保留原因计数和少量脱敏样本，限制见 E2。
- [ ] **D5／D6：接收、保存和展示分别决定。** 当前家庭的合法推送可以进入最新值和统计；历史只保存选中的能力；页面和规则只使用各自需要且已解释清楚的字段。MiLoCo 的消费白名单与规格 `notify` 标记不能直接充当接收或历史白名单。复用其文件前核对许可。

### 观测字段

属性使用真实的服务标识 `siid` 和属性标识 `piid`；独立事件使用 `siid/eiid`，参数按事件规格校验；在线通知只带设备与在线事实。

| 字段                                              | 含义                                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `account_id / home_id / device_id`                | 账号、家庭和设备身份                                                                         |
| `scope_epoch / source_id / collection_generation` | 所属家庭运行、数据来源和采集连接                                                             |
| `observation_id`                                  | 本次被接纳观测的内部 ID                                                                      |
| `input_sequence`                                  | 家庭状态机接纳输入的先后序号，从 1 开始；用于顺序关联，不是数据库回执                        |
| `siid / piid / value`                             | 属性标识和经过类型校验的值；超规格范围报错，不悄悄裁剪                                       |
| `source`                                          | `push` 上报、`initial_read` 初始化读取、`reconnect_read` 恢复读取、`on_demand_read` 按需读取 |
| `delivery_kind`                                   | `live` 实时、`baseline` 初始参考、`replayed` 重放、`unknown` 无法确认；由来源通路决定        |
| `read_semantics`                                  | 读取返回的是 `cloud_cache` 云缓存、`device_live` 设备即时值，还是 `unknown`；推送不填        |
| `observed_at / received_at`                       | 可信观测时间／backend 接收时间；没有可信观测时间时前者为 null                                |
| `source_event_id / source_sequence`               | 来源实际提供的消息 ID／序号，没有就不填                                                      |
| `read_started_at`                                 | 读取开始时间，用于识别读取期间发生的新上报                                                   |
| `quality`                                         | 下文的有效性结构                                                                             |

时间使用 UTC；超时按实际经过的时长计量，避免系统时间调整影响等待长度。来源时间只有通过 Step 1 验证才可信；比接收时间晚超过 5 秒或超出已验证偏差时，将 `observed_at` 置空并记录异常。旧消息可能只是晚到，不能仅因它很旧就认定设备时钟错误。

### 当前值保存什么

`latest` 按 `{ device_id, siid, piid }` 保存一份当前值。未映射的合法属性也可在容量范围内保存，但标为未知，不进入规则判断。

| 字段                                       | 含义                                                         |
| ------------------------------------------ | ------------------------------------------------------------ |
| `has_value / value`                        | 是否已有值；缺值用 false／null，不能冒充 0 或 false 的设备值 |
| `observation_id` 和来源字段                | 当前值来自哪次观测；没有值时为 null                          |
| `observed_at / received_at / effective_at` | 设备观测、后台接收、成为当前值的时间                         |
| `last_reported`                            | 最近收到合法实时上报的时间；读取和重放不推进它               |
| `last_changed`                             | 后台最近观察到已有值改变的时间；首次赋值为 null，同值不更新  |
| `last_read_at`                             | 最近一次成功读取的时间                                       |
| `read_candidate`                           | 一份无法确认比当前值更新的读取结果，供诊断使用               |
| `quality / policy_version`                 | 当前有效性和采用的配置版本                                   |

读取候选包含 `value、read_semantics、received_at、observed_at、observation_id`，计入最新值容量。新的可信观测到来后清除候选；候选放不下时只报告该次读取失败，不降低原有可信值的质量。

## 怎样判断一个值能不能用

`quality` 为 `{ status, time_basis, reason }`。`time_basis` 表示时间依据：`source` 使用可信设备时间，`received` 使用已验证实时通路的接收时间，`unknown` 表示无法确认。

| status        | 页面和规则应怎样理解                                                                 |
| ------------- | ------------------------------------------------------------------------------------ |
| `valid`       | 设备能力和来源已验证，所需订阅已确认，值与类型合法，期间没有丢报且未过期；可用于规则 |
| `unconfirmed` | 有值，但可能是旧缓存、恢复后的旧值或已过期；可以展示，规则按未知处理                 |
| `unavailable` | 设备明确离线，或所需连接／授权不可用；保留旧值并显示原因                             |
| `unknown`     | 尚无值、能力未映射或来源语义未验证                                                   |

温度等连续数值默认 15 分钟后待确认，可按实测调整。门磁等“变化时才上报”的状态，在通路及恢复方式已经验证时可以一直有效，直到断线、离线或丢报；不因长时间没变化而自动过期。未验证的能力不参与规则。

没有持续推送的设备仍可读取和展示值，但保持 `unconfirmed/unsupported`：只能说明读到过，不能承诺持续掌握其状态。`device_live` 表示这一次读取的性质，不能代替持续采集能力。

### 多个原因同时存在时

从当前事实重新计算质量，按下表从上往下选第一个适用原因。原始事实仍保留，便于一个原因解除后显示另一个。

| 顺序 | 条件                                                 | 公开结果                                                                        |
| ---- | ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1    | 能力未映射／尚无值／来源或策略未验证                 | `unknown`：`unmapped / no_observation / contract_unverified`                    |
| 2    | 设备明确离线／来源连接或授权不可用                   | `unavailable`：`device_offline / source_disconnected`                           |
| 3    | 不支持持续推送／订阅被拒绝／等待确认                 | `unconfirmed`：`unsupported / subscription_rejected / subscription_unconfirmed` |
| 4    | 当前值受容量、丢报、非法值、时间异常、过期或恢复影响 | `unconfirmed`，原因按下面的顺序选择                                             |
| 5    | 以上均不成立，满足有效条件                           | `valid / confirmed`                                                             |

第 4 项的原因顺序为 `capacity_exceeded、collection_gap、invalid_value、source_time_invalid、expired、restoring、cached_unverified`。没有持续推送、但读取通路已验证的能力走第 3 项。`read_failed` 用于读取失败诊断，不因一次读取失败就推翻已有可信值。

例如温度已过期，设备又离线，先显示“设备离线”；设备重新上线后显示“值已过期”，直到收到可信新值。连接恢复和订阅成功本身不刷新旧值的时间。到期事件只更新质量，且须仍匹配当前属性版本；读取候选不延长有效期。

### 在线状态单独判断

`availability` 为 `{ status, source_id, collection_generation, observed_at, received_at, reason }`，状态是 `online / offline / unknown`。每个设备使用 Step 1 确认的在线通知来源；没有证据时来源和时间为空。

连接断开、授权失效、订阅丢失或采集重建后，在线状态变为 `unknown`，等待新的可信通知。目录中的 `isOnline` 只是目录获取时的记录，属性读取或视频连接成功也不自动把它改成在线。

reason 使用 `confirmed、no_observation、unsupported、contract_unverified、source_disconnected、subscription_unconfirmed、subscription_rejected、source_time_invalid、collection_gap`。只有当前有效的 `offline` 阻止新属性读取；未知不阻止尝试读取或播放。

## 新消息和读取结果冲突怎么办

- [ ] **D8：保护较新的值。** 读取开始时记下属性版本。期间收到新推送，较晚返回的读取响应不能直接覆盖它。只有来源序号或观测时间可信且可比较时，才据此判断先后；否则实时推送按当前连接的接收顺序处理。
- [ ] **D9：区分值更新与事件。** 同值实时上报更新收到时间和有效期，不产生“值变了”的事件。初始化、恢复和主动读取用于建立当前状态，不推测断线期间发生过什么。

| 收到的数据                           | 怎样处理                                                             |
| ------------------------------------ | -------------------------------------------------------------------- |
| 可信实时推送                         | 通过顺序检查后更新当前值；恢复后的第一条建立新的比较起点             |
| 已验证为当前状态的初始消息           | 可以建立当前值，是否有效仍按质量规则判断                             |
| 设备即时读取                         | 没有被期间的新推送超过时可更新当前值；不自动证明设备在线             |
| 带可比较设备时间的云缓存             | 只有比当前证据新才替换，新鲜度按原时间判断                           |
| 没有时间保证的缓存／未知读取         | 尚无值时作为待确认初值；已有值时只保存读取候选                       |
| 已确认晚到、重放或交付性质未知的消息 | 不凭到达时间覆盖新状态；可作为符合条件的历史证据，不触发即时规则事件 |

“属性边沿”指可确认的前后变化，例如“关门→开门”。只有同一采集连接内，两条连续、有效的实时推送才能构成它。首次读到开门、恢复后发现开门、从缓存读到不同值，都不能据此报告“刚刚开门”。独立按钮事件有自己的消息身份和已验证通路，可以直接处理，不要求先有属性值。

## 用户主动读一次

沿用 `POST /api/mijia/properties/read`：

```ts
// 请求
{ scope_epoch, properties: [{ device_id, siid, piid }] }
// 响应
{ state_version, results: [{ device_id, siid, piid, status, observation_id, error_code }] }
```

请求最多 100 项、32 KiB，同一属性去重，并与当前连接已有的读取任务合并。backend 检查家庭归属、可读性和配置；家庭尚未就绪返回 HTTP 409 `household_not_ready`，切家后的旧请求也返回 409。

| 每项 status | 含义                                                 |
| ----------- | ---------------------------------------------------- |
| `applied`   | 已进入当前值；仍须看 quality，不能直接说“全部已确认” |
| `candidate` | 只保留为读取候选                                     |
| `unchanged` | 合法结果，但没有替换当前值                           |
| `failed`    | 没有可接纳结果；附错误原因                           |

合法接纳结果带 `observation_id`，否则为 null；成功时 `error_code=null`。错误枚举为 `not_in_scope、not_readable、capability_unverified、device_offline、source_unavailable、rate_limited、deadline_exceeded、upstream_error、invalid_response、capacity_exceeded`。候选因容量被丢弃时返回 failed，不报 candidate。

整条命令最多 30 秒，包含等待和实际请求；客户端等待响应最多 35 秒，再等状态订阅追上响应版本最多 5 秒。这三个值放在共享契约中，Web 和 Agent 直接引用。到期未完成的项报告 `deadline_exceeded`。共享读取在仍有其他等待者时继续，无人需要时取消。

逐项业务结果用 HTTP 200 返回，格式错误沿用通用请求错误。命令返回已经提交的 `state_version`，页面仍从订阅取得值。超时或状态没有追上时显示“结果未确认／状态未同步”，由用户决定重试，不自动重发整条命令。

## 一条输入怎样成为公共状态

设备观测按收到顺序进入一个有上限的队列。切家、目录完成、策略变化和到期等控制事件直接进入家庭状态机，避免设备积压堵住停止操作。所有状态更新仍经过同一个同步提交点，`input_sequence` 表示实际接纳顺序。

1. 校验当前家庭、连接和设备归属，判断消息是否可接纳。
2. 读取变更前的状态，计算本次新值、质量、历史记录候选和统计。Step 6 的规则计算也使用这份变更前后数据，此时不做网络或数据库操作。
3. 一次提交本次状态、规则运行状态和后续操作描述。接纳输入分配 `input_sequence`；只有公共内容改变才增加 `state_version.sequence`。同时记录属性是否被用作当前值证据（`state_applied`）及生效时间（`effective_at`）；候选和迟到值分别为 false／null。
4. 通过 Step 2 C12 的提交后出口发布状态、调整计时器，将历史记录交给 Step 4，并向 Step 6 发布带本次证据的事件。

被拒绝的输入不占序号、不执行本次业务操作；接纳但公共值未改变的消息仍可有历史或事件结果。逐条提交保证快速的“开→关”不会被合成一个最终值；页面可以减少渲染次数，但不改变业务处理顺序。

目录、策略和规则保存成功后才发送生效事件。切家则沿 Step 2 B5 先清空旧状态，再保存和初始化。数据库等待不阻塞状态机；保存结果进入状态机时重验所属家庭和版本即可。

切家或停止时丢弃尚未接纳的旧观测，记录丢弃数量和对应采集缺口；已交给历史写入器的记录保留原家庭身份继续处理。`input_sequence` 用于顺序和关联，历史写入不为每个序号建立确认账本。

## 配置哪些属性值得使用和保存

来源和能力解释由 Step 1 的 `mijia/properties/source-profiles.ts` 提供。`household/policies.ts` 按设备型号和能力定义默认策略；本机 `data/household-config.json` 可以覆盖具体设备的别名、用途和允许调整的策略。

- [ ] **D14：绑定生效配置。** 默认模板按型号与能力匹配，具体设备配置优先。配置只在启动时读取；语法错误或重复设备键显示配置错误并停止采集，单项能力不匹配只停用该能力。账号和诊断功能仍可用。
- [ ] 配置生效后保存到 `collection_policies`，记录版本、来源契约、规格版本和生效时间。相同内容复用版本，变化才产生新版本，供历史解释。启动时无法保存本次配置则暂停受影响能力，显示错误，不静默使用旧配置。
- [ ] 向页面发布 `read_enabled_properties: [{ siid, piid }]`，表示已经验证并启用的一次性读取能力。页面无需再读取本机文件或自行推导资格。

本机文件结构如下；文件可省略，账号和设备 ID 只出现在本机配置中：

```ts
{
  devices: [
    {
      account_id,
      home_id,
      device_id,
      alias,
      usage,
      capabilities: [{ siid, kind, iid, overrides }],
    },
  ];
}
```

`kind` 是 property 或 event，`iid` 对应属性 piid 或事件 eiid；alias、usage 可省略，capabilities 默认空。`overrides` 只允许下表的读取、新鲜度、历史、阈值、汇总、展示和规则开关，不修改来源验证结论。

| 策略字段                                                     | 含义与默认值                                                                                                                                 |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `policy_id / policy_version / effective_at / capability_key` | 生效配置身份、版本、时间和具体设备能力                                                                                                       |
| `mapping_verified / source_contract_verified`                | 来自 Step 1 和规格验证，不接受手动填写“已验证”                                                                                               |
| `read_enabled`                                               | 是否允许主动读取；默认 false，能力可读且通路已验证后启用                                                                                     |
| `freshness_mode / max_age_ms`                                | `max_age / 900000`：15 分钟期限；已验证变化上报用 `until_gap / null`；未验证用 `unverified / null`                                           |
| `history_mode`                                               | `none` 不保存、`all` 全部、`changes` 变化时保存、`last_valid_per_window` 每个时间段保留最后有效值；默认 none                                 |
| `history_window_ms / important_change_threshold`             | 采样段默认 60000 毫秒；其他模式 window=null；重要变化阈值默认 null，可按属性单位配置                                                         |
| `summary_enabled / summary_window_ms`                        | 是否生成统计摘要，默认 false／null；开启后固定 5 分钟，并合成小时摘要                                                                        |
| `metric_kind / interpolation / counter_reset_signal`         | 指标类型为 `gauge / power / counter`；数值按上次有效值保持（`interpolation=previous`），计数器须有可信重置信号；未声明为 null，算法见 Step 4 |
| `display_enabled / rule_eligible`                            | 已映射能力默认可展示；默认不参与规则，验证语义后启用                                                                                         |

可覆盖字段为 `read_enabled、freshness_mode、max_age_ms、history_mode、important_change_threshold、summary_enabled、display_enabled、rule_eligible`。时间段长度、算法和计数器重置依据由模板确定。

历史明细和摘要可以分别启用；启用任一项都保存所需的有效性和缺口信息。数据保留期限统一由 Step 4 定义。

## 先看一天真实数据

- [ ] **D11：统计实际消息量。** 按设备和能力记录收到次数、变化次数、同值次数、可确认的重复次数、无效次数、字节量、间隔分布与最近收到时间。独立事件单独统计。没有可靠消息身份时重复率为“无法判定”，不能拿同值率代替。
- [ ] **D12：连续观察 24 小时。** 包含正常使用、真实开关门等操作，记录断网等特殊时段。根据数据选择需要长期保存的属性和采样方式。
- [ ] **D13：按需录制诊断数据。** 启动参数 `--record-household-observations` 开启一次规范化观测录制，绑定首次运行的家庭，切家即结束。默认关闭，最多 24 小时、100,000 条或 128 MiB，任一达到即停止。存储沿用 Step 4 的诊断表；表未就绪时报告未启动，正常采集继续。

录制只保存校验后的值和来源元数据，不保存供应商原始报文或凭据。统计文件为 `data/diagnostics/household-collection/report.json`，包含当前家庭运行标识、统计时间、接收量最高的 20 项、错误和队列情况；只保留一份，切家重置当前统计。报告写入失败记日志，不影响采集。

## 数量过大或处理不过来时

上限集中放在运行配置中，首轮实测后再调整。它们用于限制实际资源占用，不为每一类消息建立调度系统。

| 编号 | 对象               | 初始上限和处理                                                                                                           |
| ---- | ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| E1   | 当前值             | 最多 20,000 项或 2 MiB，包含读取候选；按 Step 5 提交前检查，给质量和错误字段留空间。超限保留旧值并标待确认，新键不接纳。 |
| E2   | 单次输入与诊断样本 | 单值 16 KiB、消息 256 KiB；更小的协议限制优先。脱敏样本最多 100 条或 256 KiB，覆盖最旧样本，切家清空。                   |
| E3   | 一轮处理量         | 每轮最多 128 条观测，然后交还事件循环；低流量立即处理，不固定等满批次。                                                  |
| E4   | 观测缓冲           | 单一先进先出队列，最多 2,048 条或 4 MiB；数据按接收顺序处理，不按类别切出配额。                                          |
| E4   | 历史缓冲           | 独立于采集，最多 10,000 条或 16 MiB，包含正在写入的批次；具体失败处理见 Step 4。                                         |
| E7   | 统计输出           | 每 10 秒合并更新日志与报告，不逐条打印高频消息。                                                                         |

大小按序列化数据估算，并监测实际内存。公共状态与 SSE 的限制统一见 Step 5。

**E6：观测队列满时暂停采集。** 停止接收并取消当前采集连接，清空尚未处理的设备观测，通过状态机控制事件将相关属性标为待确认、在线状态改为未知，并记录丢失时段及可确定的数量。控制事件不经过已满的观测队列。

页面显示“采集过载，已暂停”，用户通过现有 `connection/retry` 重试。重试创建新的采集连接，重新订阅和补读；旧连接的剩余消息被拒收，新数据先建立可信当前状态。这样接受一次明确的数据缺口，不增加优先级队列或逐消息恢复机制。

**E5：历史尽力保存。** 单纯历史写入失败或历史缓冲溢出，只影响历史完整性，实时最新值继续更新。进程异常退出时，内存里尚未保存的数据可能丢失；Step 4 用明确的未知区间表达，首期不承诺可靠告警或断电零丢失。

## 完成条件

- [ ] 无人打开页面时仍能接收设备变化；切家、退出和停止后旧任务不会写回当前状态。
- [ ] 同值上报可更新收到时间；初始化、补读和恢复不会编造“刚刚发生”的事件。
- [ ] 读取期间的新推送不会被晚到的云缓存覆盖；读取失败不抹掉已有可信值。
- [ ] 断线、离线、过期和能力未知能分别展示；重新连上不能把旧值自动变成有效。
- [ ] 订阅失败可单独重试；明确离线时暂缓读取，在线未知仍可尝试。
- [ ] 过载会暂停采集并显示错误，重试后建立新状态；慢数据库或慢页面不会造成无限积压。
- [ ] 能从一天的报告说明哪些属性值得保存、为何采用该采样方式。
- [ ] 按总览完成共同检查，更新当前实现文档与仍未验证的限制。
