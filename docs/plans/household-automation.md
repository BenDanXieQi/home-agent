# 家庭情景与自动化：第一方 Agent 协作计划

**状态：实施设计，尚未实现。** 本文定义下一阶段的协作契约、首个场景及实施顺序。当前已实现设备接入、持续属性采集、房间事实与 AI 观测描述、本地检测、人体外观跟踪、猫狗位置跟踪和独立文本对话服务。房间分析使用独立的一次性图，支持手动和可信属性变化触发，限制见[房间 AI 上下文](../contracts/room-analysis.md)；现有聊天图没有家庭工具，家庭任务尚无统一执行入口或调用预算。接口、字段、模块及表名均为实施目标，不是可调用能力。

领域定义以[家庭模型](household-model.md)为准，媒体计算以[摄像头计划](media-perception.md)为准，当前设备事实沿用[设备事实契约](../contracts/device-facts.md)，新增来源和历史接入见[设备采集计划](device-collection.md)。本文统一规定持续情景维护、长期任务、规则与语义触发、统一执行及证据获取的协作方式，不另建 backend 语义 LLM 流程。

阅读路径：[任务与规则](#3-长期任务与持续情景) → [身份与位置](#4-身份与位置的本地处理) → [接口](#6-具体接口与工具) → [执行与费用](#7-第一方-harness-的执行路径与费用) → [实施顺序](#9-实施顺序与改动位置)。领域含义不在此另定，P2–P4 媒体细节与设备原始状态分别引用所属计划。

## 家庭资料、记忆与查询约束

后台保存确认后的身份、设备关联和明确偏好；Agent 记忆维护有依据的推测习惯。一次操作先记为经历，多次独立经历才可提出条件化偏好；操作者不明时不归入某人画像。新增经历、纠正或明确指令触发更新，不定时重写全部记忆。

活动由本文的情景事件所有者维护候选、进行中、结束及修正，不归设备原始历史写入器。证据撤回影响相关判断及“上一次”索引；明细清理后保留必要证据摘要和追溯限制。当前位置、上一次遛狗和未开灯原因分别查询情景、活动索引和执行记录，按对象、时间及大小取证；答案区分事实、推测与未知，不扫描全量日志或因记录缺失断言从未发生。

切换家庭遵守[清理流程](../household-runtime.md#切换家庭与清理数据)。新增画像、长期记忆、情景、活动索引、任务与执行记录都必须纳入清理，不能跨家庭复用。

米家自身独立运行的自动化不受本项目拦截。需要遵守本项目动作条件时，必须验证对方支持条件接入，或使用本项目经过核验的执行路径。喂食等动作仍需检查近期投喂量、储粮／食碗状态、上限与权限；建议、请求发出、设备响应和效果核对分别记录，结果未知先核对，历史纠正不重执行动作。

## 1. 交付决定与首个场景

采用现有 backend 与 Agent 两个本机进程，HTTP/SSE 通信。backend 持续运行本地感知和家庭状态；第一方 Agent 拥有目标理解、上下文选择、模型与工具编排。Agent 可以主动提出或调整受控观察请求，backend 按已实现的模板持续执行。模型、提示词、工具、观察策略和效果评估由同一项目共同演进。

主线是“持续家庭情景 → 用户长期任务 → 确定性规则或 Agent 判断触发 → 统一执行”。首期成员位置是按身份汇总最后出现房间及时间，独立于具体提醒；不要求保持连续轨迹或还原跨房间经过。跟踪可辅助选帧和减少重复核验，合格的新证据需要语义理解时才调用 Agent。业务到期或触发时读取已有情景并核对所需时效，最后出现记录不能直接证明当前位置；不临时启动识别并等待其完成。临时观察补充范围或证据，不是所有家庭任务的父对象。

基础维护须在实际授权范围内启用；位置未知、覆盖缺失或证据过期时如实降级。卧室和卫生间不增加摄像头；跨房间维护不等于所有房间都可定位。尚未实现的来源与推断不能列为可用能力。

完成后应具备：

1. 用户经已有聊天 API 提出目标，Agent 查询能力和家庭上下文，启用基础维护或提交有限期观察请求，并向用户说明接纳结果及不可观察区域。
2. backend 持续检测、跟踪，按已接纳身份保存出现记录并汇总最近房间；无轨迹但有合格画面也可核验，不逐帧调用模型。
3. 未知或冲突目标出现有用新证据时，backend 产生核验候选；本地识别执行器与 Agent harness 分别按任务、证据和各自预算准入，可独立启用或并行运行。
4. 本地身份模型读取合格图片及版本化参考资料，Agent 读取对应媒体、成员参考及任务上下文；各自提交身份候选，场景理解由 Agent 提交；backend 接纳后更新家庭状态。
5. 用户再次提问时，Agent 通过工具读取当前／最后已知状态，给出带时间与限制的回答；不会为了回答已有状态而默认再拍一段视频。
6. Agent 暂停后，本地感知、关联有效性和到期处理继续；已启用的本地身份识别继续，新 LLM 核验暂停。恢复时只处理仍有效且有新价值的候选。

最终场景分批交付：场景观察闭环与成员身份／位置按各自依赖接入，本地身份路径不等待场景 LLM 闭环。首批同时验证基于已有情景的确定性策略处理结果，但不发送命令；情景更新异步进行，即时处理不等待 LLM。首批不交付设备控制、主动通知、未知人物永久建档、自动样本晋升或长期习惯学习。它们不成为持续本地感知的前置条件。

## 2. 模块与状态所有权

| 位置                                            | 拥有的状态及职责                                             | 不承担的职责                       |
| ----------------------------------------------- | ------------------------------------------------------------ | ---------------------------------- |
| backend `perception/tracking/`                  | 每来源运行的局部轨迹、实测框／预测框、近期外观特征           | 家庭成员真值、LLM 调用             |
| backend `perception/window/`、`gate/`、`media/` | 有界媒体、窗口、变化与质量指标、证据描述                     | 用户目标解释、供应商模型协议       |
| backend `perception/identity/`                  | 本地身份模型适配、选帧质量检查、特征计算及有界执行           | 正式成员身份、LLM 调用             |
| backend `household/identity/`                   | 成员参考资料、观察目标与成员关联、冲突与纠正                 | 复制 tracker、独立语义提示词       |
| backend `household/presence/`                   | 出现记录、最后被看见及最后已定位的汇总                       | 以摄像头安装房间直接代替目标位置   |
| backend `household/observation-requests/`       | 已接纳的持续观察请求、模板条件、候选当前视图和变化通知       | Agent 执行队列、推理记录           |
| backend `household/assessments/`、`events/`     | 已接纳情景的有效性、领域事件和修正依赖                       | 模型推理与任务 checkpoint          |
| backend `household/automations/`、`actions/`    | 长期任务定义、确定性条件、持久期限、动作意图和结果           | 穷举开放语义识别、运行模型生成代码 |
| Agent `runtime/`                                | 任务执行、并发、取消、模型请求预算、执行记录                 | 家庭实时状态                       |
| Agent `household/`                              | 目标解释、观察工具、上下文组织、LLM 身份／场景任务与结果提交 | 直接改 backend 数据库              |
| `packages/api/src/contracts/`                   | 跨应用请求、响应和事件 schema，类型从 schema 推导            | 运行对象或厂商协议                 |

`household/observation-requests/` 管理持续观察需求，设备采集计划的 `household/observations.ts` 继续表示设备观测规则。不把采集、身份与位置塞进同一个家庭 actor；各所有者同步提交自己的数据，跨域引用按版本与资格检查。

持续观察请求与一次执行分开：backend 保存“已启用的基础维护或临时关注，以及当前生效的参数”；Agent 保存“为了这次证据执行了什么”。`watch_id` 标识观察请求，`task_id` 标识一次执行，`thread_id` 标识该次 Agent 执行的 checkpoint。本地身份执行使用独立执行身份，不创建聊天或 Agent checkpoint；其准入不依赖 Agent 在线。观察请求可以产生多次执行，不共享一条无限增长的聊天记录。

### 任务定义与两条执行路径

用户自然语言需求由第一方 Agent 理解，转换为可审阅的长期任务定义，backend 校验并可靠保存后启用。自然语言保留为解释和语义任务输入，不直接充当可执行条件。创建或修改任务时可以使用 LLM 理解语言；配置生效后，运行时按下面的原则分配计算，不反复解释用户原话。

**运行时优先使用确定性规则：普通代码、本地能力和已有有效情景能确定的部分直接执行；只有仍需语义理解、跨来源推断或开放决策的部分才调用第一方 Agent 的 LLM。** 读取上下文、比较时间、匹配结构化事件、查位置选音箱、填充固定播报模板均不构成调用模型的理由。条件和动作两个维度都遵守这一原则；`semantic` 和 `agent_decision` 分别说明还有哪个判断或决策无法由已定义步骤解决，不是任意切换到模型执行的选项。

规则可确定性描述，与其输入怎样产生分开。例如“有人休息时不开主灯”由 backend 执行；“是否有人休息”可能由 Agent 提前异步推断并写入情景。条件和动作均确定、所需情景仍有效时，本次执行不依赖 LLM 在线；持续生产新情景仍可能需要 Agent。缺失或过期按已定义的未知分支处理，可另行异步补证，不让即时执行等待模型。

“尚未实现某个确定性模板”属于能力缺口，不等于需求具有模糊语义，不能因此自动转交 LLM。定期综合仍用于发现尚未由现有规则表达的关系和修正推断；到期检查、证据选择与预算准入由普通代码完成，规则已能算出的结论不再付费重算。开放语义指需要模型解释证据，例如综合行为判断“猫可能饿了”，不只是自然语言关键词匹配；结果保留不确定性并由 backend 按证据接纳。

| 对象                      | 唯一职责与身份                                                     |
| ------------------------- | ------------------------------------------------------------------ |
| 长期任务 `automation_id`  | backend 保存目标、版本、启停、期限、授权范围和执行配置，跨重启恢复 |
| 观察请求 `watch_id`       | 提供持续或临时证据；多个任务共用基础情景，不复制身份／位置维护     |
| 一次 Agent 执行 `task_id` | Agent 保存此次推理输入、调用和结果，不代替长期任务或动作记录       |
| 家庭事件 `event_id`       | backend 保存已接纳的发生经过和修正，与当前情景分开                 |
| 动作记录 `action_id`      | backend 保存动作意图、执行状态和结果，规则与 Agent 共用            |

长期任务最小定义包括稳定家庭身份、`automation_id/revision`、原始意图、目标对象、启停和可选期限、依赖的情景能力、触发方式、动作配置、未知／冲突处理、重复策略和授权依据。触发按 `rule / semantic` 判别：前者引用已实现的条件模板及参数；后者保存有界的判断目标、允许证据、候选触发配置和预算。混合需求通过语义事件接上确定性步骤，不默认两条路径同时重复提醒。模板与语义目标各自记录版本。

动作配置限定渠道、接收人、目标设备或房间选择规则、内容生成方式、动作期限、失败备用方式和重复限制。backend 校验实际能力、参数与授权，保存失败保留旧版本；更新检查预期版本，同一提交重试返回保存回执。停止任务撤销未执行动作和后续执行资格，但不停止其他消费者共用的基础维护；已发出的操作如实记录。重启恢复原家庭内的定义并重新检查能力和权限，改绑不将旧任务带入新家庭，不凭 checkpoint 恢复执行资格。

本地条件路径：来源事件／计时到期 → 读取已提交情景 → backend 条件计算 → 执行既定计划或派发 Agent 动作决策。语义条件路径：合格证据 → Agent 判断 → 提交事件及可选动作请求 → backend 接纳后选择相应执行方式。Agent 可以在同一次分析中通过工具请求已授权提醒，不强制先写长期情景再等待另一轮推理；只发出事件时，由已启用任务确定性消费。用户已授权的持续提醒在范围内无需每次重新询问。

语义长期任务由 backend 已实现的候选模板产生唤醒依据，Agent 输入适配器核对任务版本、证据期限和预算后进入同一执行入口；不为理解触发通知先调用一次模型。候选关联 `automation_id/revision` 和证据版本，不伪造 `watch_id`；取得媒体与提交结果继续复用证据保留契约。D 接入时为判断提交增加 `automation` 来源，携带任务版本及 backend 发出的候选身份，允许同次执行更新情景或提交事件。独立输出分别有接纳回执；存在同次判断与事件的一致性要求时使用下文的共同接纳操作，未接纳不能声称已更新；同一媒体用于多个输出不变成多份独立证据。语义执行受统一并发和总预算约束，另在模板中明确请求上限与期限，不能绕过额度另建模型客户端。

### backend 本地规则运行器

规则运行器是本项目 backend 内 `household/automations/` 的应用编排模块，随 backend 启动，从数据库加载已启用任务并核验依赖。它不是米家自动化，也不是另一个 Agent 或独立服务。米家适配器只承担实际设备读取、控制和已有场景调用；本地任务不会因保存成功而自动部署到米家云端。backend 停止后本项目不继续判断和调度，已发出的设备操作按设备自身行为继续；“本地执行”不保证设备通信或模型调用可以离线。

条件判断与动作决策分别配置，不能把整个任务只分成“确定性任务”和“LLM 任务”：

| 条件判断                                   | 确定性动作计划                                           | Agent 动作决策                                                          |
| ------------------------------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------- |
| `rule`：比较设备值、已接纳情景、事件或期限 | 本地求值后执行，可在执行时按已定义规则读取上下文选择设备 | 本地条件成立后唤醒第一方 Agent，提出已授权范围内的动作                  |
| `semantic`：Agent 解释证据并提出判断／事件 | 接纳后直接执行既定动作，不再调用模型决定怎么处理         | 同一次 Agent 执行可判断并提出动作，backend 校验后执行，不强制第二次推理 |

动作使用 `deterministic / agent_decision` 的判别配置，无动作的情景维护任务可省略动作。确定性计划既可指向固定设备，也可包含已实现的上下文选择函数，例如“查用户有效位置 → 找该区域获准音箱 → 播报固定模板 → 不可定位则走备用渠道”。这不需要 LLM。只有无法提前写明决策步骤的操作才使用 Agent 动作决策，并明确目标、证据范围、允许操作及预算；任务获准不代表 Agent 可生成任意代码执行。条件曾由 LLM 推断，也不改变后续规则求值和动作选择可以确定性执行的事实。

持久工作的领取、延时唤醒与故障后再次派发采用 [Graphile Worker](https://worker.graphile.org/docs/sql-add-job)，复用现有 PostgreSQL，不手写数据库轮询队列、租约或重试调度器。随 D 批次接入库的迁移和运行生命周期，核对项目固定 Bun 与数据库版本；当前服务尚未运行该 worker。领域表仍拥有任务、待评估依据、决策请求及动作结果，库中的 job 只携带这些记录的稳定引用。事件／动作登记所在的同一 Drizzle 事务调用 `graphile_worker.add_job`，不在提交之后靠一次内存回调补入队。到期工作使用 `run_at`，执行时重新核对领域期限和版本。

库领取完成与业务处理完成不是同一事务：处理器在领域事务中保存结果并标记业务项终态，再向库报告完成；若其间重启，重复派发读取已有终态后直接结束。可重试的数据库处理显式配置有界次数；外部动作或付费执行开始前先登记执行状态，结果不明时仅查询／核对，不再次投递或调用模型。[job key](https://worker.graphile.org/docs/job-key) 只用于调度合并，不作为永久业务幂等键，业务唯一约束继续保留。串行队列使用有限的固定名称或分片，不为每个事件生成队列名；库的内部表及迁移归库管理，不复制到领域 schema。

职责按领域划分，沿用现有 backend 装配方式，不扩充成通用工作流平台：

- `automations/` 拥有任务定义、条件运行状态、进入／退出判定、已定义的延时与抑制规则、持久期限、待评估记录、触发变化、可靠决策请求和语义任务派发。普通条件函数接收时间和已提交输入，不直接访问模型、HTTP 或数据库。
- `assessments/`、`events/` 提供有来源与版本的判断和事件；规则运行器只消费，不复制一份成员位置或自行延长判断有效期。
- `actions/` 接收规则或 Agent 的动作请求，拥有可靠登记、执行前资格复核、供应商调用编排及结果确认；具体协议仍由 `mijia/` 或实际通知渠道适配器负责。
- 第一方 Agent 负责自然语言需求装配、语义条件解释及开放动作决策，复用同一 harness。派发 Agent 任务不等于条件已满足，更不等于动作已执行。

状态变化、持续条件与离散事件按模板分别处理；同值更新不能伪造进入，独立按钮／告警事件不能按当前值合并。未知按任务的明确分支处理，不默认等于 false。提醒冷却、动作幂等和状态抗抖分别定义，不能用冷却掩盖重复事件或凭抖动反复执行。规则恢复、事件到规则交接及动作登记继续采用下文的可靠保存约定；到期资格核对与动作登记须同相关事件处理按任务串行化或核验运行版本，不能检查无纠正后再用已被纠正的期限登记动作。

自然语言创建时，Agent 先查询真实能力、已有任务和共用情景维护，再生成上述结构化定义，说明采用的条件、动作、未知分支和期限。backend 校验已实现模板、设备能力、参数、范围及权限；缺少能力时拒绝该配置或明确保存为未就绪意图，不生成可执行脚本。需要多项准备时先保存未启用定义，取得依赖回执后复核并原子发布任务有效版本；不能让半装配规则提前执行。失败不删除其他任务共用的基础维护，完成后返回实际接纳配置及运行状态。

### 三种分析入口与定期情景综合

第一方 Agent 的家庭分析有三种入口，复用同一执行、上下文、预算与提交设施：

| 入口           | 唤醒依据                       | 分析范围                                                               |
| -------------- | ------------------------------ | ---------------------------------------------------------------------- |
| 设备／家庭事件 | 有价值的来源变化或已接纳事件   | 关联相关设备、人物、区域与近期经过，不限于触发设备                     |
| 媒体候选       | 合格的视频／音频窗口或身份证据 | 解释画面／声音，可结合其他来源，不把描述直接当作物理真值               |
| 定期情景综合   | 已启用维护任务的复核时间到达   | 读取家庭概览及选定时间范围的事件、判断和缺失项，发现跨设备、跨时间关系 |

定期综合是独立的情景生产任务，不要求先存在一个需要提醒的业务任务，也不要求 backend 已识别出“猫饿了”才唤醒 Agent。复用长期任务的持久定义，以情景维护为用途，允许没有动作配置；提醒任务消费维护结果，不各自复制综合任务。`rule / semantic` 表示判断方式，事件、媒体和定时表示输入入口，不能把两组概念混成一个互斥类型。

backend 的长期任务模块保存维护目标、对象／区域、允许来源、事件查询范围、复核间隔、时间条件及任务版本，并拥有到期调度。Agent 拥有跨来源推理，不在 Agent 另建一份可独立修改的定时配置。到期产生带任务版本、周期身份、评估时间和最晚启动时间的 `context_review` 候选，沿用 `automation` 提交来源；它不需要 `watch_id`、摄像头或媒体窗口。定时器使用普通代码，不用模型决定是否已经到期。只有维护所需的实际来源和上下文查询就绪即可接入，不等待全部设备历史或人物识别交付。

定时唤醒不等于每次必须调用 LLM。准入检查相关证据／判断依赖是否变化、纠正或缺口是否出现，以及是否跨过任务定义的时间条件。距离上次进食的时长变化可以构成有效分析理由；输入版本不变不等于没有新问题。任务明确要求定期语义复核时，按配置间隔和预算执行；不能由模型任意缩短间隔，也不能把身份核验冷却到期直接当作这种复核任务。无新分析价值时保存跳过原因；预算或模型不可用时显示维护受限，保留原判断的有效期，不伪造完成。

每个维护任务最多一个在途执行和一个合并后的待复核项。重启或长时间离线后，只为当前仍有价值的范围生成一次恢复复核，不逐个补跑错过的周期；不同物理事件本身仍独立保存，不因综合任务合并而合并原事件。停用、版本替换及撤权取消旧候选；周期身份和准入／执行记录随任务保存，回执丢失先核对，已发出但结果不明的执行不自动重跑；后续新周期可按价值和预算重新评估，不承诺跨进程恰好调用一次。周期结束后不自动创建动作，动作仍须满足独立授权和触发条件。

开始分析时冻结有界输入：生成／评估时间、来源时间、各领域版本、查询时间范围、覆盖缺口、支持与冲突证据，以及待复核判断。上下文接口与事件查询返回 backend 可核对的证据身份；不能只让模型带回自己写的摘要。超过范围时明确裁减或分页，未查询／未保留不等于没有发生。查询游标只描述返回范围，不代表全屋历史完整，也不决定判断有效期。纯上下文综合不要求重新取帧；确需媒体补证才使用媒体入口及其独立期限。

### 多来源判断与事件：猫可能饿了

| 信息                                   | 接纳后的含义                                                 |
| -------------------------------------- | ------------------------------------------------------------ |
| 喂食器报告出粮完成                     | 设备来源观察／事件，证明设备报告了出粮，不证明猫已经吃下     |
| 本地规则发现距已确认进食超过设定时长   | 确定性派生，保留基线事件与规则版本；未记录进食不直接等于饥饿 |
| Agent 视频分析发现猫反复靠近食盆或叫唤 | 带原媒体区间与依据的行为解释，不自动定位为某只已登记猫       |
| Agent 关联食盆信息、近期行为和进食经过 | “猫可能饥饿”的候选判断，可由事件、媒体或定期综合入口产生     |
| 首次接纳饥饿迹象，或该次迹象明显变化   | 按已实现事件规则生成／更新家庭事件，供已启用提醒任务消费     |

判断与家庭事件使用共同的来源语义，区分设备上报、本地规则推导和 Agent 推断；Agent 的输入入口另行记录，允许一次推断同时引用设备和媒体。记录原始证据身份、推导依赖及版本、证据适用区间、评估时间和接纳时间；不为不同生产者建设可独立修改的“猫饿了”状态副本。设备上报也有来源质量，推断不会因为入库或转成事件而变为确定事实。

“猫可能饥饿”作为情景判断保存主体、维度、支持／冲突证据、不确定性和失效条件。用于自动化的事件采用已实现的类型化契约，例如 `hunger_signs_detected` 表示发现饥饿迹象，不宣称测得生理饥饿或精确起始时间；未支持的开放描述可保存为分析说明，但不能冒充已实现规则条件。无法区分多只猫时使用带来源运行的猫轨迹或区域级判断；没有可靠个体关联时保留匿名，不凭轨迹编号把进食量或饥饿判断归给某只已登记猫。

backend 判断接纳模块拥有该维度的当前版本，事件模块维护同一次迹象的稳定事件身份及更新。Agent 提交时引用已有判断／事件及其预期版本；首次成立、有实质新支持、矛盾、结束或纠正分别处理。纯复述、提示词变化或新执行 ID 不产生新事件、不提高置信度、不重置提醒周期；到期只变为未知，不伪造“猫不饿了”。再次成立是否属于新一轮迹象，须有该场景明确的结束和重新成立依据。

上次判断和 Agent 长期记忆只作背景或待复核假设，不能成为新的独立支持；保留原证据引用，防止“模型认为猫饿了 → 下次总结仍饿 → 多次确认”的循环。新的时间评估可以改变推断，但必须记录时间条件与观察覆盖，不刷新原始来源时间；静止、无新消息和反复读同一记录不能自行延长观察有效性。

同一结果需要同时更新情景并产生对应事件时，通过一个受控接纳操作在同一数据库事务保存判断版本、事件及必要待评估项，成功后发布当前视图；失败不单独发布已成立事件。多个入口对同一主体／维度的并发结果按证据与版本检查接纳或保留冲突，不按返回先后覆盖。事件后续规则处理和动作继续遵守下节的可靠交接，不把每次分析完成当作提醒触发。

### 规则到 Agent 动作决策的交接

`agent_decision` 分支在条件成立时尚无具体动作，须先登记决策请求。backend 在完成规则评估的同一事务内保存 `decision_request_id`、稳定家庭身份、任务版本、下文的触发变化身份、动作决策槽、不可变触发依据、允许的动作范围、预算约束及最晚启动／结果接纳期限；只有该请求保存成功才标记规则评估完成。同一任务版本、触发变化与决策槽只登记一个请求，不能在标记完成后仅用内存回调或 SSE 派发。登记请求不占用数据库事务等待模型，也不表示动作已决定。

backend 的 `automations/` 拥有请求及接纳状态，Agent 的共用执行入口拥有实际执行。派发与执行查询使用稳定请求 ID；Agent 先可靠记录请求 ID 与唯一 `task_id` 的关联再返回已接纳，同一 ID 的重送返回同一执行记录而不再调用模型，内容不同则冲突。等待派发、已接纳、决策结果已接纳、失败、结果不明、取消／过期分别表达。Agent 的模型完成记录不是 backend 已接纳决策的证明，更不是设备执行成功。

恢复时先按请求 ID 核对双方记录。请求尚未被 Agent 接纳且仍有资格时可重送；Agent 已接纳但尚未开始的执行按期限与预算启动。已开始而执行结果不明时不自动重跑模型，保留结果不明，按任务预设失败分支处理；已有持久决策结果则重新提交原结果，不重复推理。双方对该请求的去重与查询记录至少保留到其启动、结果提交和回执核对期限结束；缺少记录且无法证明尚未执行时，不能把查询未找到解释成允许重新付费执行。实际模型调用仍遵守共用预算，不承诺跨故障恰好调用一次。

Agent 提交带原请求 ID 和稳定结果 ID 的有界动作提案，也允许明确“不采取动作”。backend 重新核对任务版本、触发依据、权限、期限及动作范围，在同一事务内保存结果接纳回执、登记必要动作意图并完成决策请求；无动作也有完成回执。动作项身份来自已接纳提案中的稳定项，不因回执重试重新生成。结果被拒绝须返回终态或可修正原因，不能将派发成功当作完成。后续执行沿用 `actions/` 的资格复核与结果确认。

停用、任务版本替换、触发纠正或撤权使对应请求失效，取消传至 Agent；已经结束的计算不能据此向新任务提交动作。恢复与并发派发通过请求身份及条件更新协调，不能让同一触发同时走固定动作与 Agent 决策两条路径。语义判断与动作决策已在同一次 Agent 执行完成时，直接使用共同接纳入口，不为补这条交接强制再创建一次推理。待派发数量、字节、证据保留及失败处理在动作阶段设上限，容量不足拒绝相关触发登记并报告原因，不阻塞基础采集。

### 依赖启用与运行健康

长期任务的启停意图与实际可执行状态分开。启用或修改时，backend 不仅核对能力是否已实现，还要解析实际依赖：适用家庭与区域、需要的基础维护及版本、来源是否启用、维护运行状态，以及所需模型服务和自动预算是否可用。已有共用维护直接引用；没有启用时，只能在用户已授权的来源、用途和费用范围内经同一观察接纳入口启用，不为每个提醒复制位置维护。需要另行启用的依赖先取得可靠回执，再重新核验任务资格；不假设跨模块保存天然原子。依赖未就绪时，可保存用户意图，但不能返回正常运行成功。

每项依赖明确必需程度及允许的降级方式。已有授权的备用方式能满足该任务时，可以降级启用，并在回执说明实际行为；否则暂停受影响分支。缺少遛狗事件生产者，不能仅以“音箱位置未知时换渠道”掩盖；除非任务明确接受按已有记录提醒，否则不得宣称正在正常监测遛狗。未授权的来源或付费范围不自动扩大。

任务查询与接纳回执同时返回启停意图、当前运行状态、受影响分支、依赖身份／版本、原因及最近核对时间。运行状态按 `ready / degraded / suspended / recovering` 表达；关闭意图始终禁止执行，不被健康恢复重新打开。区分两类信息：当前位置暂时未知属于情景质量；位置维护被停用、来源不可用、Agent 离线或自动预算耗尽属于生产能力健康。已有有效判断仍可按自身期限使用，不能因模型不可用而一并抹掉；需要新语义的分支必须显示受限，不能以旧判断冒充正常监测。

基础维护停用、来源撤权、模板或范围变更、模型失联及预算变化时，重新计算依赖任务的健康与执行资格。backend 使用所属模块的状态；Agent 提供带有效期限的模型可用性和预算摘要，摘要过期标为未知，实际付费准入仍由 Agent 负责。具体动作及新语义任务启动前再核对，不能只相信创建时的回执。停止业务任务不撤销其他消费者使用的基础维护；用户明确停用基础维护后，不因仍有依赖任务而偷偷重启它。

重启后先标记恢复中，核对持久定义、来源、实际运行和依赖版本后再转为就绪或降级。恢复不直接重放历史提醒，只按任务期限和重复策略处理仍有价值的待办；当次提醒遇未知或过期位置仍立即走已配置分支，不等待 Agent 补证。上述健康为可重新计算的运行视图，任务意图和依赖配置由长期任务模块可靠保存。

### 情景、事件与统一执行

当前情景描述现在的判断及有效性，事件描述某个时段发生的事情。backend 保存事件身份、类型、主体／区域、发生区间、接纳时间、证据引用和摘要、不确定性、来源任务／版本及修正关系。同一证据的转述不是新的经历。遛狗完成等规则输入使用已实现的判别类型和字段；开放异常可用有界的 `suspected_hazard` 事件载荷保存描述及依据，不把任意文本直接编译为条件。纠正保留原事件并重算依赖，不悄悄覆盖历史。

两条路径共用 backend 执行入口。Agent 同时提交事件和处置请求时，事件、动作意图与接纳回执在同一数据库事务保存，提交后由执行器投递；通知丢失可从待执行记录恢复，不依靠 SSE 重放。规则路径也可靠保存触发依据与动作意图。此恢复保证从可靠登记开始；此前未接纳的原始观测或断线未收到的设备事件仍可能缺失，不能据此承诺端到端零漏报。保存失败不得报告任务已触发成功，按任务期限处理失败，不阻塞本地采集。同一任务版本、获准的触发变化身份和动作项只登记一次动作；后续窗口识别同一持续异常时关联已有事件，按任务重复策略处理。无法确认是同一事件时保留不确定性，不能用全局冷却吞掉不同事故。

事件、触发变化与提交使用不同身份：

| 身份                    | 含义与去重边界                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `event_id`              | 同一次发生经过或持续迹象；补充支持、升级或纠正通常更新该事件，不另造一次事故                                     |
| `trigger_occurrence_id` | backend 按任务版本和已实现触发策略接纳的一次可执行变化，例如首次成立、严重程度升级、明确允许的重复周期或条件进入 |
| 提交／结果 ID           | 同一次写入或决策结果的重试身份，不代表新的事件或触发                                                             |

事件版本变化不自动产生新的触发变化。普通补充说明、新执行 ID、提示词变化或同一证据复述不再次提醒；任务明确允许的严重程度升级，即使沿用同一 `event_id`，也可登记新的 `trigger_occurrence_id`。周期身份与事件／条件的有效轮次关联；冷却结束本身不产生新变化。重新成立必须满足场景的结束与重新成立依据。提醒频率、升级阈值及是否替代尚未执行的旧提醒由任务策略明确，不能以更新任意字段绕过重复限制。

规则评估在同一事务内核对已接纳版本，按任务、基线事件／条件及触发类别、适用版本或周期定位已有触发变化，存在则复用；新建触发变化与动作意图或决策请求一起提交。Agent 可提出升级或动作请求，但不能自行分配一个新触发变化来绕过去重。语义结果同时附动作、以及事件随后被规则消费时，使用同一 backend 触发变化和动作槽身份，不分别提醒。任务版本替换不自动重放旧事件，新版本采用历史基线仍须显式初始化。

已保存事件到确定性规则的交接也必须可恢复，包括 Agent 只提交事件而不附动作的路径。事件或修正接纳时，在同一数据库事务内为当时适用的已启用任务登记有界的待评估项，保存稳定家庭身份、事件／修正身份、任务 ID 与版本及处理期限；接纳回执表示事件和必要交接均已保存。任务启停／版本变更与适用任务选择必须通过事务内版本核对或同一串行化边界协调，不能在事务外读旧任务列表后漏掉交接。重复提交沿用原身份，不重复登记。

backend 普通规则处理器消费待评估项，不调用模型。按任务串行化或核对任务运行版本，从已接纳且未被纠正的适用事件中重新选取有效基线，不按待办完成顺序覆盖较新依据；确认当前资格后，在同一事务内保存规则处理结果、更新持久期限、登记或撤销动作意图，并将该项标记为已处理；没有触发动作也记录处理完成。事务失败保留待处理，提交结果不明先查询原处理身份。重启由 Graphile Worker 再次派发未完成工作；领域事务仍核对处理版本和唯一约束，避免重复派发产生重复动作。沿用同一任务版本、获准的触发变化身份与动作项的唯一身份；选择 Agent 决策时在该事务登记决策请求，按上文完成可靠交接，不依靠 SSE、内存回调或 Agent checkpoint 恢复。

例如遛狗事件已保存但尚未更新八小时期限就重启，待评估项仍在，恢复后从实际事件时间重算。到期执行前检查是否存在影响该期限的已接纳但未处理事件／修正；有则先完成本地重算，不按旧期限发出提醒。迟到纠正撤销尚未发出的过时动作，已发出结果保留。任务已停用、版本已替换或动作期限已过时，旧待办按明确规则取消或只更新历史，不自动套到新版本执行；新任务采用历史基线须显式初始化，不能遍历历史重放通知。

待评估依据由 backend 的任务领域保存，执行派发由 Graphile Worker 管理，不再建设第二套通用队列。条数、字节、保留和恢复批次上限在动作阶段配置；容量不足时拒绝新的相关事件接纳并报告原因，不能保存成功却丢弃必要交接，也不阻塞本地采集。未完成项及所依赖的必要事件摘要不能被普通历史清理提前删除；过期或取消后记录终态再按保留策略清理。此保证仅覆盖已可靠接纳事件，不能补造未收到的原始观察。

动作区分待执行、执行中、成功、失败、结果不明及取消／过期。执行前再查任务版本、授权、禁令、期限和所需情景。按当前位置选音箱时读取有效位置并记录依据，成功播报后不因人移动而换房间重播。位置未知或设备不可用走预设备用方式，可另行异步补证，但当次处置不等待识别。供应商超时不证明未执行；无幂等或结果查询能力时不盲目重发播报，不承诺恰好执行一次。

### 四类需求的具体契约

| 需求                                | 提前维护的信息                                     | 触发与执行                                                                            |
| ----------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 人来灯亮、人走灯灭                  | 区域占用、活动及有效要求                           | backend 按占用边沿、离开确认和延时模板执行；缺失不当作离开，重复检测不重复开灯        |
| 超过 8 小时没遛狗，在我所在房间播报 | 已接纳遛狗事件、持续维护的用户位置、音箱及作用区域 | backend 从最近一次有效遛狗完成时间计算期限，到期读已有位置选音箱，不调用 LLM 找人     |
| 卫生间门开着，猫狗进去就提醒        | 有效门状态、动物类别及区域／通行证据               | 证据已结构化时本地规则执行；需理解画面时 Agent 识别后提交事件及提醒请求，共用执行入口 |
| 有人出现疑似危险状态时提醒          | 可用来源、人物／区域上下文及近期证据               | Agent 按任务目标判断疑似异常并请求提醒；backend 保存事件、检查授权、去重及执行        |

遛狗完成的判据随真实来源实现，普通出门不等于遛狗；明确针对哪只狗、是否限定执行成员及可接纳的证据。没有历史或观察覆盖有缺口时只能说“未记录到”，不能断言没遛；任务明确允许按记录提醒或指定其他处理后才能启用。时间从实际事件算起，不从模型返回算起；迟到或纠正事件重算期限、撤销尚未发出的过时提醒，已发出记录保留。与设备连续条件计时不同，该期限保存事件依据和到期时间，重启后按配置补发一次仍有用的提醒或跳过，不重新计满 8 小时；检查时钟跳变，重复间隔、结束条件和首次缺记录处理是任务参数。

猫狗场景消费 P2 已实现的猫狗位置轨迹，并校验物种、来源运行、实测状态与有效期；预测框不单独证明动物进入，轨迹编号也不代表已登记宠物身份。卫生间只使用允许区域的门口视野或验证过的其他来源；看不清门状态或方向时不承诺识别进入。若接受“发现动物在区域中也提醒”，须显式配置，不能伪造进入事件。门开且进入要求两种证据在相关时间适用，不拼接过期位置与门状态。

危险任务的候选触发不能要求 backend 已知道危险才唤醒 Agent。启用时明确可实现的本地异常／变化筛选、代表证据，以及是否需要有预算的定期观察；仅变化筛选可能遗漏静止异常，覆盖方案未验证时不能宣称持续危险监测可用。定期语义观察按独立模板交付，不改变身份核验的新证据要求。可信本地报警也可走规则路径。分别记录证据发生、候选产生、识别完成及投递时间；识别后立即处置不等于从危险发生起保证实时发现。Agent 不可用时显示语义监测不可用，不把旧判断当作正常。

### 基础维护与临时观察

基础维护与临时观察复用同一套模板、候选与执行设施。基础维护由用户或部署配置明确启用，在原家庭与授权范围内持续到停用，不要求每天经聊天续期；临时观察表达额外目标，必须有截止时间。基础维护持续启用不表示持续调用模型，仍由证据变化、质量和预算决定调用。部署配置通过同一接纳入口保存，不能另建一份可独立修改的运行状态。

第一批只实现 `scene_context` 模板：在指定来源上，P4 场景筛选产生合格窗口时，请求一次与观察目标相关的场景理解。身份场景接入后增加 `member_presence`：持续维护所选成员的位置，并对符合条件的身份问题提出核验。每个模板是代码中已实现、带版本的领域规则，不接受脚本、任意布尔表达式或自然语言直接充当触发器。

自然语言目的只指导 Agent 分析，backend 不把“有人在做饭”等语义直接编译成已实现的本地条件。现有模板无法表达的需求，Agent 明确说明缺少能力；不能创建一条表面接纳却永不正确触发的观察。

Agent 工具 `list_observation_capabilities` 返回当前支持的模板、实际可用来源／区域、可选参数及其允许范围。`put_observation` 只提交这些能力允许的数据：

| 字段                            | 含义                                                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `watch_id`、`expected_revision` | 客户端首次生成 UUID；新建预期版本为 0，更新须匹配当前版本                                                |
| `scope_epoch`                   | 本次修改所针对的有效家庭运行；backend 独立核验账号与家庭                                                 |
| `template`、`parameters`        | `scene_context` 的来源、区域和判断有效期；`member_presence` 的来源、区域和已登记成员 ID；按模板判别校验  |
| `purpose`、`origin`             | 有界的任务目的及原始用户请求关联；用于模型任务输入和解释，不作为权限证明                                 |
| `mode`、`expires_at`、`enabled` | `baseline` 表示持续到停用的基础维护，不携带到期时间；`temporary` 必须携带 UTC 到期时间；两者都有启停意图 |
| `requested_limits`              | 请求的调用频率与单次证据规模，只能在部署允许范围内收紧                                                   |

`scene_context.parameters` 使用 `{ sources: [{ device_id, channel }], area_id, validity: { occupancy_max_age_ms, rest_max_age_ms } }`，区域须有用户确认的覆盖依据，两个有效期必须在部署允许范围内；`member_presence.parameters` 使用 `{ sources, area_ids, member_ids }`。来源保存稳定设备／通道引用，运行时由 backend 解析为当前 `source_id/source_run_id`，不把短命运行 ID 保存成跨重启配置。观察请求初始最多 16 个启用项、单项 16 KiB、总计 256 KiB；临时观察单次有效期最长 24 小时，续期须有对应用户意图；基础维护无固定到期时间，模型不得把临时任务自行升级为基础维护。模式按判别 schema 校验。

backend 返回 `{ watch_id, revision, mode, status, effective_limits }`，临时观察另返回 `expires_at`。同 ID、相同预期版本与相同内容的提交重试返回已保存回执；同 ID/版本而内容不同则冲突。可靠保存后才生效，失败保留旧请求；撤销也可靠保存后返回。运行中权限撤销立即禁止访问，不等待保存。

首期只支持可信本机单用户。Agent 提议须在用户已经授权的来源与任务范围内；超出范围向用户说明并取得授权，不能靠 `origin` 文本扩大权限。持续开启的基础观察也必须由用户或部署配置明确启用，不因登录或启用 P1 自动产生付费任务。

观察请求可在线更新，但不修改设备采集计划的采集策略、本地模型阈值、米家账号或摄像头启用范围。它与下文设备事件启动时读取的本机场景配置是不同对象；复用模板中的纯条件函数，不为此改造为通用规则编辑器。

请求保存稳定家庭身份及模板版本。backend 重启后重新校验来源、模板版本、期限和当前权限，基础维护仍启用或临时观察未到期，且其余条件满足时才在新 epoch 激活；运行基线和持续计时重新建立，不回放旧触发。模板版本改变时暂停并要求重新接纳；到期、改绑或来源不适用时停用，不恢复到其他家庭。用户长期任务的恢复不等于一次 Agent 执行自动恢复。

### 一次实际执行的时序

1. 批次 B 中，用户或部署配置启用客厅 `scene_context` 基础维护；也可由聊天创建一小时临时观察。接纳后返回有效范围及生命周期。首个闭环不依赖动态观察编辑工具先完成，基础维护可由部署配置经同一服务启用。
2. P4 窗口通过筛选，backend 发布包含 watch 版本的候选。Agent 准入层在读取媒体前检查预算与期限，选择对应任务处理器；用户聊天已经结束，不影响后台观察。
3. 场景任务取得该窗口媒体与允许读取的家庭上下文，调用模型并提交结果。backend 接纳后按下节规则维护当前判断，另一次聊天或确定性策略读取其值、原证据时间和有效性，不将窗口说明冒充持续实时画面。
4. 批次 C 按需增加 `member_presence`，不替换仍需运行的基础场景维护。客厅画面中的目标被确认属于成员 A，接纳为出现记录；厨房后来取得合格新画面时，可独立核验其中目标，不要求先关联客厅轨迹。
5. 厨房身份结果返回后，backend 核对原证据、时间依据、覆盖与身份版本，接纳后按观察先后汇总 A 的最后出现房间。迟到结果不覆盖更新观察，同一时间的重叠视野不虚构通行；最新观察区域未知时保留较早的最后已定位记录及原时间。
6. 用户停止观察，工具返回保存回执，新候选停止并取消对应任务。已接纳出现记录保留原时间，不能因停止观察反写成“无人”，也不再声称正在更新位置。

### 首个情景的维护与即时消费

批次 B 选择允许部署摄像头且实际覆盖明确的客厅区域，维护“区域占用”和“可能有人休息”两个独立判断；不依赖成员姓名或 P2。模型可以依据代表画面及可用设备上下文提出休息迹象，但只能表示推断，不确认睡眠。没有相应证据时保持未知。

| 情况                                   | backend 的维护规则                                                             |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| 新的实测人体检测覆盖目标区域           | 按实际覆盖更新占用支持；不能因此确认某个人或延续休息判断                       |
| 新的实测猫狗检测或轨迹覆盖目标区域     | 更新对应物种的占用证据；不能当作“有人”或确认某只宠物，预测框不能单独刷新占用   |
| 取得足以支持未占用的有效证据           | 按已验证覆盖、遮挡与场景规则建立未占用基线；一次空检测、旧值或缺帧不构成该证据 |
| Agent 提交有效的休息迹象判断           | 记录目标区域、原证据时间、支持与冲突证据、依赖和有效期；后续查询不续期         |
| 同值上报、无画面变化、同一目标持续存在 | 不构成新的休息证据，不自动延长活动判断有效期                                   |
| 新人或新的存在信号出现                 | 更新对应占用证据，不单独清除原休息判断，也不证明所有人已醒                     |
| 来源中断、遮挡或覆盖失效               | 依赖该来源的当前判断降级为未知或待重评；不把缺失当作无人或休息结束             |
| 取得适用的新语义证据，明确不再支持休息 | 按该维度的版本与证据规则更新；存在矛盾则保留冲突，不按响应先后覆盖             |
| 判断到期而无新的支持证据               | 移出当前可用判断，保留最后已知；不自动变成“无人休息”，也不强制调用模型刷新     |

首个场景配置须分别声明占用证据最大年龄和休息判断最大年龄，并在真实机位验证后启用；未设置时不提供可用于策略的当前判断。有效期从支持证据的时间计算，不能从模型返回时间起算。来源变化只更新实际支持的维度，人物身份、位置和活动不互相自动续期。

批次 B 同时实现一个只记录结果的具体策略：区域占用从有效未占用变为有效占用时触发；重复检测只更新证据，启动／断流恢复首次取得占用只建立基线，未知不冒充未占用。策略以本机配置中的稳定 ID、模板版本、区域、启停和参数启用，由 backend 策略模块拥有；后续长期任务接入同一规则函数，不并存两份启用状态。触发时，若休息判断仍有支持、为暂定、未知、冲突或过期，记录“抑制自动开主灯”；只有有效证据支持无休息者且没有禁止要求时，记录“允许进入后续开灯资格检查”。这不直接生成开灯授权。策略记录本次已提交情景、要求和策略版本、触发证据及理由，不等待模型、不发送命令；此默认处理仅用于首个场景。

真实命令在后续动作阶段启用：backend 重新检查当前条件与权限，按已启用策略执行并确认结果。Agent 不可用不阻塞上述确定性处理；异步重评只影响后续上下文，迟到结果不自动重放已经处理的动作。验收分别记录事件接纳到策略决定的延迟及异步语义更新延迟，不把模型完成时间当及时响应时间。

## 4. 身份与位置的本地处理

首期批次 C 交付“最后出现房间”，字段和不变量唯一维护在[人宠出现记录](household-model.md#人宠出现记录与最后出现房间)。人类成员和已登记猫狗统一使用稳定 `member_id`；`member_presence` 首期维护出现记录，不承诺当前在场。各来源独立核验成员，再按身份汇总，不要求跨摄像头保持同一轨迹编号。

首期流程为：合格画面与来源时间 → 对照人宠参考核验身份及覆盖区域 → backend 接纳出现记录 → 普通代码汇总 `latest_sighting` 与 `last_located_sighting`。来源时间不可靠、身份或区域未知时保留限制；模型返回时间不参与出现先后排序。局部轨迹键 `{scope_epoch, source_id, source_run_id, track_id}` 只是可选的证据关联，附 `className`（`human / cat / dog`），没有轨迹时以窗口、帧及其中的目标引用定位核验对象，同一画面多目标不能共用一个身份结果。

身份核验不能仅凭物种、跟踪外观相似度或未经校准的身份匹配分数命名。人体 ReID 只提供人体外观相似性，猫狗当前没有宠物 ReID。低质量、相似个体无法区分或无参考资料时保持未知；未知观察不更新某个指定成员。轨迹可辅助选清晰画面与候选去重，跟踪失败不阻断有合格证据的独立识别。

本地模型与 LLM 是可分别启用、可并行运行的身份候选生产者，不互相等待，也不默认对每张图片同时调用。人物本地路径可先验证 YuNet＋SFace，猫狗另行验证适用模型；这些均为待实施能力，模型资产、预处理、阈值、未知处理及实景效果通过核对后才接入，不作为 P2/P4 前置条件。参考库较小时先在有界内存集合比较，不预建向量数据库。

本地路径消费与原帧关联的有界图片，不等待 4 秒窗口关闭、场景变化放行或视频编码；LLM 路径根据已启用配置和自身预算消费适用证据。本地优先后按条件启用 LLM、仅启用其中一种或并行对照均须明确配置，不能把本地返回未知自动转换成一次付费调用。两条路径均记录生产者、执行身份、证据与目标、模型／处理版本、参考资料版本、匹配依据及未知状态。本地计算有独立容量与期限，失败不停止采集或另一生产者。

两种生产者调用同一家庭领域身份接纳操作；本地路径在进程内调用，不绕经 Agent 或为其伪造 HTTP 任务。HTTP 仅适配外部提交。相同底层证据的多模型结果不算多次独立确认，不能刷新观察时间；各模型分数按自身经验证的规则解释，不直接比较大小。冲突保留原依据并按身份接纳／纠正规则处理，没有验证过的裁决规则时保持未知或争议，不按谁最后返回覆盖，也不默认调用 LLM 仲裁。其他功能只读取已接纳身份及其限制。

最后出现位置是历史证据汇总，不设到期后自动删除历史事实的“在场有效期”。新观察区域未知时，同时保留较早的最后已定位记录及原时间；冲突、撤销和身份纠正触发重算。受控接纳入口复核证据、家庭资格、资料和覆盖版本，保存记录、受影响汇总及接纳回执后再发布。重复提交或重复证据不刷新时间；保留期限内的迟到结果可解释原区间，不要求目标现在仍有活动轨迹。

后续 E 再按需要交付可靠轨迹上的身份延续、跨镜头对象关联与通行事件；只沿验证过的连续性复用身份，交叉、遮挡、类别抖动或重建后重评。跨源匹配须检查物种、时间质量、覆盖关系和候选歧义，不能直接套用人体相似度到宠物，也不凭排名第一接纳。不同镜头的像素轨迹不能直接拼接。Frigate 可作为后续来源适配，沿用同一证据与出现记录契约，不成为首期依赖。

## 5. 候选触发与执行准入

本节定义首期场景维护和身份核验；后续语义任务的候选方式按第三节逐场景实现。场景筛选和身份核验使用不同模板条件，但都由 backend 普通代码检查。场景理解沿用 P4 的画面／声音筛选。身份核验要求启用 `member_presence`，且有待解决的身份问题和足够质量的视觉证据；画面静止不阻止清晰人脸或宠物的可区分外观成为核验依据。

| 条件                                                 | 处理                                             |
| ---------------------------------------------------- | ------------------------------------------------ |
| 已接纳身份且没有实质新证据                           | 不重复核验；后续经验证的连续性规则才可沿轨迹更新 |
| 后续跨镜头匹配满足已验证接纳规则                     | 本地关联，不调用 LLM                             |
| 未知目标短暂出现、模糊、没有有效参考资料             | 等待或保持未知，不因未知反复调用                 |
| 未知目标持续出现，取得合格代表帧，有待解决的身份问题 | 创建身份核验候选                                 |
| 已有身份与新观测冲突、疑似目标串号                   | 先降级关联；取得适用证据后创建候选               |
| 上次回答未知，未出现新证据                           | 抑制重复；冷却结束本身不重新调用                 |
| 更清晰视角、有效新参考、新的实质冲突                 | 更新证据版本，重新检查准入                       |
| 最近观察变旧、模型失败或预算不足                     | 保留历史时间并报告限制；不强制付费刷新           |

模板按物种使用已实现的帧尺寸、清晰度、实测目标可见性和持续观察指标判断证据是否改善。人体可使用适用的人脸和人体外观特征；猫狗使用全身、面部、毛色花纹及必要视角的可见证据，不要求人脸框，也不假定已有宠物外观向量。质量阈值按实际来源配置和验证，未配置合格标准的来源不自动核验。首次实施记录每次放行／抑制原因，不让“新帧 ID”直接等于“新证据”。

backend 保存有界的当前候选：`candidate_id, watch_id, watch_revision, scope_epoch, purpose, subject_key, evidence_revision, reason, evidence_refs, available_until`。场景候选按观察请求及来源合并；身份候选按观察请求、目标和核验目的合并，不能按摄像头只留一个，否则同镜头多人会互相覆盖。跨镜头只有关联依据充分时才合并为同一问题；不能为省调用先假定是同一个人。

观察候选最多 64 项／2 MiB（初始工程上限，媒体另计）；满额清理过期项，同问题更新替换，仍满则拒绝新项并计数。证据资源先就绪，再同步登记候选版本并发布通知；只增大版本、不在事件中携带媒体字节。

事件只通知候选变化，不直接命令调用模型。Agent 首次连接或重连先取得当前候选快照再接续变化；注册与快照边界内的更新有界暂存。序列缺口重新取快照，不补发全部旧窗口。SSE 复用现有解析、大小及慢连接清理机制，候选流有自己的版本，不塞入设备公共快照。

本地执行器与 Agent 普通代码分别检查观察仍有效、证据可取、是否已处理、在途任务和预算，然后创建一次执行。每个生产者对同一问题最多一个在途执行和一个等待更新；去重同时关联证据指纹，单纯 track ID 重建不作为再次调用的充分理由；等待期间选取更有价值的证据，开始执行时冻结证据版本。跨多个观察请求引用相同目标、目的及证据时，可共用模型结果；每个请求的使用资格分别核对，取消一个请求不撤销其他合法使用。首期不跨不同问题盲目合并。

本地执行器通过应用边界消费同一版本化身份候选，Agent 通过上述订阅消费；互相不以执行完成或结果接纳为启动前提。未启用的生产者不领取候选，失败或超预算不自动转交另一生产者。

## 6. 具体接口与工具

任务与动作阶段增加 `GET /api/household/automation-capabilities`、`PUT /api/household/automations/:id`、`GET /api/household/automations`，对应能力查询、创建／修改／停用和有界查询工具。`PUT /api/household/event-submissions/:id` 使用稳定提交 ID 接纳事件及可选动作请求；存在同次情景更新时，增加受控的关联判断及预期版本字段，作为共同接纳提交，`GET /api/household/event-submissions/:id` 核对接纳回执，`GET /api/household/actions/:id` 查询执行结果。提交引用有效长期任务版本、调用资格和 backend 可核对证据，自报任务身份不构成授权。这些接口在对应批次定义共享判别 schema、容量和保留期限后注册；下表首期判断接口不假装支持事件或动作。选定事件的有界查询支持最近遛狗时间及 Agent 读取，不依赖保存所有设备原始观测。

以下是拟实施的本机 API，按交付批次注册；全部复用现有本机访问校验和错误结构，修改操作校验 epoch，所有证据读取与结果接纳重新核对资格。

| backend 接口                                  | Agent 工具／调用方              | 最小返回与行为                                                                                                      |
| --------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `POST /api/household-members/:id/references`  | 批次 C 的参考资料入口           | 基于[现有成员资料](../../apps/backend/README.md#家庭上下文表)补充有界参考图和资料版本，Agent 不能凭猜测登记真实身份 |
| `PUT /api/household/coverage/:id`             | 批次 B 的最小覆盖登记入口       | 保存用户确认的设备／通道与区域覆盖，不从安装房间自动生成                                                            |
| `GET /api/household/observation-capabilities` | `list_observation_capabilities` | 已实现模板、来源、参数范围与不可用原因                                                                              |
| `PUT /api/household/observation-requests/:id` | `put_observation`               | 新建、修改或 `enabled=false` 撤销；返回可靠保存后的有效版本与额度                                                   |
| `GET /api/household/observation-requests`     | `list_observations`             | 当前绑定家庭的请求及暂停／到期原因，有界分页                                                                        |
| `GET /api/household/candidates/events`        | Agent 输入适配器                | 当前候选快照、变化、心跳；不是 LLM 工具                                                                             |
| `GET /api/household/context`                  | `get_household_context`         | 按来源／成员／区域选取状态、证据引用、缺失项和各领域版本                                                            |
| `POST /api/household/evidence/read`           | `read_evidence`                 | 给定已发出的引用，单次读取一个已确认表示的有限媒体流；对应不可变描述通过候选／上下文返回，不接受任意 URL            |
| `PUT /api/household/assessments/:id`          | `submit_assessment`             | 接纳或拒绝及原因；以稳定结果 ID 去重，返回正式判断与版本                                                            |
| `GET /api/household/assessments/:id`          | 执行器确认回执                  | 同一运行内查询接纳结果，响应丢失不重跑模型                                                                          |

接口字段以共用 Zod schema 定义，HTTP 路由只作转换。媒体通过工具内部的有界资源句柄交给模型适配器，不进入普通聊天 JSON、工具文本或日志。证据准备／保留期限遵循[媒体与判断期限](media-perception.md#p5p6-证据登记与提交期限)；流未读完整视为未取得证据，不能发起模型请求。

Agent HTTP 结果提交的公共字段为 `task_id, scope_epoch, evidence_refs, expected_subject_revision, result`，提交 ID 由接口路径提供。`origin` 按来源判别：`observation` 携带 `watch_id, watch_revision, candidate_id, evidence_revision`；`device_event` 携带已接纳的事件身份及规则版本；`interactive` 携带聊天任务与该任务实际取得的证据身份。仅相应来源携带对应字段，不为聊天或设备事件伪造观察请求。来源关联由 backend 已发出的事件、证据记录及调用资格核验，Agent 自报任务身份不构成授权。`result` 按 `scene_assessment / identity_association` 判别；身份只能引用本次允许的成员及证据中同物种目标（轨迹引用可选），也可返回 unknown；批次 C 接纳后登记出现记录并汇总最后出现位置。backend 校验目标版本、来源、证据与对应任务资格后，在一次领域提交中记录接纳回执并更新判断。观察来源的提交还校验观察有效性，失效观察拒绝其迟到新提交；其他来源按自身资格和期限校验。已经接纳的身份与位置按自身证据策略继续有效，不因停止观察自动抹掉事实。

本地身份候选复用同一身份接纳 schema 与领域操作。生产者按本地模型／Agent 判别，本地分支携带实际本地执行身份、已登记证据、候选版本与参考资料版本，不伪造 Agent `task_id` 或聊天来源。共同身份结果允许匹配成员或 unknown，并保留模型／处理版本与匹配依据；字段在批次 C 定义一次，HTTP 与本地适配复用。证据提交期的容量和资格校验随首次身份路径接入，不等待批次 B 或 Agent 消费；本地来源也不能越过家庭、证据、目标和版本检查。

首期非持久接纳回执只保证当前 epoch 内去重，backend 重启会使旧提交失效。需要跨重启保存的确认记录与回执采用同一数据库事务，成功后再发布；保存结果不确定先核对，不盲目重复累计确认。失败只影响该次语义接纳，不停本地检测。

## 7. 第一方 harness 的执行路径与费用

在 Agent 内从现有聊天路由抽出共用执行入口，保留现有对话行为、会话并发锁、取消与 checkpoint 完成语义。现有 `graph/home-agent.ts` 仍是模型图入口，`http/chat.ts` 保留传输职责；后台执行按任务隔离 checkpoint，不把后台更新写入用户聊天。新增工具与任务处理接入同一运行设施，不将现有文本图当作已经具备工具循环。按实际来源增加场景、LLM 身份核验、设备事件与定期情景综合任务处理器，均由同一模型适配、预算、工具与追踪设施执行，不建 backend 的 Omni 客户端或另一个外部执行 Agent。

聊天入口可以理解目标、调用观察工具、查询已接纳状态；后台入口直接带类型化任务进入对应处理器，不先花一次模型调用解释事件。启用的 LLM 身份核验默认一次结构化多模态调用；场景任务按明确需要允许有限补证。每次自动执行先准备不可变的输入证据及其最晚提交时间；60 秒运行期限不延长观察或证据的截止时间。相同媒体、期限与上下文可兼容时可以合并场景和身份请求，否则各自准入，不强制每次核验都做场景分析。

LLM 身份核验只携带定位清楚的代表帧、必要全景及候选参考资料，屏蔽该目标此前的身份猜测和习惯先验；位置与场景推理才按任务加入已接纳判断和其他设备证据。统一 harness 不意味着共享全部提示词或会话。模型返回理由及置信分数仅是候选说明，不作为准确率或自动入样本库的证明。

参考成员多于输入上限时必须说明候选不完整，不能强选最近似成员；模型可返回“不在候选内”。没有足够候选筛选依据时跳过自动核验或通过明确用户任务缩小范围，不把成员上限伪装成完整家庭资料。

harness 所有实际模型请求共用预算入口，包括聊天、补证、重试和恢复探测；自动任务另受自动调用额度限制，用户交互不因自动额度耗尽而绕过总额度。SDK 内部重试关闭或逐次纳管，不能一项任务暗中多次请求。小时／日预算的已用量由 Agent 持久化，发送前预留次数，超时结果不明仍计入；重启不清零，存储不可用时不发新的付费请求。token 预估与供应商用量分开记录，无用量报告时不宣称精确费用。

### 模型故障与恢复

模型返回未知属于合法判断，等待实质新证据，不按传输故障重试。传输失败、限流与配置错误分别记录；恢复由 Agent 模型适配模块统一负责，限流遵守供应商等待要求，配置错误等待修正或显式探测。按部署配置的有界退避和失败预算暂停调用，恢复探测最多一个在途且计入全局预算。恢复只处理新的有效任务，不自动重跑失败任务；取消传到底层，实际调用结束前仍占并发名额。模型故障不停止 backend 情景有效性维护或已启用的即时策略。

### 设备事件输入

设备事件是共用执行入口的一种输入，依赖[设备采集](device-collection.md)的真实来源及质量规则，不依赖摄像头或在线观察请求。设备场景可以先于媒体场景交付，但任务执行、预算、工具与判断接纳使用本文同一契约。

设备场景模板放在本机 `data/household-config.json` 的 `rules: [{ id, enabled, template, parameters }]` 中，启动时读取；修改后重启相关运行。模板只选择已实现的普通领域函数，参数明确设备能力、单位、阈值、持续时间和启动期限，不接受任意脚本或条件语言。规则版本包含配置内容及模板实现版本，实际生效参数随证据保存。规则模块维护本轮启用项的 `rule_status { rule_id, rule_version, status, reason }`，其中 status 为 active／suspended；按具体界面需要投影，不保存第二份规则配置或提前发布空字段。该配置不等于即时动作策略，也不修改基础维护与临时观察的在线生命周期。

| 触发                | 证据要求                                                     |
| ------------------- | ------------------------------------------------------------ |
| `device_event`      | 已验证的独立按钮、门铃等事件；同值不代表重复事件             |
| `property_edge`     | 可信连续基线之后的实时变化；首次值、恢复值和缓存不补造边沿   |
| `condition_entered` | 条件由假或未知变真；恢复时已经成立须注明，不能伪造刚发生变化 |
| `condition_elapsed` | 有效证据支持持续成立；缺口或未知取消计时，重启重新建立基线   |

只实现实际场景使用的触发。普通条件函数读取同次设备提交的前后值，在提交内生成规则状态和不可变证据，提交后才通知消费者；持续计时用单调时钟，到期检查等待先到观测的处理边界。某条规则失败只暂停该规则。即时策略另由 backend 使用已维护情景处理，不等待事件分析结果。

`GET /api/mijia/semantic-events?scope_epoch=…` 为拟实施的独立事件 SSE。事件包含 `semantic_event_id, event_sequence, account_id, home_id, scope_epoch, rule_id, rule_version, trigger_kind, state_version, generated_at, start_before, trigger_evidence`。证据保留实际模板版本、必要参数（含默认值）、设备与能力、原观测 ID、来源时间、质量、前后态或持续依据；字段与证据合计最多 64 KiB，超过则拒绝而不截断必要事实。证据提交资格与有界保留沿用判断接纳契约，不能只剩 Agent 自报数据。

连接先注册并发送 `event_ready`，边界内的新事件有界暂存，再顺序发送。它不重放断线事件；缺口记为已知缺号或未知漏收范围。相同 epoch 下合法且证据完整的递增事件即使跳号也可接纳，重复忽略；身份冲突或非法消息关闭重连。事件流与候选快照流的恢复语义不同：前者保留独立事件身份，后者恢复当前仍有价值的问题。传输心跳、解析与慢连接清理复用[现有状态传输](../household-runtime.md#公共接口与-sse)，事件连接初始最多 2 条、每连接待发 256 条或 2 MiB。

启动期限按场景设置，初值 60 秒；等待队列最多 100 条或 8 MiB，过期清理后仍满则拒收并计数，不合并不同物理事件。实际执行受本文共用并发、任务期限与预算约束，不另设设备任务满额池。媒体补证仍检查媒体自己的期限，不借此延长缓存。

明确停止、改绑或访问撤销取消受影响任务。临时采集断流只使当前条件与连续性失效，已经交付且证据充分的历史事件分析仍可在期限内完成；不能因此把其结果作为当前事实。来源为 `device_event` 的判断提交引用原事件，不要求 `watch_id`。

当前值工具返回值、来源、观测质量、当前质量、时间及缺失项；状态副本未同步时拒绝作为当前事实使用，显式读取最后已知值须标记过时。一次性读取使用[设备事实契约](../contracts/device-facts.md#接口与页面)的受控读取入口；历史工具只在[设备历史](device-history.md)交付且任务需要时注册。查询范围、返回大小和文本输入均受共用预算限制。

场景必须明确最终用途：更新情景时，完成条件是 backend 接纳、维护并可查询；回答用户时核对实际输出渠道。checkpoint 只证明执行记录已保存，不单独作为家庭功能交付。通知和设备命令仍须单独完成投递或执行边界。

实现时 backend 的设备规则模块拥有条件与事件证据，Agent 输入适配器负责转换并交给共用执行入口；共享 schema 放在 `packages/api`。验收覆盖真实触发、首次值不伪造事件、持续计时遇缺口取消、独立事件不被合并、跳号与重连、异步失败不影响即时策略，以及最终判断或用户输出确实可用。

## 8. 数据保存与长期记忆

| 数据                           | 所有者与存储                                                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 长期任务、家庭事件及动作记录   | backend 数据库保存定义与依赖、事件及修正、待评估项与处理终态、触发变化、决策请求及回执、期限依据、动作意图和结果，不以 Agent checkpoint 代替 |
| 当前情景判断                   | backend 维护有效视图，保存所需证据摘要与版本；重启核验来源和依赖后才作为当前判断                                                             |
| `household_observations`       | backend 数据库：观察模式、用户／部署来源关联、版本、临时期限及启停意图；不保存每次执行状态                                                   |
| 成员档案、参考样本及元数据     | backend 数据库保存身份、版本和来源；受控本地文件保存图片，按样本资格与容量清理                                                               |
| 活动轨迹、外观特征、核验候选   | backend 有界内存；按来源和证据期限清理，非永久成员身份库                                                                                     |
| 当前关联、位置及关键确认／纠正 | backend 维护当前视图；需要恢复解释的记录保存到数据库，重启只恢复“最后已知”                                                                   |
| 已提交任务与结果               | Agent checkpoint 保存本次输入快照、任务来源、task/result 及适用的 watch 关联；不直接覆盖家庭状态                                             |
| 请求预算账本                   | Agent 独立业务表保存窗口及预留次数，不伪装成 LangGraph checkpoint 表                                                                         |
| 习惯、偏好与经验推断           | Agent 长期记忆，后续单独实施；引用 backend 经历并保留反例与修正，不作为实时身份依据                                                          |

首期人类成员及猫狗资料由用户明确登记；不自动把陌生人命名或将一次模型判断保存为永久训练样本。动态身份关联的可用时间与参考样本保存时间分开，参考资料可以长期保存，但不能因此证明成员现在仍在家。

用户撤销观察停止该观察的新任务，并重评依赖长期任务的健康与执行资格；删除成员参考资料使依赖该版本的核验和关联重新检查。保存必要记录不要求设备历史计划保存全部设备观测，也不建设逐帧轨迹历史。原始媒体短期释放后仍须能解释已接纳结果的来源和范围。

## 9. 实施顺序与改动位置

按下表实施，各批按实际依赖接入。B 只依赖 A 中纯视频 P4 的证据能力；C 依赖可读画面、成员参考与身份接纳；本地路径可在 B 之前或与 B 并行交付，按需接入最小覆盖、`member_presence` 配置、候选与证据接纳，不要求场景判断或 Agent 工具先完成；LLM 路径另依赖 Agent 执行设施；P2 人体及猫狗跟踪是可选辅助，不依赖跨镜头关联。下一步先完成 P4 的无 Agent 证据出口，跟踪的实景验收按媒体计划继续。编号仅属于本文的交付批次，不改变已有本地能力的完成状态。

| 批次                   | 实施内容与主要文件                                                                                                                                                                                                                                                  | 验收出口                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| A 本地证据             | 按纯视频 P4 实现窗口、筛选、代表帧和媒体读取；复用已实现的 P2 人体及猫狗轨迹，供 C 使用                                                                                                                                                                             | Agent 未运行时，可查筛选原因和有界媒体；另查人体及猫狗局部轨迹；仅 A 不提供正式身份                                                           |

| D 长期任务、综合与执行 | backend `household/{automations,events,actions}/`、共享契约及 Agent 工具；实现本地规则运行器与动作计划，接入无动作定期维护；交付一个规则任务及一个语义事件提醒，共用持久动作通路                                                                                    | Agent 停止时规则继续；语义识别后可直接请求处置；重复提交不重复登记动作，未知位置和失败按配置处理                                              |
| E 按实测改善           | 按需验证连续身份延续、跨镜头关联及通行事件；可接入 Frigate 来源适配；识别模型效果、样本选择与参数调整按 P7 测量                                                                                                                                                     | 同一素材比较误认、未知覆盖、切换、延迟、模型请求与资源消耗                                                                                    |

判断接纳与上下文查询放在各所属领域；B 按需接入最小区域覆盖登记、判断有效期配置及 `scene_assessment` 所需的最小接纳模块，C 接入最小身份关联、覆盖与证据接纳，两批不互为前置条件，不预建全部家庭实体。首个情景的有效性和只记录结果的策略属于 backend 判断与策略领域模块，HTTP 只转换输入，不把规则塞入 Agent 或供应商适配器。目录是职责位置，实施时小型纯函数可留在所属文件，不为目录表创建空壳。

D 的定期情景综合可先依赖实际设备观察与最小事件查询交付，不必等待 P2/P4、全量设备历史或动作适配；没有媒体输入时不宣称理解画面。猫饥饿场景须先验证所用进食及行为来源，不能仅凭通用总结宣称有效。

D 中遛狗播报依赖真实遛狗证据和播报适配；按位置选音箱还须另行验证当前位置与时效规则，C 的最后出现记录不能单独满足该条件；猫狗与危险场景分别验证来源和候选覆盖，不以通用场景描述验收代替。D 可先交付不依赖身份的通知，不必等待跨镜头优化。真实动作按设备／渠道验收后启用；危险监测另核对漏检、误报和端到端延迟，不能沿用普通场景筛选直接宣称支持。

P3 音频及设备事件按场景需要接入共用入口。无摄像头卧室依赖真实设备集采和相应判断规则，不假设已有视觉覆盖；不必等待摄像头或身份能力。

## 10. 分阶段验收

使用真实授权来源和现有聊天 API、HTTP 查询及执行记录验收；本设计不授权新增测试代码或实机设备动作。首期 B/C 按下列观察与判断条件验收；真实动作在 D 完成适配和相应授权后单独验收。

- [ ] 基础维护经一次启用可跨日持续并在重启后重新核验恢复；临时观察按期结束，不能自动转为基础维护。
- [ ] 占用与休息分别维护；同值、无变化与持续可见不延长活动判断，过期不变成无人休息。
- [ ] 真实占用事件读取已有情景产生策略处理记录；暂停 Agent 或让模型任务尚未结束时仍可处理，不发送设备命令；未知、冲突与过期分支可核对。
- [ ] 观察、设备事件与聊天来源可分别提交适用判断，不伪造 watch 或候选；证据缺失与任务资格失效时拒绝。
- [ ] 聊天创建、修改、停止观察后，backend 的保存回执、有效参数和实际行为一致；未支持模板及来源不能假装成功。
- [ ] 没有任何已启用自动任务来源（观察、设备事件或语义任务），或者未启用自动预算时，P1/P2/P4 继续，自动模型请求为零；Agent 不在线不影响本地链路。
- [ ] 已接纳的同一证据、同值上报、仅新帧编号变化不重复核验；冷却到期而无新证据也不调用。
- [ ] 本地模型与 LLM 可独立启用或并行运行；本地身份不依赖场景变化放行、视频编码或 Agent 在线；未启用／失败不隐式转交另一生产者。
- [ ] 同一底层证据的双生产者结果不重复计数或刷新观察时间；分数不跨模型直接比较，冲突不按返回顺序覆盖，无裁决规则时保持未知或争议。
- [ ] 同镜头多人、多只猫狗分别获得候选处理；身份候选按物种过滤，跨镜头重复证据不会按每帧重复计费，证据不足时不强行合并成员。
- [ ] 猫狗的检测、连续轨迹与已登记个体身份分别核对；同类宠物交叉、遮挡、重入或类别抖动后不盲目延续身份，未知宠物仍可参与适用的区域级场景。
- [ ] 未知目标模糊时不调用，取得合格新画面后可进入核验；场景无变化不阻挡已启用的身份质量筛选。
- [ ] 无轨迹或跟踪失败时，合格画面仍能核验；目标结束不单独否定原时段的出现证据。改绑、撤权、观察修改及参考资料变更按接纳资格检查，迟到结果不覆盖更新观察。
- [ ] 重叠视野不制造位置冲突；镜头覆盖未知或媒体时间不可靠时保留限制，不补造跨房间路径。
- [ ] 媒体在模型返回前淘汰，仍可在证据提交期内核对结果；超期、重复提交及回执丢失分别处理。
- [ ] backend 重启恢复观察意图但重建运行资格；Agent 重启不清空付费预算、不重跑过期任务；断线恢复查询当前候选。
- [ ] 用户可查询人及猫狗的最后出现房间及原时间；更新观察区域未知时保留其未知事实和较早的最后已定位记录。断流不生成离开，身份纠正重算汇总，最后出现不当作当前仍在。
- [ ] 每次调用关联实际任务来源、适用的 watch／候选、证据版本、task、结果接纳状态与策略版本；记录跳过原因、实际请求数和可得用量。

任务与动作阶段另验收：

- [ ] 自然语言任务保存后，时间比较、结构化事件匹配、按位置选设备与固定模板输出均不调用模型；缺少确定性模板明确报告能力缺口，不自动改走 LLM。
- [ ] 已有有效语义情景可供确定性规则直接使用；情景生产的模型调用与业务执行分开记录，输入过期走已配置分支，不等待临时推理。
- [ ] 条件判断与动作决策分别配置；本地条件可派发 Agent 决策，语义条件可直接接既定动作，同次语义判断与决策不强制再调用模型。
- [ ] 本地条件触发 Agent 决策后，在登记后派发前、Agent 接纳后回执前及模型完成后结果接纳前中断，均能按原请求查询恢复；不漏掉已登记请求，不因重送再次付费。
- [ ] 已开始但结果不明的决策不自动重跑；无动作结果可完成，任务停用、版本替换和触发纠正拒绝迟到动作，模型完成与动作成功分开表达。
- [ ] 同一事件首次成立与获准升级可分别触发；纯说明更新、重复提交和多个生产入口不新增提醒；周期重复遵守明确策略，语义附动作与规则消费共享去重身份。
- [ ] 按有效位置选择音箱由普通代码执行，Agent 离线且情景仍有效时可完成；不将上下文读取等同于 LLM 决策。
- [ ] 未完成依赖准备的任务不提前生效；任务保存不创建米家云自动化，Agent 派发成功不冒充设备执行成功。

- [ ] 设备事件、媒体候选与定期综合进入同一执行设施；无摄像头的上下文综合不伪造 watch 或媒体证据。
- [ ] 输入值不变但跨过时间条件可复核；无分析价值时跳过，预算耗尽显示受限；恢复不逐周期补跑，结果不明不自动重跑。
- [ ] 出粮、进食、行为解释和可能饥饿分别记录；匿名猫不强行命名，多来源结果保留原证据及推导关系。
- [ ] 同一迹象的重复总结不产生新事件或提高置信度；新支持、冲突、纠正和过期分别处理，旧判断不循环佐证自身。
- [ ] 关联判断、事件及必要待评估项共同接纳；并发版本冲突或保存失败不发布部分成立结果，不重复生成提醒。

- [ ] 自然语言创建、修改、停用任务的保存回执与行为一致；停止业务任务不撤销共用基础维护。
- [ ] 暂停 Agent 后，情景有效时规则与持久期限仍可执行；位置未知走备用方式，不等待识别。
- [ ] 遛狗事件重复、迟到、纠正、观察缺口与重启分别处理；期限不从模型返回或进程启动重算。
- [ ] 两条路径共用动作入口，事件与动作意图可靠保存；回执丢失可核对，重复证据不反复提醒，结果不明不盲目重发。
- [ ] 事件保存后、规则处理前重启，仍能完成期限重算或适用动作登记；规则事务失败、提交回执丢失及重复领取不丢交接、不重复产生动作。
- [ ] 期限到期遇已接纳但未处理的纠正时先重算；任务停用、版本替换和过期后，恢复不向新版本重放旧动作；未完成项的必要证据不被清理。
- [ ] 能力已实现但基础维护未启用时，不返回正常运行成功；按授权接入共用维护，或明确降级／暂停，缺少事件生产者不能用投递备用渠道掩盖。
- [ ] 基础维护被停用、来源撤权、Agent 离线、预算耗尽或健康摘要过期时，依赖任务显示受影响分支；暂时位置未知与维护不可用分开，仍有效的情景按原期限可用。
- [ ] 重启先核对依赖再恢复资格；关闭意图不因依赖恢复而自动启用，多个任务不重复启动共用维护，单次提醒不等待位置补证。
- [ ] 动物进入与区域存在分别验证；门和位置证据时效匹配，缺少视野不宣称可识别。
- [ ] 开放异常的候选触发不要求已经识别危险；覆盖、费用、模型离线、静止异常与投递延迟有独立验收结果。

“协同进化”的验收是：同一场景能比较不同 Agent 提示词／上下文／工具策略与本地筛选策略的组合，定位误认或费用来自哪一步；调整策略无需把 backend 变成另一套语义模型服务。运行指标不证明长期准确率，模型及本地关联阈值仍须在本项目真实条件下验证。

## 11. 参考与采用范围

- [HA AI Task](https://www.home-assistant.io/integrations/ai_task/)：参考自动化请求结构化模型能力；不采用外部 Agent 分工。
- [Frigate 生成式描述](https://docs.frigate.video/configuration/genai/genai_objects/)：参考目标变化触发和代表帧；身份核验不能照搬“目标结束后描述”。
- [LangGraph 工作流与 Agent](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents)：固定核验与开放任务可在同一应用使用不同流程，共用运行基础。
- [DeepSORT](https://arxiv.org/abs/1703.07402)：参考局部运动与外观关联，不将轨迹编号当成员身份。
- [选择性分类](https://arxiv.org/abs/1705.08500)：允许未知与拒绝；论文保证不自动适用于本项目阈值。
- [MiLoCo 媒体感知与身份识别参考](../references/miloco-perception.md)，固定提交 `cad239dca9b7a2dd3bf0e6565a26cf9eef6581b8`：参考身份状态、样本和 fused 输入；主模型请求与身份重审频率分别核对。本项目由第一方 Agent 组织语义任务，不以共享样本聚类宣称已交付全屋连续位置追踪。
- 同提交的 `plugins/skills/miloco-create-task/SKILL.md` 与 `backend/miloco/src/miloco/rule/{service,runner}.py`：参考自然语言装配结构化任务、独立选择条件来源与动作方式。STATIC 仅表示动作直接执行，视频条件仍可依赖模型；其 `schedule/runner.py` 到期调用 Agent，本项目已明确的期限及设备选择步骤由本地运行器执行。
