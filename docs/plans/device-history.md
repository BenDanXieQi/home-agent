## 交付范围

保存明确选中的属性观测和设备事件，提供有界查询及来源、质量和已知缺口。历史回答“后台当时收到什么”，不重建任意时刻状态或证明记录之间从未变化；精确时长、能耗积分与汇总按实际场景另行定义。消息量用于校准资源，不要求先录满一天。

当前值仍由家庭状态机维护，数据库故障或历史丢失不降低正常采集的当前值质量。原始历史写入允许有界丢失；用户报告、职责与动作使用[工作与执行设计](household-automation.md#用户报告与持续工作)的可靠接纳边界。

## 保存范围与记录语义

保存范围在接入设备采集时扩展本机配置后确定；当前配置尚无历史保存字段。计划中的 `history_enabled=true` 的属性或事件保存全部通过校验并被接纳的观测，不按值去重，不建立多种采样策略。未启用的能力不保存。高频能力是否需要限选或以后增加采样，由实际场景和消息量决定；达到资源上限时明确报告丢失，不悄悄改变保存口径。

每条记录保存：

| 内容                                                                         | 用途                                                                                        |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| observation_id、account_id、home_id、device_id、能力标识及当时房间           | 保留原始身份与归属，名称改变不改写历史                                                      |
| scope_epoch、source_id、collection_generation、input_sequence、state_version | 关联所属运行、来源和处理顺序                                                                |
| received_at、observed_at、effective_at                                       | 原始接收 UTC、可为空的可信来源时间、被用于当前值的时间；候选或迟到值的 effective_at 为 null |
| source、delivery_kind、read_semantics                                        | 区分实时推送、读取、缓存及已知重放，不把它们都称为新发生事件                                |
| value／事件参数、单位与必要枚举说明、规格与来源契约版本                      | 保留当时可解释的值，不依赖后来改变的展示资料                                                |
| policy_version、适用的新鲜度方式及期限                                       | 记录所用配置依据；需要解释的少量字段随记录保存，不依赖独立策略版本库                        |

规则触发与原始设备事件不同，不能为获得事件历史把属性变化伪装成 `siid/eiid` 事件。尚无独立事件通路时不启用该能力。

## 有界写入与恢复

写入器随应用启动和退出，可使用独立 XState actor 管理等待、写入和恢复；不负责切换或同时运行其他家庭。正常停止时停止入队，按关闭期限尽量写完；重新绑定先可靠保存新绑定，再撤销旧运行并关闭旧写入器；旧写入器结束后才启动新家庭的写入器。未完成记录仍保留原身份，不能转交新家庭。

复用 Drizzle 与现有 PostgreSQL／TimescaleDB。下述拆批方式、分块粒度和清理周期是本能力的初始实现选择，可按实际记录规模与故障处理成本调整；调整后仍须满足有界资源、坏记录隔离和明确保留口径的要求。原始接收时间用于时序分区；唯一键包含 observation_id 和分区时间，重试沿用原身份。数据库提交不确定时先按同一键确认或安全重试，不生成新 ID。

| 项目           | 初始工程预算与处理                               |
| -------------- | ------------------------------------------------ |
| 队列           | 最多 10,000 条或 16 MiB，包含正在写入的批次      |
| 批次           | 每 1 秒或 500 条提交，以先到为准                 |
| 单次数据库操作 | 最长 5 秒；确认底层操作结束后才释放在途名额      |
| 瞬时故障       | 1 秒起退避，最长间隔 30 秒，复用原批次           |
| 关闭           | 最多等待 10 秒；未确认数量单独报告，不宣称已保存 |

队列满时拒收新历史记录并计数，不阻塞设备状态提交。坏记录通过有界、顺序拆批定位，合法记录继续保存；连接、权限或表结构错误不按坏数据反复拆分。系统性故障公开原因，写入器按有界退避检查恢复，不要求另建恢复服务。

入队记录固定内容，后续观测不能再修改。私有队列和计数可以直接更新；发布到公共状态的健康摘要使用不可变提交。

## 缺口与健康状态

采集断开、输入丢弃、历史队列拒收和进程异常分别记录，不混成“设备离线”。`collection_gaps` 保存所影响的能力或来源、开始／结束时间、原因及已知丢失数量；未知数量为 null。队列外只保留有界缺口摘要，连续同类故障可扩大范围合并，细节不确定就如实标记，不承诺逐条丢失审计。

`collection_sessions` 记录每次运行的开始、结束及是否正常退出。上次未正常结束时，查询提示未确认尾部可能丢失；已经保存的观测仍有效，不因为运行异常抹掉它们。没有运行或缺口证据时，不声称整个查询区间完整。

历史恢复后继续保存新的合格观测，即使与 latest 同值也正常入库。恢复前的缺口不填成旧值，收到新点后也不推断缺口中一直相同。本能力不重建连续状态，因此无需清理边界值基线或恢复时的人工合成观测。

历史写入器维护 `history_health`，经家庭状态机提交并向页面发布：`{ scope_epoch, status, reason, pending_count, pending_bytes, last_saved_at, updated_at }`。status 为 idle／healthy／degraded／recovering，reason 为安全枚举。它是当前写入健康摘要，不是全历史完整性证明；详细缺口仅按需查询。退出或重新初始化清空运行摘要。

## 查询与清理

本机历史接口仅查询当前绑定账号和家庭。请求携带预期稳定身份 `{ account_id, home_id }`，后台在查询及响应前独立核验绑定与访问资格，身份不匹配返回 409，未授权拒绝；客户端也核对响应归属。同一绑定跨重启可查，记录保留原 `scope_epoch`，不要求等于当前运行。稳定本地家庭迁移时增加本地家庭和来源绑定身份，旧来源历史访问按[家庭生命周期](household-automation.md#家庭生命周期)另行核验。

| 接口                                | 参数与返回                                                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GET /api/mijia/history/observations | account_id、home_id、capabilities、start、end、limit、cursor；返回属性记录、next_cursor、保存口径、已知缺口与 history_health |
| GET /api/mijia/history/events       | 同上，能力使用 siid/eiid；只在真实事件来源启用后提供对应记录                                                                 |

时间范围为 UTC `[start,end)`，默认按 received_at 查询和分页，返回原始时间及 input_sequence。分页排序键为 `(received_at, scope_epoch, input_sequence, observation_id)`；该排序用于枚举记录，不证明物理因果顺序。系统时钟跳变时标注时间不确定，不能用回拨的时间计算负持续时长。运行内处理顺序看 input_sequence，业务计时继续使用单调时钟。

查询最多 20 个能力、跨度 7 天；每页默认 500 条、最多 2,000 条，响应最多 4 MiB。游标绑定稳定身份、过滤和排序键，每页核验当前资格，同一绑定重启不失效。缺口超预算须标为不完整并要求缩小范围。分页不冻结数据库，恢复写入可能补入旧时间记录，响应标明恢复状态。

查询只显示保留的观测与可确认缺口。区间前的值、没有记录的空白和未启用保存的能力，都不能画成已确认持续状态；页面不以插值暗示完整经过。查询响应不写回当前状态。

原始观测与事件使用 TimescaleDB，初始按天分块、保留 30 天；迁移调用 [`add_retention_policy`](https://github.com/timescale/Tiger-Data-Docs/blob/main/src/content/docs/reference/timescaledb/data-retention/add_retention_policy.mdx)，设置 `drop_after => INTERVAL '30 days'`、`schedule_interval => INTERVAL '1 hour'`。数据库清理到期块，失败投影到 `history_health`；实际保留可能多一个块及清理周期，查询公开生效口径。缺口与运行记录使用普通表，仅清理已结束且不再解释保留数据的条目。保留期是可调工程参数，不承诺 30 天完整覆盖。

使用 `device_observations`、`device_events`、`collection_gaps`、`collection_sessions`，表与迁移由现有 Drizzle 管理。临时来源诊断沿用[设备上报日志](../household-runtime.md#设备上报日志)，不另存一份正式历史。

## 历史页面

随历史查询接入有界分页，缓存键包含绑定身份、能力、时间和过滤条件。取消传到请求，关闭周期、聚焦和重连自动刷新，不下载全量记录到浏览器解析。历史响应不覆盖当前值，异步响应核对身份和选定范围，离开页面或切换对象后不写错视图。

显示来源质量、实际保留范围、裁减、缺口与保存健康，空白不插值成连续状态。浏览器未同步与设备离线分别表达；保存故障通过公共健康状态可见，详细缺口按需查询。多页面不增加云端读取，历史故障不清空当前事实。

## 完成条件

- 所选真实观测可保存、分页查询并显示质量；同值报告保留，未支持事件不伪造。
- 数据库故障不停止采集，积压有界，丢失、恢复及异常退出尾部可见。
- 重试复用记录身份，坏记录不连带丢弃合法批次；停止、重启与切换不混入其他家庭。
- 查询、游标与清理遵守当前访问资格、时间和响应预算，时钟异常不产生虚假时长。
- 历史页面展示实际记录和缺口，不覆盖当前值或暗示完整连续状态。

按[共同检查](README.md#每项交付的检查)交付；高级统计和完整历史页面不阻塞不依赖它们的消费者。
