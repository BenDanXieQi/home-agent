# 摄像头感知与推理接入计划

> 状态：P0、P1 已完成；P1 已通过当前 macOS arm64 双摄范围的功能与短时运行验收；P2–P7 待实施。当前功能、模型契约和计算池限制以[本地目标检测](../perception.md)为准。

## 1. 范围与阶段规划

本文规划摄像头音视频接入、本地检测与跟踪、多模态推理，以及感知结果输出。第 2–6 节定义 P1 的架构和验收，第 7 节定义后续阶段的 MiLoCo 参考契约及本项目差异；具体代码随对应阶段实现。

P0/P1 的完成范围是本地图片检测与摄像头持续检测，不包含音频、语义前置筛选或 LLM 调用。后续音视频路由及模型能力的验收分别属于 P3–P5，不追溯扩大 P0/P1 的完成条件。

```text
摄像头 → go2rtc → 解码/采样 → 本地检测 → 检测结果
                         ├→ 跟踪/外观特征 → 轨迹结果
                         ├→ 音频分析 → 声音/人声观测
                         └→ 有界音视频窗口 → 本地前置筛选
                                              ├→ 未通过：跳过，不调用 LLM
                                              └→ 通过 → 调用预算准入 → 裁切/编码
                                                                     ↓
                                                    人物参考资料 → 多模态推理 → 语义结果
```

交付边界是带来源、时间、证据和有效性的感知结果。基础检测完成即发布，不等待跟踪、音频或多模态推理；后续结果独立关联到对应来源和时间区间。成功未检出、没有数据、结果过期和计算失败分别表达，来源中断不等于目标消失。

持续采集和本地检测不触发逐帧或逐窗 LLM（大语言模型）调用。自动语义分析必须先经过 P4 的本地前置筛选，未通过的窗口不编码为模型输入、不提交 P5，也不积压等待补发。MiLoCo 的实时主流程在筛选后执行检测/跟踪与多模态推理；本项目让 P1/P2 独立持续运行是本地计算链路的差异，语义调用仍须前置筛选。

### 实施约束

- P1 已完成，后续 P2 与 P3 可独立推进。P4 可先交付纯视频窗口及视觉前置筛选，未接通的音轨明确不可用；启用轨迹裁切或音频输入时再满足相应依赖。P5 可先输出不带人物身份的语义，但不能跳过 P4 筛选；P6 再增加参考资料与身份识别。
- 每个阶段都验证自己的效果、失败路径和资源清理；P7 负责多能力同时运行的联合测量，不承接前面遗漏的基本验收。
- P0/P1 沿用 `det_4C.onnx`、sharp、ONNX Runtime CPU、Bun 单计算子进程及 Piscina 模型 worker；worker 数在启动时按可用逻辑核数与 `cpuRatio`（默认 0.5）计算。后续模型按所属能力接入，不把现有检测池改成任意模型路径接口，不让音频或语义长任务占住检测名额。
- P2 核对 `human_body_reid_v2.onnx` 的输入和特征归一化；P3 核对 `silero_vad.onnx` 的连续状态与实际音轨。模型资产使用固定来源并记录哈希，不在运行时隐式下载。
- P4/P5 的窗口、媒体编码和模型请求有独立预算；同源语义主流程按序处理，积压有界。P6 的参考资料和样本保存属于身份模块，后台保存不阻塞下一轮推理。
- P2/P4 接入时明确检测、人体裁切和窗口使用的图像及其所有者；保留或复制像素须有字节、数量和存活时间上限，任务结束或来源失效时释放。不能在缓冲区已转移给推理 worker 后继续读取，也不能用新帧替代检测框对应的原帧。P1 仅实现检测所需的像素流转。
- 每项能力只保存运行所需状态；本文不建设通用事件历史或通知系统。文件按实际阶段创建，P1 不预建后续模块。
- MiLoCo 作为媒体处理及推理能力参考，沿用已核对的模型契约，效果与资源行为按本项目验收，不逐项复刻其实现。

### P1 参考基线与实施默认值

以下依据文末固定提交的 `config/settings.yaml`、`perception/collect/camera_adapter.py`、`perception/collect/stream_buffer.py` 和 `perception/runner.py` 核对。路径均相对于 MiLoCo 的 `backend/miloco/src/miloco/`。这些值用于启动实现与测量，不代表本项目已通过性能验收。

| 项目       | MiLoCo 依据                                                                           | P1 采用方式                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 视频采样   | `perception.engine.input.fps: 3`，用于检测/跟踪流水线输入；不是摄像头原始帧率         | 每路默认采样上限 3 fps；来源不足时使用实际新帧，不复制帧凑数，不承诺每路有效检测达到 3 fps                            |
| 首帧等待   | `_FIRST_FRAME_THRESHOLD_MS = 90_000`                                                  | 分析读取启动后默认最多等待 90 秒取得首张完整帧                                                                        |
| 视频断流   | `_SILENCE_THRESHOLD_MS = 30_000`                                                      | 已有帧后连续 30 秒无完整新帧判为断流；只报告媒体故障并交给既有媒体恢复入口，不照搬其物理重连实现                      |
| 帧新鲜度   | MiLoCo 窗口消费选择最新就绪窗口，不能据此推出本项目单帧期限                           | 本项目初始最大帧龄设为 2 秒，从完整解码帧可用时起算，提交与发布均检查；观测同样按该期限过期，不等 30 秒断流阈值才失效 |
| 图像尺寸   | `video_short_edge: 512` 用于多模态视频输入；检测模型输入仍按模型契约处理              | 解码初始保留源尺寸，受 P0 帧限额约束；超限明确报告，按实际负载再配置等比缩小和坐标映射，不把 512 当作检测输入要求     |
| 窗口与积压 | 4 秒窗口、最多 3 个待处理窗口、500 毫秒慢轨道宽限；窗口消费取最新，溢出配置为 `clear` | P1 不等待窗口，使用每路最新帧与轮转调度；窗口和音视频同步留给 P4                                                      |
| 计算预算   | MiLoCo 使用常驻推理线程，本项目使用独立计算子进程                                     | 采用单进程、启动时固定 CPU 比例预算的多个 worker，沿用现有任务/恢复/关闭期限，不复制 MiLoCo 的线程退出方式            |

采样、首帧、断流及帧龄默认值由 P1 配置定义并允许调整。设备与通道、源分辨率和实际帧率从当前已授权来源及媒体信息获取；正式配置仍显式启用来源，不因缺少参数而默认打开全部摄像头。无启用来源时继续完成实现和可执行检查，只有需要实际采集且无法确定授权范围时才询问用户。

## 2. 摄像头与解码接入

- 复用当前家庭已提交的设备清单、授权和媒体连接。通过显式设备列表或 `sources: "household"` 明确启用分析；家庭模式订阅当前已提交设备清单中的摄像头通道增减，采集独立于页面运行。
- 在现有 go2rtc 私有接口下增加 `POST analysis`，使用当前 `sessionId/sourceId`。每个请求持有一个分析消费者，连接结束、源退休、内部通道重建或 session 结束时清理。复用租约，不新增独立 analysis ID、DELETE API 或心跳。
- 分析出口沿用内部访问限制，不公开摄像头凭据；流式写出不持有全局锁，慢消费者不阻塞预览。固定 go2rtc 版本的封装能力和实际 H264/H265 输入须在接入时核对。
- FFmpeg 持续解码，输出契约明确的 RGB24 完整帧。明确采样、输出尺寸、颜色、媒体时间及原图坐标映射；原始帧限额复用 P0。没有可信媒体时间时标记未知，不按帧序号伪造拍摄时间。
- 限制解码进程数量、管道积压、半帧缓存、帧尺寸，以及首帧/断流等待。持续读流不能作为长任务占用推理 worker。
- `prepared` 只说明媒体源配置被接受；实际完整帧到达才说明解码可用。静止画面仍持续采样，不能以无画面变化关闭检测。

双摄按通道分别解码和检测，物理连接及重连仍由现有媒体模块管理。停止一路分析不影响另一路或预览。只因计算失败，不重连物理摄像头。

## 3. 运行边界与状态所有权

```text
backend 主进程
  household/mijia：现有设备及访问资格
  perception/service：来源启停协调
  observation-store：有效结果接纳、当前摘要与订阅
  compute/pool + process：进程监督、IPC 与硬期限
                  │ 控制、状态与结果，不中转持续视频 RGB
计算子进程        ▼
  video/runtime → 每路 video/source → FFmpeg 解码与最新帧槽
  video/scheduler → inference-pool → inference-worker → detector
```

分析流读取通过注入的米家适配器完成，普通视频模块不依赖 `MijiaService` 或摄像头协议。访问描述只包含当前内部端点和会话/来源关联，不包含账号凭据，也不接受页面传入任意 URL。主进程与子进程入口负责组装具体依赖。

访问资格由现有 household/mijia 决定；`service.ts` 根据其已提交状态协调来源启停，把有效运行标识及失效通知传给 `observation-store.ts`。后者只按已授予的运行标识、结果顺序和时间接纳观测，不查询米家、不判断账号权限、不自行恢复访问。失效时先撤销接纳资格，再异步清理执行资源，迟到的健康通知与检测结果同样不得更新新运行。

| 状态                                     | 唯一所有者                                                         |
| ---------------------------------------- | ------------------------------------------------------------------ |
| 家庭、设备清单及授权                     | 现有 household/mijia，感知只订阅已提交状态                         |
| 启用意图与期望来源集合                   | `service.ts`                                                       |
| 已授予的运行标识、最新观测和公开健康视图 | `observation-store.ts`；内存当前视图，公开健康是执行状态的只读投影 |
| 本代视频源实例集合                       | `video/runtime.ts`                                                 |
| 单路生命周期、帧序号与在途任务关联       | `video/source.ts` 的 XState actor                                  |
| FFmpeg、管道、时间映射与拼帧资源         | `media/ffmpeg-decoder.ts`，独占 frame assembler                    |
| 一张最新完整帧                           | `media/latest-frame.ts`，由 source 独占                            |
| 就绪来源顺序与轮转位置                   | `video/scheduler.ts`，不保存像素副本                               |
| 图片/视频共用的计算名额                  | `compute/inference-pool.ts`                                        |
| 模型 session                             | 现有推理 worker / detector                                         |

`video/source.ts` 的 XState actor 属于应用编排，协调读取、解码和任务，不承载米家协议。`observations.ts` 定义观测、新鲜度与结果接纳的纯规则，显式接收运行标识、顺序和时间；这些规则不依赖 XState、FFmpeg、IPC 或 HTTP。`observation-store.ts` 持有规则所需的当前状态并安排过期通知，不承担数据库保存或采集调度。

`process-entry.ts` 是计算子进程的依赖组装入口，可以组装视频运行模块；`compute/inference-pool.ts` 只负责计算准入与执行，不管理来源集合、授权或观测发布。`video/runtime.ts` 协调来源与调度器，通过注入的计算能力提交任务；进程协议适配负责把消息转成应用调用，避免视频模块与计算池相互导入业务实现。

内部观测、IPC 消息和公开 HTTP/SSE 响应分别在其边界定义。`packages/api` 只放实际跨应用共享的公开 schema；领域规则不依赖 HTTP 响应结构或 SSE 事件封装。接口适配层把内部当前视图转换成公开响应，类型从已有 schema 和实现推导，不重复手写类型。真正跨项目共用且不含传输细节的契约放在根目录 `packages/`，不为尚未出现的复用预建抽象。

主进程保留 IPC 传输预算、未完成请求和任务硬期限，不另维护一套模型执行名额。图片与视频的实际计算准入统一由子进程中的 inference-pool 管理，主进程只保留有界 IPC 请求及失败监督。每个视频检测任务都有可监督的提交、完成、失败和期限，不能只给启动长流设置一次超时。

计算侧持有 FFmpeg 可以避免主进程中转 RGB，但必须先核对目标环境的进程树清理。正常关闭由 decoder 收尾；计算进程异常或被强制终止后，监督者仍需确认 FFmpeg 已回收。不能确认时停止重建并报告，不能把发送信号视为退出完成。若宿主无法可靠支持，先调整进程布局再接入，不受目录命名约束。

## 4. 调度、失效与输出

每路最多一个已提交未完成的检测任务和一张最新待处理帧。新帧替换未提交帧，不为追新强制取消原生推理。调度器在有名额时轮转选择就绪来源，不预先把旧帧填满 FIFO，也不在池忙时循环重试。

提交前与发布前检查最大帧龄。退出、撤权、重新绑定、源替换或计算重建后，使用家庭 `scope_epoch`、来源运行标识与任务关联拒绝旧结果；原有媒体恢复负责重新取得来源，感知不自行延长授权。

完整关闭有期限，覆盖分析读取、解码、在途请求与计算资源。来源退休立即撤销结果资格，不等待推理完成。单路解码失败只影响该路；共享计算池失败时，各路健康准确反映不可用，恢复后只处理当前有效来源的新鲜帧。

感知配置无效、FFmpeg 不可用或模型初始化失败时，感知服务报告不可用及具体原因，健康查询仍可访问；设备清单、预览和 backend 其他功能继续运行。初始化中已创建的分析读取、解码器和计算资源也必须按关闭期限清理。

输出至少包含来源与通道、运行标识、帧序号、采样/接收时间、尺寸及框坐标基准、类别与置信度，以及观测有效性。内部会话标识、读取描述不暴露给页面。模型与配置元信息按运行记录，不逐帧重复。

- `GET /api/perception`：来源健康、计算状态与最新观测摘要。
- `GET /api/perception/stream`：订阅当前状态更新，发送缓存与写入等待有界。
- `POST /api/perception/retry`：由感知服务合并并发请求；已取得检测池实例时调用其显式重试，初始化失败且未取得实例时重新初始化。重新创建计算资源前须确认旧资源已回收，不重连物理相机；配置和宿主依赖的启动设置修改后仍需重启。

无新帧时旧观测也会过期。查询和订阅读取同一当前视图，慢订阅者不阻塞检测；不建立历史回放、媒体保存或数据库写入通路。

| 交付点       | 已通过的验收范围                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| 分析流接入   | 真实双摄分析流可读取，与预览共存；取消分析不影响预览；旧运行结果和健康事件被拒收                      |
| 持续解码     | RGB 转换前选择真实帧，低帧率不补帧；完整帧与缓冲有界；单路中断隔离和恢复正确                          |

| 结果查询     | 摘要、订阅、过期和显式重试可用；慢订阅不阻塞检测；计算失效与重试后的健康状态准确                      |

### 验收口径

P1 使用分钟级持续测量结合故障注入和反复启停完成验收，不要求两小时或全天常驻作为阶段完成条件。复测先区分预热与统计窗口，按当前启用设备核对实际配置、逐路观测间隔、帧龄、CPU、RSS（驻留物理内存）、进程数量及清理结果。P0 图片基准不能替代真实视频链路验证。

逐路指标从采样后完整 RGB 帧开始统计，覆盖提交、发布、替换、过期、拒绝和失败，在途单列；模型完成与主进程接纳发布分别计数。FFmpeg 内过滤掉的帧数及源端总帧数不报告，不能解释成零。帧龄从本机完整 RGB 帧可用起算，不能当作物理拍摄延迟。

配置无效、FFmpeg 不可用、模型初始化失败、计算恢复预算耗尽及显式重试属于功能验收；单路媒体清理和计算硬超时后的整组回收分别验证。合成 H264/H265、失效运行拒收和过载测试补充实机检查，不冒充其他设备或固件的实机覆盖。

测试和测量遵守仓库授权规则，只运行受影响的针对性检查。原始实测与复核记录保存在 Git 忽略的 `data/perception/`；功能文档只维护当前能力、使用方式和验证范围。

### 验证范围与后续部署测量

以下属于当前验证范围的限制，不作为 P1 未完成项：

- 全天运行及长期内存增长趋势尚未验证。需要无人值守部署时，按目标时长单独测量。
- 实际账号撤权/重新绑定、物理断网或自然断流，以及其他固件的实机 H264/H265 行为尚未全部覆盖；现有故障注入验证对应执行边界。
- 真实八路、4K 负载及其他宿主尚未验证，不能由双摄短时结果外推。

部署前按实际可用核数、cpuRatio、路数和分辨率制定资源预算。CPU 比例约束推理并发，不是整机 CPU 或 RSS 硬限额；默认多模型会话不能按 1 GiB 总内存保证部署。更高负载、其他平台和长期运行需要各自的部署测量，P7 另负责实际启用能力的联合性能评估。

### 模块职责与依赖

以下位置相对于 `apps/backend/src/`，随对应阶段创建；模块边界按领域职责确定，运行进程按资源隔离要求组装。沿用[家庭语义模型](household-model.md)中基础感知与语义理解的职责划分，不把后续能力都塞入 P1 的 `video/source.ts` 或 `observation-store.ts`。

| 阶段与位置                                                            | 状态所有者与规则                                                                                         | 外部边界                                                                                                        |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |

基础感知向语义理解提供带来源和时间的结果及受限媒体引用，语义模块不修改基础观测，也不控制物理连接。P1 检测独立发布；跟踪消费对应帧的检测结果，窗口按媒体时间收集输入，不等待检测完成才接收媒体。各消费者按自身预算处理，过载可以跳过输入并报告缺口，不能反压基础发布或无限占住媒体引用。纯规则不读时钟、文件、网络或全局可变状态；应用编排传入所需数据，资源适配负责外部系统。

P6 合并进 P5 调用时，由 `scene-understanding/service.ts` 取得身份候选和参考资料快照，组织模型输入，再把结构化身份回答交回身份模块判断；供应商适配不调用身份模块，身份模块也不直接调用语义 service。同一次模型响应中，场景语义与身份候选分别按自身证据和版本接纳，人物资料失效不直接抹掉其他有效语义。P5 未接入 P6 时可以独立运行，结果不依赖身份字段。

### P2 人体跟踪

参考 `engine/identity/{deep_sort.py,tracker/human_reid.py,tracker/tracker.py,default_config.yaml}`。MiLoCo 的 DeepSORT 只对人体形成轨迹，猫、狗、头部和人脸仍可作为检测结果；本项目采用同一范围。通过外部检测结果入口复用 P1 的框及对应原帧，避免再跑一次检测。轨迹标识只在来源运行内有效，不等于人物身份。

- `human_body_reid_v2.onnx`：人体裁切线性缩放到高 192、宽 96，BGR 顺序、float32 `[1,3,192,96]`，像素不除以 255；输出节点 `head/out_emb:0`，参考形状 `[1,1,1,128]`，展平后做 L2 归一化（向量长度归一为 1）。P1 的 RGB 帧须在此模型边界转换通道顺序。
- 初始沿用 `n_init=1`、检测确认阈值 `0.5`、失配保留 `2 秒`、`mode=fast` 和 `human_reid_skip_windows=4`。跳过静止目标的重复特征推理时复用已有特征；其计数单位按 tracker 实现核对，不把字段名当作 P4 的音视频窗口数。
- MiLoCo 将失配秒数按配置帧率换算成帧数；本项目存在最新帧替换，须按实际时间间隔推进位置预测和失效，不把每次处理都当作固定间隔。特征缺失、预测框和实测框分别表达；特征或关联失败不阻塞 P1 发布检测。

### P3 音频与人声观测

参考 `engine/gate/{audio_gate.py,speech_vad.py}` 和 `engine/config.py`。本项目当前 go2rtc 私有源设置 `audio=0`，双摄 `dual_camera.go` 设置 `enableaudio:0` 且只声明视频媒体；P3 必须完成源端启用、真实音频包探测/分发、分析出口及 PCM（解码后的音频采样）链路，不能只增加 VAD 调用。双摄共享音轨只解码和分析一次，两个通道引用同一音轨；视频和音频分别判断就绪与断流。

- 初始采用 16 kHz 单声道 int16 PCM。能量检测沿用 30 毫秒分块，计算每块均方根能量并除以 32768，窗口取峰值，阈值 `0.015`；它只表示声音能量，不区分哭声、犬吠或语音内容。
- `silero_vad.onnx` 使用每块 512 个采样，前置上块末尾 64 个采样，float32 输入 `[1,576]`、值除以 32768；状态 `[2,1,128]`，采样率输入为 int64 `16000`。输入名 `input/state/sr`，输出名 `output/stateN`。初始概率阈值 `0.4`；参考窗口内至少 3 块过阈才判有人声。
- MiLoCo 每次 `evaluate_speech` 重置状态，在窗口内续接，且忽略不足一块的尾部。本项目持续音频链路按音轨运行保存状态、64 点上下文和不足 512 点的余量；连续块只处理一次，断流/运行替换时重置。P3 及时发布分块概率和能量，P4 按 4 秒窗口汇总并应用至少 3 块过阈的判据，重叠窗口不重复推进模型状态；不足一块时保持输入不足，不输出否定人声结论。
- MiLoCo 在 VAD 不可用时放行语音字段；本项目输出未知/不可用，不生成肯定人声观测。能量低、人声未检出、输入不足及无音轨分别表达；识别具体声音类别和转写内容属于 P5。

### P4 窗口、前置筛选与裁切

参考 `collect/stream_buffer.py`、`engine/{config.py,pipeline.py}`、`engine/gate/{gate.py,visual_gate.py}` 及 `engine/omni/{crop_enhance.py,prompt_builder.py}`。初始采用 4 秒窗口、最多 3 个待处理窗口和 500 毫秒慢轨道宽限；消费最新就绪窗口，积压时丢弃旧窗口并计数。还需限制总字节、编码任务和在途引用，不能把窗口数量上限当作内存上限。缺轨和首个不完整窗口显式标记，本项目不因缺少音轨长期等待纯视频分析。

自动语义调用采用以下前置判据，先筛选和检查调用预算，再做模型输入裁切、编码与请求：

| 窗口条件 | 语义处理 |
| -------- | -------- |
| 视觉有变化，或仍在视觉变化后的放行期内且本窗有视频帧 | 允许视频语义分析；仅在音频能量过阈且所选模型的带音轨视频输入已验证时附带音频 |
| 视觉未放行，但音频能量过阈 | 仅允许音频语义分析，不附带静止视频；供应商不支持纯音频时报告能力不可用 |
| 视觉未放行，音频也未过阈或不可用 | 跳过窗口，不编码、不调用 LLM；不生成“无人”或“无活动”结论 |
| 无有效媒体，或筛选失败且没有其他已通过的媒体 | 跳过并报告缺失或失败，不默认放行原始视频 |

音频能量决定是否需要分析声音，VAD 进一步决定是否请求语音内容；未检出人声不阻止对犬吠等非语音声音的分析。筛选通过不代表已识别活动或人物。

MiLoCo 在本地分别判断画面变化、声音能量与人声，随后选择视频或纯音频路由。参考提交的两条路由共用 `model.omni` 配置（默认 `xiaomi/mimo-v2.5`）：视频路由将通过音频筛选的音轨封装进 MP4，经 `video_url` 提交；纯音频路由经 `input_audio` 提交 M4A，不附带视频、人物参考图或视觉身份候选。它不是固定分别调用一个视觉模型和一个音频模型，也不是每窗都同时提交音视频。源码证明输入构造与调用方式，不证明每个部署端点均正确理解这些媒体。

- 视觉筛选参考 1 fps 检查、448×448 灰度帧、像素差大于 25 的比例达到 `0.005`；保留跨窗比较基准，首个有效窗口放行。沿用 MiLoCo 的 90 秒视觉放行期：从最近一次视觉变化起计时，期内静止但有帧的窗口仍可进入视频分析；仅因处于放行期而通过的窗口不续期。它不是“每 90 秒调用一次”，持续运动可持续续期，仍须受 P5 调用预算约束。所有筛选只控制语义调用，不停止 P1 检测或 P2 跟踪。
- 多模态视频初始采用 1 fps、短边 512，与检测采样及模型张量尺寸分开配置；音视频时间关联使用实际时间，不按帧数虚构时长。编码后的音轨、帧率、时长和裁切坐标应一致，缺轨不可伪造为静音。
- MiLoCo 智能裁切使用窗口内逐帧检测框与运动区域的并集，而非仅用末帧人体轨迹；本项目同样保留宠物等检测框及全景参考。初始采用水平/垂直扩展 `0.40/0.30`、最小区域占比 `0.10`、最大 `0.49`；无合适区域时使用全景，映射后的框裁到有效范围。全景与裁切使用同档尺寸预算，裁切失败不拖住基础链路。

### P5 语义推理

参考 `engine/omni/{omni.py,omni_client.py,provider.py,response_parser.py,field_registry.py,circuit_breaker.py,error_classifier.py,probe.py}`。供应商协议留在适配器，按实际支持的视频、音频及结构化输出能力组织输入；不因接口形式兼容就假定媒体能力相同。使用本项目实际配置的模型和凭据，初始请求期限参考 MiLoCo 的 30 秒；缺少凭据时报告语义不可用，其余感知继续运行。

模型能力按具体型号与端点分别验证无音轨视频、纯音频、带音轨视频；支持前两项不能推定支持第三项。官方能力说明作为接入依据，实际素材中的画面、声音及语音内容须分别核对，HTTP 成功不等于理解正确。带音轨视频未验证或不支持时，视频请求只提交无音轨画面并省略声音/语音输出；已通过筛选的音频仅在显式配置且已验证的独立音频调用下分析，否则报告音频语义不可用，不自动新增一次模型请求。独立音频调用属于本项目按模型能力选择的接入方式，不宣称是 MiLoCo 参考提交的默认流程；启用时同样遵守调用预算，结果按来源和实际时间窗口关联。

自动场景请求只接纳 P4 放行的窗口及媒体类型。筛选用于减少无变化输入，但不能保证调用费用上限：持续活动、噪声和视觉放行期都可能连续通过。P5 启用时须配置每来源最小调用间隔、全局单位时间请求上限及单次媒体/输出上限；超出预算跳过并计数，不排队补发全部历史窗口。具体值随所选模型和可接受费用确定，这是本项目的调用预算要求，不宣称 MiLoCo 已提供同等费用上限。记录放行、跳过、实际请求数及供应商返回的 token 用量；未返回用量时标记未知，不能用本地检测帧数估算 LLM token。恢复探测与 P6 自动样本校验等额外模型请求也计入全局请求预算。

P4/P5 交付须核对静止安静且放行期结束后没有自动语义请求、仅音频触发不携带视频、持续活动受预算限制，以及未通过和超预算窗口不会补发。只有同源顺序处理或限制并发，不能作为调用量受控的验收依据。

输出范围为活动、可见场景、声音及语音内容等有窗口证据的语义。MiLoCo 输出中的规则匹配和动作建议不纳入本计划。按当前 schema 校验结果，解析失败不能变成空场景或无人结论；同源主流程按序处理，来源失效后的迟到响应不更新当前结果。

失败隔离参考其熔断机制（连续失败后暂停调用，再探测恢复）：初始连续失败阈值 3，或 60 秒内至少 5 次调用且失败率超过 0.5；可恢复故障退避从 1 秒开始倍增，限流基准上限 60 秒、其他可恢复故障基准上限 600 秒，在基准上增加 0–20% 随机等待。尊重供应商返回的 `Retry-After` 等待要求，不通过抖动缩短它。配置错误等待修正或显式探测，手动探测冷却 5 秒。恢复探测有唯一在途所有者且不依赖新媒体到达；不让每路来源各自无界重试同一供应商。

### P6 人物参考与身份识别

参考 `engine/identity/{default_config.yaml,state.py,engine.py,dispatcher.py,library.py,gallery_composite.py,registration_session.py,registration_filter.py,tier_u.py}`。沿用参考图片、轨迹候选、模型确认、重审与纠正的链路；初始把身份候选合并进 P5 同一次多模态调用，复用已算出的外观特征。身份结果只能关联本轮提交的轨迹与参考人物，允许未知；外观相似不直接确认身份。

身份候选只合并进有对应视觉证据的视频请求；纯音频请求不携带人物参考图或轨迹候选，不产生视觉身份确认，也不因一次音频调用刷新身份重审结果。

- 默认值以 `default_config.yaml` 为依据：候选派发间隔 5 秒、每次最多 4 个、候选有效期 30 秒；确认阈值高/中/低为 `0.85/0.65/0.50`，所需一致回答次数为 `1/3/3`，低于 `0.5` 为未知。普通重审 30 秒、样本积累期间 10 秒，连续 2 次不一致后退回待确认。本项目按实际时间计时，调用失败不计为身份否定票。
- 区分用户登记资料和自动积累样本。参考每人登记样本上限 10（身体、人脸各 5）、自动身体样本上限 10；写入初始要求连续 6 次已确认重审一致，并通过置信度至少 `0.8` 的同人校验，矛盾或无有效证据时不得累计资格。只有通过校验的自动样本才能重新作为参考，未经验证的模型判断不得自我强化。显示身份与样本写入资格分开，后台保存有界且不阻塞后窗。
- 参考误检抑制、身份漂移检查及人物资料变更后的重审；这些只更新身份/轨迹解释，不删除 P1 的原始检测事实。陌生人默认统一为未知，不把临时聚类编号当作真实人物。MiLoCo 中未实现的独立身份调用模式、中期样本晋升和声纹绑定占位不作为本项目交付依据。

### P7 联合测量

MiLoCo 的帧率、窗口、阈值及源码中的性能注释是参考配置，不能证明本项目达到相同性能。使用相同素材核对检测、跟踪、音频和语义效果，并在实际摄像头上验证联合运行；分别记录缺帧、身份纠正、语义失败以及第 6 节的逐路延迟和资源指标。线程、采样和编码参数按实测调整，保持基础链路独立、结果有效性与资源清理约束；缺少最终部署门槛不阻塞已具备条件的能力实现及探索测量。
